# Nori persistent-index measurements

The SQLite and redb benchmark entrypoints live in `uqa-storage-sqlite` and `uqa-storage-redb`. They exercise each provider's public inverted-index and transaction APIs with the pinned Nori revision. Shared measurement code lives in `benchmarks/nori/persistent.rs`; it contains fixture construction, timers, allocation instrumentation, and output verification. No Engine algorithm or runtime dependency is added. Both benchmark targets require the dependency feature `uqa-analysis/nori` and leave their provider's runtime features unchanged.

```sh
python3 scripts/run-nori-persistent-benchmark.py --provider sqlite --output target/benchmark-runs/nori-sqlite-native.json --allocation-only
python3 scripts/run-nori-persistent-benchmark.py --provider redb --output target/benchmark-runs/nori-redb-native.json --allocation-only
python3 scripts/run-nori-persistent-benchmark.py --provider sqlite --target wasm --output target/benchmark-runs/nori-sqlite-wasm.json --allocation-only
```

The corpus and document identities match the [Memory-index benchmark](INDEXING.md). Four workloads commit a 256-document batch into an empty index, commit 16 additional documents after 256 or 2,048 existing documents, and roll back 16 appended documents after 2,048 existing documents. A closed seed database is copied into a fresh temporary directory for every sample. `--allocation-only` executes one allocation sample per workload, without warmups, clock reads or timing fields. CI uses this mode. Input construction, transaction begin, index mutation, and commit or rollback are counted. Seed creation/copying, connection initialization, close, graph checking, and reopen are excluded.

Every execution is checked against an independently built Memory index, both through the live provider and after dropping every database handle and reopening the file. The digest includes every document's versioned source/revision metadata, sorted canonical term keys, and complete encoded score/occurrence clusters. Document count, field length, and posting count are verified separately. The rollback workload must retain the seed graph and document count. Both sampling modes enforce the same six allocation ceilings and complete output contract. The gate rejects missing workloads, incomplete sampling, changed graphs/counts, and omitted reopen checks. Reviewed allocation limits use the transaction model and exact target OS, architecture, and pointer width; an unmeasured model or target requires calibration and cannot inherit another ceiling. A failing check reports every exceeded allocation ceiling from the report in one error, after validating all workload outputs and limits. An earlier allocation excess cannot hide a later changed graph.

Without `--allocation-only`, seven timed operations follow one warmup and a separate operation records allocations; all nine executions receive live/reopen verification. Timing comparisons require a controlled host and an independently established noise bound. On such a host, collect a timed report without `--allocation-only`, then supply that report with `--baseline` for the comparison. Allocation-only reports cannot contain timing observations or serve as either side of a timing comparison. Run authorized measurements sequentially after other builds finish.

Native measurements use files on the host temporary filesystem. The SQLite report reads its actual library version, journal mode, synchronous setting, and page size from a connection. redb uses its default immediate commit durability. SQLite WASM measurements use Emscripten's virtual filesystem in Node, so their results cover provider serialization and transaction behavior without host filesystem durability or browser storage synchronization. This matrix measures native SQLite/redb and WASM SQLite; it does not claim a WASM redb result.

The SQLite entrypoint opens `Catalog` and `SQLiteInvertedIndex` directly on an unbound `ManagedConnection`, exercising native physical transactions. The redb entrypoint opens the provider's current public store, which now uses common logical MVCC transactions. These entrypoints therefore verify different transaction implementations. Passing the SQLite allocation check does not establish allocation acceptance for bound native MVCC or SQLite Key/Value sessions; those remain required in the [concurrent-storage implementation plan](../../docs/plans/0008-concurrent-storage-transactions.md).

Each entrypoint checks its actual transaction model on open and reports it explicitly. Every redb workload additionally verifies that its private transaction allowance returns to zero after commit or rollback, before graph verification and provider close. This retained allowance is separate from redb's shared page cache and supplements all six allocator counters. SQLite's physical transaction entrypoint reports no private MVCC allowance.

Pre-merge CI accepts `run_rust=false` with `run_nori_allocations=true` for allocation/output verification without timing samples. SQLite and redb run as separate required steps, so a failed provider still leaves the other provider's diagnostic report available. The obsolete two-table redb commit-order probe has been removed; it described the pre-MVCC layout and cannot justify the current provider's budget. The MVCC budget review must retain explicit target evidence and explain any dependency-internal allocation variation.

Allocation counters measure current-thread Rust allocator requests during the operation. They exclude the existing index, dictionary, C allocations inside SQLite/SQLCipher, OS page cache, stack, and JavaScript heap. Net allocation can include released seed-owned buffers. File observations are the sum of closed file lengths, including remaining sidecars, rather than allocated disk blocks or a peak disk-space measurement. SQLite and redb have different transaction and durability costs; their elapsed times are reported separately.

Reports include CPU, platform, compiler versions and flags, C compiler overrides, executable hashes, runtime-source hashes, and both entrypoint/shared benchmark-source identities. Home directory prefixes in flag text become `${HOME}` for publication, while the SHA-256 of the complete original flag dictionary preserves exact comparison identity. A same-environment timing comparison rejects changed original flags, durability/filesystem scope, and benchmark code. Candidate collection uses `--measure-only` and records a false gate status until checked against reviewed limits. The instrumented benchmark is excluded from Cargo archives.

These measurements cover provider index operations and explicit provider sessions. SQL parsing, row storage, catalog assignment, Engine/session snapshots, phrase scoring and browser host memory have separate workload contracts. Concurrent-storage acceptance is tracked in its [implementation plan](../../docs/plans/0008-concurrent-storage-transactions.md).

Generated reports stay in ignored output directories and CI artifacts. See the [report storage and timing policy](README.md#report-storage-and-timing-interpretation); historical source references in the limits do not establish performance acceptance on an uncontrolled host.

## MVCC allocation budgets

The redb limits originally described the serialized `uqa_key_value`/`uqa_storage_metadata` provider. The current provider instead owns private MVCC history and preconditions, short physical commits for transaction allocation and publication, separate head/version records, durable receipts and a shared page cache. Reusing that former budget confounds the changed storage contract with regressions. The revised limits require `versioned_concurrent`; SQLite retains its `provider_serialized` budgets unchanged. Limits schema 3 rejects an unspecified or mismatched transaction model.

Before calibration, common storage and redb were corrected to share evaluated keys/values with private history, move occurrence vectors during staging, validate field revisions once per fixed read, reuse a charged physical encoding workspace, look up visible head revisions directly, borrow large committed occurrence streams and preserve canonical conditions for atomic admission. Quota, cancellation, corruption, conflict, savepoint and retained-snapshot regressions remain in the owning crates. The same four workload inputs, output graphs and six allocator metrics remain mandatory.

The budget uses one complete allocation-only observation per target. Counts, retained bytes and peak bytes use the exact observation. Commit `bytes_total` adds only the independently derived maximum nine-byte range from redb 4.1.0's table-root update order; rollback adds zero. There is no timing-derived or percentage margin. All completed private transaction allowances must return to zero independently of these ceilings.

That nine-byte range follows the dependency's `tree_store/table_tree.rs`, `tree_store/table_tree_base.rs` and `tree_store/btree_mutator.rs`: pending table roots drain a randomized map; in the single-leaf table directory, the first replacement retains the old committed page while subsequent replacements copy their old definition value. The serialized definitions have equal fixed overhead and type-name payload lengths of 9 bytes for metadata, 8 for heads, 16 for versions and 8 for receipts. Transaction allocation updates metadata/receipts, giving a range of `9 - 8 = 1` byte. Publication updates all four, giving `16 - 8 = 8` bytes. Each committed workload has these two physical commits; logical rollback has neither. Adding their ranges bounds the unknown order in one observation without repeatedly sampling until a preferred outcome appears. Changing the dependency, table types, directory shape or physical commit schedule requires reviewing this derivation.

A prior cache-layout diagnostic observes 57,664 cached bytes after binding the 2,048-document seed and 12,448,064 after either append or logical rollback: a 12,390,400-byte shared-cache increase. Its ignored 740-byte log has SHA-256 `32b1ec40db8a137acb957c0c8b6cae85bbde6ae506ae76ddd0aefd9cd282a320`. This explains most of the macOS rollback's 12,405,364 retained allocator bytes; it is not a private-history allowance or a timing result. The current workload directly verifies zero private retention before close, and the owning tests verify release after the final retained snapshot drops. The fixed workloads do not establish an unbounded-history reclamation policy; reclamation remains in the concurrent-storage plan.
