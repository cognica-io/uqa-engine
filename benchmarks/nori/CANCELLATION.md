# Nori cooperative cancellation measurements

The existing `uqa-analysis` benchmark has a separate `--cancellation` mode using the public budgeted tokenizer and analyzer APIs. It covers all six fixed corpora, three decompound modes, both analysis scopes, and cancellation at the first, middle, and final poll of a complete successful operation: 108 workloads. The ordinary analysis mode keeps its existing 39 measurements and reviewed gates. Both modes record the additional source module in their benchmark identity. No runtime algorithm, dependency, Cargo feature, or test target changes.

Each workload retains an unrelated 4,096-byte reservation in a 256 MiB allowance. Every cancelled call must return `AnalysisError::Cancelled`, stop at the selected poll, and restore exactly that unrelated reservation. After two warmups, each of seven samples executes the same selected count of interrupted operations in batches of 16 and must last at least 75 ms. One additional operation measures allocations. The reported cancellation count must equal every timed operation plus the warmups and allocation observation. Ten subsequent complete recovery operations compare every native token and stream-end field with the successful result. The report's recovered output hash and token count must also agree with the existing analysis contract. Allocation observations must retain zero additional bytes and allocations.

The runner first collects a complete timed pilot in a separate process and selects twice the largest pilot operation count for each workload. It then starts a fresh measured process with that complete plan. A repeat uses the baseline's original plan and pilot, so both measured processes execute exactly the same work with the default allocator. Native and WASM receive identical canonical plan bytes as a command-line argument, without requiring host-file access from WASM. Schema-version-3 reports retain the plan, its hash, the complete pilot and source provenance, and the exact measured invocation. Validation checks every pilot result, the selected count rule, matching CPU/toolchain/flags/benchmark identity, all fixed sample counts, and the minimum duration. Historical schema-version-2 reports remain readable for evidence review; a new measured repeat requires a baseline with the fixed plan.

## Timing scope

Every interrupted operation records entry-to-return time and callback-decision-to-return time. The latter includes workspace destruction and clock-call overhead. It begins when the cooperative callback decides to return the cancellation error; it does not measure the interval between an external signal and the next poll, scheduler latency, or a preemptive interruption. Verification and recovery occur outside those intervals. Per-sample values sum the individual observations, and the estimator is the median of each sample's duration divided by its actual operation count. Separate wall durations establish the minimum sample length, include per-call verification, and exclude subsequent recovery. Both supported report versions require both timing scopes to contain the same complete operation counts. A zero value remains a valid observation below clock resolution but cannot establish a timing-comparison ratio.

The collector previously constructed JSON records between workloads. With the workspace's `serde_json/arbitrary_precision` feature, timing-dependent numeric strings introduced variable allocations into the heap used by subsequent operations. The collector now retains typed numeric records and fixed-size sample arrays, reserves the complete record inventory up front, and converts records to JSON only after all workloads finish. This removes reporting allocations that depend on earlier timing values. The sampling protocol and JSON schema remain unchanged; repeated measurements of the revised collector must establish its actual effect before calibration is accepted.

Rust allocation counters cover one interrupted operation on the current thread. Preloaded dictionary/input/reference results, the allowance handle, the unrelated reservation, and host memory are outside that scope. Each new reference count and cancellation position comes from the same fixed complete input; changing the polling schedule makes a timing baseline incomparable until reviewed again.

## Regression policy

`cancellation-limits.json` retains the complete recovery contract, polling schedule, exact allocation ceilings for macOS aarch64, Linux x86_64, and Emscripten WASM, and references to historical source reports. Additional retained allocations and bytes must remain zero. Generated measurements and diagnostics remain in ignored output directories and CI artifacts.

Explicit timing comparisons retain the 1.26 ceiling and require the same CPU, platform, compiler, flags, benchmark source, arguments, inputs, polling schedule, and sampling protocol. Both complete-operation and callback-to-return medians are checked independently for every workload. The checker tests cover complete fixed plans, source identity, every allocation counter, recovery, invalid samples, and both timing scopes with deterministic inputs.

```sh
python3 scripts/run-nori-cancellation-benchmark.py --output target/benchmark-runs/nori-cancellation-native-baseline.json
python3 scripts/run-nori-cancellation-benchmark.py --baseline target/benchmark-runs/nori-cancellation-native-baseline.json --output target/benchmark-runs/nori-cancellation-native-repeat.json
```

The first report enforces allocation, complete recovery, reservation cleanup, inputs, and sample validity. A repeat also checks all 216 timing comparisons. `--measure-only` records an unaccepted candidate and cannot be combined with a timing baseline. Full CI and the standalone cancellation workflow expose this paired comparison for explicit benchmark runs; it is not a merge prerequisite. Apply the [controlled-host timing policy](README.md#report-storage-and-timing-interpretation); matching process identities alone does not establish stable host timing.
