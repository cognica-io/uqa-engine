# Nori cooperative cancellation measurements

The existing `uqa-analysis` benchmark has a separate `--cancellation` mode using the public budgeted tokenizer and analyzer APIs. It covers all six fixed corpora, three decompound modes, both analysis scopes, and cancellation at the first, middle, and final poll of a complete successful operation: 108 workloads. The ordinary analysis mode keeps its existing 39 measurements and reviewed gates. Both modes record the additional source module in their benchmark identity. No runtime algorithm, dependency, Cargo feature, or test target changes.

Each workload retains an unrelated 4,096-byte reservation in a 256 MiB allowance. Every cancelled call must return `AnalysisError::Cancelled`, stop at the selected poll, and restore exactly that unrelated reservation. After two warmups, each of seven samples executes the same selected count of interrupted operations in batches of 16 and must last at least 75 ms. One additional operation measures allocations. The reported cancellation count must equal every timed operation plus the warmups and allocation observation. Ten subsequent complete recovery operations compare every native token and stream-end field with the successful result. The report's recovered output hash and token count must also agree with the existing analysis contract. Allocation observations must retain zero additional bytes and allocations.

The runner first collects a complete timed pilot in a separate process and selects twice the largest pilot operation count for each workload. It then starts a fresh measured process with that complete plan. A repeat uses the baseline's original plan and pilot, so both measured processes execute exactly the same work with the default allocator. Native and WASM receive identical canonical plan bytes as a command-line argument, without requiring host-file access from WASM. Schema-version-3 reports retain the plan, its hash, the complete pilot and source provenance, and the exact measured invocation. Validation checks every pilot result, the selected count rule, matching CPU/toolchain/flags/benchmark identity, all fixed sample counts, and the minimum duration. Historical schema-version-2 reports remain readable for evidence review; a new measured repeat requires a baseline with the fixed plan.

## Timing scope

Every interrupted operation records entry-to-return time and callback-decision-to-return time. The latter includes workspace destruction and clock-call overhead. It begins when the cooperative callback decides to return the cancellation error; it does not measure the interval between an external signal and the next poll, scheduler latency, or a preemptive interruption. Verification and recovery occur outside those intervals. Per-sample values sum the individual observations, and the estimator is the median of each sample's duration divided by its actual operation count. Separate wall durations establish the minimum sample length, include per-call verification, and exclude subsequent recovery. Schema-version-2 reports require both timing scopes to contain the same complete operation counts. A zero value remains a valid observation below clock resolution but cannot establish a timing-comparison ratio.

The first clean repeated measurements at `fe36f0af` used only 16 operations per sample. All 108 workloads had identical repeated allocations on macOS aarch64, Linux x86_64, and Emscripten WASM, with successful cleanup and complete recovery. The [native/WASM workflow](https://github.com/cognica-io/uqa-engine/actions/runs/34766040793) also passed the ordinary analysis gate. However, the shortest WASM cancellation samples varied by up to 1.734 times: one response median changed from 1,100.125 ns to 634.5 ns. That pair cannot justify widening the timing limit for every workload. The 75 ms minimum matches the existing successful-analysis benchmark's sampling duration and replaces the short protocol; its actual repeated results must be reviewed before establishing timing limits. The earlier reports remain downloadable as artifacts `10320366718` (native) and `10320686183` (WASM) of the recorded run and are excluded from the revised protocol's calibration.

The longer protocol at `437d61c0` passes all 108 workloads in eight clean reports: two local macOS reports, two WASM reports, and two independent Linux pairs from [the workflow and its native retry](https://github.com/cognica-io/uqa-engine/actions/runs/34766803689). Every repeated allocation counter agrees. WASM's maximum timing ratio falls to 1.134 and macOS's is 1.165, but Linux callback-to-return medians still vary by up to 3.564 times while whole-operation timings remain close. Both Linux attempts use the exact same executable bytes. Artifacts `10320413714`, `10320743976`, and `10320763023` retain the two Linux pairs and the WASM pair respectively; these observations do not establish reviewed timing limits.

The collector previously constructed JSON records between workloads. With the workspace's `serde_json/arbitrary_precision` feature, timing-dependent numeric strings introduced variable allocations into the heap used by subsequent operations. The collector now retains typed numeric records and fixed-size sample arrays, reserves the complete record inventory up front, and converts records to JSON only after all workloads finish. This removes reporting allocations that depend on earlier timing values. The sampling protocol and JSON schema remain unchanged; repeated measurements of the revised collector must establish its actual effect before calibration is accepted.

Rust allocation counters cover one interrupted operation on the current thread. Preloaded dictionary/input/reference results, the allowance handle, the unrelated reservation, and host memory are outside that scope. Each new reference count and cancellation position comes from the same fixed complete input; changing the polling schedule makes a timing baseline incomparable until reviewed again.

## Regression policy and evidence

The [reviewed limits](cancellation-limits.json) retain all six raw `9a8a5aee` reports and their SHA-256 identities under `cancellation-evidence/`. Each macOS aarch64, Linux x86_64, and Emscripten WASM target has two clean reports. Every one of the 108 workloads agrees on complete recovery output, polling points, and all six allocation counters. Allocation ceilings equal those observations without padding; additional retained allocations and bytes must remain zero.

After deferring JSON conversion, the maximum bidirectional repeat ratios are 1.036 on macOS, 1.089 on Linux, and 1.143 on WASM. The recorded timing ceiling is 1.26: the exact observed maximum, 1.142723344362666, multiplied by a 1.1 margin and rounded up to two decimal places. Comparisons require the same CPU, platform, compiler, flags, benchmark source, arguments, inputs, polling schedule, and sampling protocol. Both complete-operation and callback-to-return medians are checked independently for every workload. These are measured cancellation scopes, not external-signal detection or scheduler guarantees.

```sh
python3 scripts/run-nori-cancellation-benchmark.py --output target/benchmark-runs/nori-cancellation-native-baseline.json
python3 scripts/run-nori-cancellation-benchmark.py --baseline target/benchmark-runs/nori-cancellation-native-baseline.json --output target/benchmark-runs/nori-cancellation-native-repeat.json
python3 scripts/run-nori-cancellation-benchmark.py --target wasm --output target/benchmark-runs/nori-cancellation-wasm-baseline.json
python3 scripts/run-nori-cancellation-benchmark.py --target wasm --baseline target/benchmark-runs/nori-cancellation-wasm-baseline.json --output target/benchmark-runs/nori-cancellation-wasm-repeat.json
```

The first report enforces allocation, complete recovery, reservation cleanup, inputs, and sample validity. The repeat also enforces all 216 timing comparisons. The required native/WASM workflow checks the existing ordinary analysis gate first, then runs both cancellation gates and uploads their reports. The tagged `uqa-nori-cancellation/**` trigger permits independent verification while other workflows run.
