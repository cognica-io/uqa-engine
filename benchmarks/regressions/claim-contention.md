# Independent-process claim-table contention

Issue #266 retains a measurement requirement for the shared claim-table mutex. The existing deterministic regression checks prove exact cross-process ownership, bounded acquisition arbitration and complete identity reclamation. The execution owner's `row_claim_contention` example adds a fixed repeated workload for collecting separate acquisition and release observations with 1, 2, 4 and 8 independent OS processes and 64 or 512 disjoint keys per process. It calls the same public `shared_provider_manager`, `retain_key_reservation`, `acquire_batch` and `release_session` interfaces used by execution. No lock algorithm is duplicated or moved into Engine, no runtime dependency is added, and no production API or sidecar format changes.

An identity-only provider supplies a fresh temporary file identity to the existing coordinator factory; its storage-session method deliberately returns an error and is never called. This isolates reservation coordination from SQLite's writer scheduling and durable page writes. It is a coordinator workload, not an end-to-end SQL throughput claim. All sidecars live under its temporary directory. A parent coordinator remains attached for the whole case so the workload measures steady attached ownership rather than cold last-owner reconstruction.

All workers finish initialization before any receives an acquisition command. The parent sends to all workers before reading any reply and does the same for release. Each worker reports elapsed time around the actual batch acquisition and session release only: process startup, request construction, pipe I/O and parent verification are excluded from those intervals. The interval still includes mutex waits and the corresponding local/shared coordinator work; it is not a measurement of mutex hold time alone. Separate parent wall intervals run from the first command dispatch through the last completion reply for acquisition and release. They include dispatch, request construction and reply I/O and exclude parent verification. Dividing the completed key count by those wall intervals describes that coordinated workload phase's throughput; summing worker latencies does not. Raw samples and both wall intervals are retained.

Every round checks that each worker received every requested grant, that the parent's independent probes of each worker's first and last key fail with `55P03` while held, and that those same probes succeed after release. Fixed warmup is eight rounds and measurement is 128 rounds per case, with no adaptive retries. Correctness failures abort the command. The existing owning-crate regression tests continue to establish the complete per-key and resource invariants.

Run the output/ownership verification without reading the clock:

```sh
cargo run -p uqa-execution --example row_claim_contention --locked -- --verify
```

The verification mode executes two rounds of every case and emits no timing samples. Automatic performance CI runs this mode on Linux and macOS and retains `claim-contention.json` alongside its existing revision/workload provenance and deterministic results. To collect observations, a controlled runner must build the release-profile executable and run `--measure` once for the prescribed workload, redirecting its compact JSON into an ignored output directory. Measurement rejects a debug-profile executable. Retain the exact revision, toolchain, executable digest, environment/control evidence and independent noise calibration beside the output. The report deliberately keeps `timing_acceptance: false` and `acceptance_status: "unqualified"`; these samples alone do not decide partitioned locking or close #266. Applying a noise bound from a different estimator or from the candidate samples would not qualify this workload. The actual controlled contention comparison and any justified partitioning change remain required.
