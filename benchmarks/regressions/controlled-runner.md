# Controlled EC2 performance checks

Use one reusable, on-demand EC2 instance in Seoul with dedicated tenancy, sixteen physical Graviton3 cores, 32 GiB of memory and encrypted gp3 storage. The operator uses the `appspand` AWS profile and its existing `seoul` SSH key. Instance identifiers, SSH addresses, private keys, controller evidence and generated reports remain outside source control. Stop the instance after each session; retain its encrypted volume and build caches for reuse. A restart invalidates the previous session's calibration because placement and the operating environment may change.

The operator owns the host and the controller. Build both immutable revisions before calibration, then run no compiler, package installer or unrelated workload during calibration or candidate measurement. Reserve CPUs 0–7 for administration, ordinary services and unbound kernel workqueues. Keep the claim workload's complete process tree on CPUs 8–15 with scheduler load balancing; pin each sequential analytical invocation and its fixture helpers to CPU 8. The kernel workqueue mask is checked before and after each invocation, and the unit's effective CPU set is checked while it runs. Disable address randomization only for the unprivileged measurement executable with `setarch --addr-no-randomize`, leaving the host setting unchanged. Verify the actual executable's `ADDR_NO_RANDOMIZE` personality flag while it runs and retain its executable, heap and stack mappings in the signed resource inventory; missing mapping evidence or a reverted personality fails the invocation. Build processes retain their normal layout policy. Retain a compact controller-owned resource record for every invocation: task CPU residency counts, last-observed task CPU and run-queue time, per-CPU counters and CPU/memory/I/O pressure. These diagnostics include fixture construction, warmup and Criterion analysis; they are not SQL latency samples, and a task can exit between samples. Bind their hashes in the signed run attestation. Record effective cgroup CPU sets, boot identity, kernel/toolchain, CPU topology, swap state, process inventory, binary hashes and CPU steal counters. An unexpected process in the measurement partition, overlapping controller lease, reboot, nonzero CPU steal or unsuccessful workload invalidates the session; do not retry it until it passes. The controller's signing key remains inaccessible to the account executing candidate binaries.

The executable cache verifies the complete target inventory, exact revision, toolchain/build environment and executable hashes before selecting cached artifacts. Cache hits do not change source checkouts. Analytical executions separately retain their exact runtime sources and reviewed manifests; claims use only private temporary working directories. A cache miss checks out and builds the requested revision with the ordinary locked, optimized Cargo command. The claim reference may reuse the candidate build checkout on a miss, so the candidate runtime source is reselected before measurement. This preserves Cargo source freshness when only controller or documentation files change, without treating an earlier revision's executable as a new build.

Before executing a candidate, collect exactly 32 independent A/A pairs from the reference executable, alternating the order of the two named roles. Retain every observation, including outliers. For each workload let $a_i$ and $b_i$ be its paired positive estimates and define $E_i = \max(a_i/b_i, b_i/a_i)$. Set $n$ to the third-largest of all 32 errors. Compute the bound from these reference observations only and sign it before the candidate starts. The two largest errors remain in the signed raw observations and count in the rank argument; no observation is deleted or replaced. Non-finite or unrepresentable arithmetic is an error even above the selected rank.

The explicit statistical assumption is exchangeability of the 32 reference-pair absolute multiplicative errors and eight subsequent candidate/reference-pair errors after accounting for the true performance ratio. Host isolation and environmental records support that assumption but do not prove it; workload-dependent noise or drift can violate it. For an arithmetic median of eight ratios to leave $[1/n,n]$, at least four future absolute errors must exceed $n$. Since $n$ is the third-largest reference error, that event requires at least four future observations among the largest six of the combined forty errors. Exchangeable ranks bound its probability by $(\binom{8}{4}\binom{32}{2}+\binom{8}{5}\binom{32}{1}+\binom{8}{6})/\binom{40}{6}=87/9139$. Ties make the bound conservative. Thus marginal prediction coverage is at least $9052/9139\approx0.99048036$, slightly higher than the previous four-pair/max-of-32 bound $104/105\approx0.99047619$. See the [complete median-bound derivation](../../docs/design/performance-qualification.md#median-noise-bound) and independent rank-count tests. This is not simultaneous engine-wide coverage or posterior certainty about a permanent host property. Record the assumption, exact counts and selected rank with the signed evidence; expire it at the end of the controlled boot/session.

Apply the existing qualification verifier to $[r/n,rn]$, where $r$ is the candidate's median paired ratio. Accept only when the entire interval satisfies the unchanged manifest limit, report regression only when its lower endpoint exceeds that limit, and report inconclusive otherwise. Arithmetic overflow, incomplete samples, missing control evidence or a changed sampling protocol must fail explicitly. Generated observations and signatures belong in ignored output directories or CI artifacts; retain only compact provenance and conclusions in reviewed documentation.

## Hardware and fault diagnostics

Issue #653's retained slowdown occurs while the main task consumes CPU, with little run-queue delay and no increase in memory-pressure totals. Those records cannot distinguish more instructions from lower instruction throughput. Earlier instrumented diagnostics contain hardware counters but did not reproduce this large variation; they do not supply the missing counters for the failed session.

The controller resource observer collects grouped `cycles` and `instructions` counters from the reserved measurement CPUs once per second through `perf stat`. The group preserves contemporaneous event coverage; retained raw counts include each event's running time and percentage rather than presenting multiplexed counts as full-time work. Task records also retain minor/major faults, and invocation snapshots retain paging, compaction and transparent-huge-page counters. Bounded observations of complete `Benchmarking` log lines relate these intervals to fixture, warmup, collection and analysis; their timestamps are when the existing 250-ms observer sees a marker, not exact query boundaries. Partial lines and repeated unchanged markers create no new observation. [AWS's hardware-performance runbook](https://github.com/aws/aws-graviton-getting-started/blob/main/perfrunbook/debug_hw_perf.md) describes using instruction and cycle counts to distinguish hardware stalls; the [perf manual](https://man7.org/linux/man-pages/man1/perf-stat.1.html) defines the grouped events and interval/coverage output.

The observer starts no workload and changes no fixture, binary, sample count, ordering, noise rank or regression limit. Its output is bounded to the existing 300-second invocation window plus shutdown allowance, with bounded lines and event inventories. Missing, incomplete or prematurely stopped observation is retained as a resource error; an existing workload error remains primary. These counters cover fixture construction, warmup and analysis as well as measured SQL, so they are diagnostic observations rather than query timings or acceptance criteria. A fresh automatic session recalibrates independently with the observer present for both reference and candidate. Operator deployment and an idle-host smoke check precede the first such session; an active controller is never replaced.
