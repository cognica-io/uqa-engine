# Owned HTTP notification subscriptions

This implements the Rust client lifecycle in the [notification/SSE design](sql-notifications-and-sse.md), building on the [bounded decoder](notification-protocol-decoding.md). Client owns the HTTP attempt, receive queue, cancellation and reconnection. It uses Core's existing events and failure categories without importing Engine or changing `AsyncSQLEngine`. The authenticated Cloud server, its retained authorization, output-write budget and the actual Python/Node/browser runtimes remain required owners in the [fixed ledger](../plans/0015-sql-notifications-and-sse.md).

## Ownership and admission

`HttpEngine::subscribe_notifications` validates the exact requested channel set and all explicit options before sending a request. It reserves a finite event-slot array, checks that array's actual capacity against the byte budget, creates the response-independent cancellation owner, and starts exactly one Tokio task. That task receives continuously even when the application is not calling `next_event`. Initial creation returns only after the task has validated ready and its timing contract. A failed initial attempt returns its error without claiming an earlier registration boundary.

The task alone owns the dedicated reqwest client, immutable original endpoint and credential, encoded request and active response. No event path calls SQL or republishes notifications. The HTTP client retains the existing HTTPS/explicit-loopback origin rules, disables redirects, ambient proxies, automatic transport retries and decompression, requests identity encoding, and retains no idle pooled connection. Its connection timeout comes from the subscription options; the SQL client's fixed connection timeout is not inherited. TCP keepalive is not used to invent an additional subscription lifetime, and the supported Linux-family TCP user timeout override is disabled in favor of the explicit operation budgets.

Success requires exactly status 200, one valid request identity, UTF-8 event-stream content type, no-store/no-transform cache directives and identity content encoding. Pre-stream error JSON is bounded, depth-checked and closed-schema validated. Missing endpoints produce unsupported capability without attempting SQL fallback. Server messages and transport causes remain available explicitly; Display/Debug expose closed categories and bounded metadata. Malformed HTTP syntax or typed invalid-data/input failures are terminal protocol corruption; connection loss remains retryable under the supplied policy. Classification uses typed transport causes, never error-message matching.

## Queue and cleanup

The inbox is a finite ordered queue protected by a short synchronous mutex that never encloses I/O or application callbacks. Its charge is reserved slot capacity plus retained channel/payload string capacities and request-ID bytes. An event is admitted only if both the count and byte inequalities remain true. There is at most one newly decoded event outside this queue. Overflow preserves the admitted prefix and a terminal backpressure error; it does not discard an event and then continue that epoch.

Ordinary failures retain the earlier admitted prefix for the consumer, followed by the same retained error on subsequent receives. Observed cancellation or authority rejection discards unread events. Explicit close also discards unread events and frees the queue even if a different terminal failure was already recorded. Draining the last retained event after a terminal failure frees its slot allocation. Values already returned to the application are outside the subscription's queue budget.

`NotificationCancellation` is a monotonic watch signal with no reset operation. The worker selects it across connection, readiness, streaming and backoff work; receive waiters also observe it. Cancelling a receive future leaves this independent subscription running. Explicit close cancels and awaits the one retained task. Cancelling the close future retains its join handle, so a later close still joins the same task. Dropping a handle or unfinished creation future signals cancellation and aborts that same owned task; a completion guard wakes receivers and completes pending creation on unwind or abort. No detached replacement loop is created.

Tokio abort requests cancellation rather than synchronously joining; [awaiting the retained handle](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html#method.abort) establishes local task completion. These claims assume a running Tokio runtime with I/O and timers enabled and eventual scheduler progress. They do not make an operating-system DNS call or certificate-store initialization universally interruptible, establish a measured cleanup latency, or acknowledge a remote listener-cleanup transaction. The server still owns its bounded detection and cleanup obligations.

## Timing and retry policy

All configured durations are positive whole milliseconds. This native client supports at most $2^{36}-1$ milliseconds per timer, one full period of its current Tokio timer wheel, and also checks monotonic-clock addition. This is an explicit receiving range rather than a deployment default. Connection establishment and the complete attempt through ready have separate budgets, with connection no longer than readiness. Before exposing ready, the decoder checks the advertised $I>3H+M$, supported range and local idle ceiling. After ready the worker uses the accepted server $I$ from the latest received bytes, without a total SQL/request lifetime limit.

`Some(NotificationRetryOptions)` enables managed post-ready reconnection; `None` is an explicit opt-out. Each loss episode retains its first failure, a monotonic deadline and a maximum replacement-attempt count. Before any replacement attempt it queues `ResyncRequired` for the old identity. A replacement validates a different epoch and all ready fields, then queues `Reconnected` before its first notification. Successful ready ends the episode and releases its retained failure. A later loss starts a new episode, not an extension of the old deadline.

For replacement number $j$, define $b_j=\min(B,b_0 2^j)$, where $b_0$ and $B$ are the supplied initial and maximum backoff. Saturating integer arithmetic followed by the cap implements this expression even when the unbounded product would overflow. An operating-system random word selects a delay in $[\lceil b_j/2\rceil,b_j]$; no uniformity or cryptographic claim is required by this bounded-jitter policy. The actual delay is the maximum of that jitter and validated server guidance. Both [Retry-After forms](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after), delta-seconds and HTTP dates, are supported. A date becomes a bounded relative delay once, after which waiting uses the monotonic clock.

Guidance cannot extend the episode deadline. A wait that cannot fit terminates the episode instead of issuing an earlier request or extending the budget. Replacement readiness uses the smaller of its own deadline and the remaining episode deadline. There is no additional gap event for a failed replacement that never became ready. Attempt exhaustion or a terminal replacement failure retains the original loss and last-attempt diagnostics. Authentication, invalid input, protocol corruption, unsupported capability and local overflow do not gain retry authority from a remote Boolean or unknown code.

The server's blocked-output-write budget remains distinct from these client connection/readiness/idle/episode budgets. Establishing a verified server registration margin, forwarding idle budgets, authorization propagation and a complete serving-path policy remains part of actual server integration.

## Preservation proof

Let $D$ be the established decoder and let $H_E$ be the admitted notification history of epoch $E$. From the decoder proof, erasing only transport metadata yields the original ordered notification triples, and no rejected frame advances sequence state. The HTTP worker has no SQL transition; its only data operation is to append one admitted event to the inbox. Let $Q$ be that queue, $A$ the consumer's returned history and $P$ the producer's admitted history. Initially all are empty. Successful append changes only $Q$ by concatenating the next element; successful receive removes its head and appends exactly that element to $A$. Under the inbox mutex these operations have single linearization points, so induction gives $P=A\cdot Q$ while the epoch remains intact. Thus FIFO delivery preserves order and values independently of producer/consumer scheduling.

Reconnection changes the observable carrier to histories of typed notification, gap and reconnection observations. On each replacement boundary the only admissible order is an old-identity gap, a new-identity reconnection, then notifications of the new epoch. The single worker appends in exactly this order, and FIFO receive preserves it. The consumer-visible identity advances only when it removes Reconnected, so it cannot advertise the new epoch ahead of its gap observation. An initial failure emits no fabricated gap. Terminal failure preserves an admitted prefix; explicit close/cancellation and authority invalidation instead invalidate unread observations with a visible close or typed error. Neither case claims continuation across an omitted suffix.

At all times the worker owns at most one response or connection attempt: the attempt function owns the response, returns and drops it before the outer loop waits or starts another attempt, and reqwest's automatic retry policy is disabled. A ready replacement resets the episode only after its control observation is admitted. Therefore attempt limits, deadlines and old-identity diagnostics cannot be bypassed by nesting a library retry, returning headers as ready, dropping a receive future or scheduling another task. Cancellation is monotonic and cannot restore an earlier authority state.

The underlying UQA carriers and operations are unchanged. Metadata erasure within each intact epoch has the same identity, order and concatenation preservation as $D$; a gap explicitly prevents using that equality across epochs. The implementation performs no document-support, payload-collision, score, ranked-result or value-relation transformation and introduces no optimizer rewrite or numeric approximation. Existing SQL calls, transaction effects and their applicable algebraic laws remain those of the unchanged SQL interface.

## Resource and verification scope

For slot capacity $q$, event-slot size $s$, and retained dynamic allocations $d(e)$, admission maintains $q s+\sum_{e\in Q}d(e)\leq B$ and $|Q|\leq N$, with caller-supplied $B,N$. Slot bytes are checked before reservation and again using actual capacity. Popping releases the corresponding dynamic charge; terminal draining or explicit cleanup releases the slot array. The decoder owns one bounded frame and optional bounded data-join buffer, the worker retains at most one size-checked HTTP chunk, and each error body has the protocol bound. Request metadata, encoded/in-flight request copies, a currently decoded event and retained failures are finite additional resources.

This accounts for the client-owned data structures, not a measured total RSS envelope. Hyper/reqwest/TLS buffers, a returned chunk before its size check, allocator overhead, runtime scheduling, all simultaneous handles, Engine/provider state and the real server's queues still belong in the complete deployment resource profile. No numeric capacity default or measured timing margin is inferred from these tests.

Owner tests use actual loopback TCP/HTTP exchanges and the independently specified protocol fixture. They exercise readiness, queue ordering and overflow, abrupt loss, planned draining, identity changes, retry counts/deadlines/guidance, TLS handshake cancellation/timeouts, missing ready, invalid headers, response cleanup, cancellation of creation/receive/close, and actual TRACE/log content. These are Client transport tests, not a substitute for an Engine publisher connected to the authenticated Cloud endpoint or execution through the language artifacts.
