# Recursive scalar evaluation stack ownership

Physical scalar evaluation belongs to Execution. The recursive dispatcher previously held the temporary storage of every scalar variant in each unoptimized stack frame. Routine execution re-enters this dispatcher through projection and function arguments, so even shallow valid PL/pgSQL recursion could exceed the unchanged one-million-byte native routine stack budget.

Column, array, row, binary, unary, null-test, cast and subquery-membership evaluation now live in separate variant handlers. The dispatcher checks the original production control and delegates the selected variant with the same expression, context and control. No routine nesting limit, thread stack setting, error guard, SQL carrier or arithmetic algorithm changes.

For a scalar tree, induction on its structure gives the same result and observation sequence. Leaf evaluation is unchanged. Each moved handler evaluates the same children in the same order, calls the same SQL-owned operations, and retains each `Produced` reservation until the same result or error boundary. Binary operands still evaluate left before right; deferred enum metadata, real-width selection and integer-width inference retain their previous conditions. Row field inference still precedes value evaluation. Cast source inference still precedes operand evaluation. Lazy AND, OR, CASE and COALESCE branches retain their original implementations. Cancellation remains checked at each dispatcher entry, and allocation or SQL errors unwind the same owned values and leases.

The change shortens live stack storage by keeping unselected variants' temporaries out of recursive dispatch frames. It introduces no query rewrite or new algebraic operator and makes no claim about elapsed-time performance. Owning Execution tests construct a 32-level physical scalar tree directly and check both ordinary and controlled evaluation within the native routine budget, its exact result and complete reservation release. Existing tests cover numeric and null semantics, lazy error precedence, cancellation and reservation release. Existing Engine integration tests retain factorial and Fibonacci at depth ten, explicit depth-limit rejection, unbounded recursion rejection and successful calls after guard cleanup.
