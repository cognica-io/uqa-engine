# Native Node.js notification ownership and preservation

The Node.js binding adapts the existing [owned direct listener](owned-notification-listeners.md); the separate [JavaScript HTTP owner](javascript-http-notifications.md) handles remote subscriptions without loading an addon. Engine retains the original hub, role and provider. Node owns value conversion, Promise scheduling, cancellation and environment cleanup. This change adds no Cargo dependency, feature, SQL operator, publication path or deployment default. The [fixed implementation ledger](../plans/0015-sql-notifications-and-sse.md) retains actual Cloud, browser and complete platform/resource qualification.

## Exact observation map

Let $\mathcal{E}$ be Core's disjoint union of notification, resynchronization and reconnection events. Conversion $\Phi:\mathcal{E}\to\mathcal{J}$ produces the existing frozen JavaScript event representation: `kind` selects the variant; epoch and optional request identity remain unchanged; a notification exposes its sequence as `bigint`, process identifier as an exact `number`, and channel and opaque payload as Unicode strings. Fields outside a variant are `null`. Conversion never parses the payload or normalizes text.

For every $q\in[1,2^{64}-1]$, the native intermediate BigInt consists of a nonnegative sign and the single unsigned word $q$. Node-API transfers that integer directly to JavaScript; no floating-point intermediate exists. Every $p\in[-2^{31},2^{31}-1]$ is exactly representable by binary64. Strict UTF-8 conversion preserves Unicode scalar sequences, so re-encoding each string recovers its original bytes. Define $\Psi$ on the image of $\Phi$ by selecting the variant from `kind`, restoring the finite integer domains and re-encoding the strings. Disjoint tags and exact component maps give $\Psi(\Phi(e))=e$ for every $e\in\mathcal{E}$.

The pointwise extension therefore preserves the empty trace, ordered concatenation and all original field observations: $\Phi^*([]) = []$ and $\Phi^*(x\mathbin{+\!\!+}y)=\Phi^*(x)\mathbin{+\!\!+}\Phi^*(y)$. Applying the direct listener's metadata-erasure projection after $\Psi$ yields exactly its selected committed SQL history. The adapter has one active consumer and no prefetch queue; every yielded value corresponds to one receive from that same listener. Core's failed inbox discards unread values and retains its terminal failure. Explicit cleanup preserves that failure, including when close and receive overlap, and cannot relabel a failed suffix as successful exhaustion.

Registration neither executes SQL on the creating query session nor drains its low-level listener. Core establishes all-channel readiness, the original database and role, independent cursors, transaction duplicate suppression and commit/rollback boundaries. The adapter only schedules that operation and converts its resulting observations. Consequently existing relation, document, graph, score and ranked-result operands and operations remain unchanged; no optimizer rewrite or approximation is introduced.

## Registration and close ownership

A native state retains the original Engine, bounded copied channels and an independent cancellation signal before registration enters the existing libuv work pool. Submission is single-use. Registration stores either the original ready listener or its retained failure in that state before reporting completion. Cancellation signals the actual native operation. If native readiness wins the race, the JavaScript owner joins cleanup of the resulting listener before rejecting the cancelled registration. It never leaves a successful but undisclosed handle running.

Before constructing that state or submitting native work, the adapter reserves the original Engine's opaque subscription permit. Pending inputs, queued/running registrations and ready handles share the same hub ceiling. Native registration consumes and transfers that exact permit; failed or abandoned inputs retain it until their original cleanup releases it. The [shared admission proof](owned-notification-listeners.md#capacity-before-runtime-submission) extends the limit to the libuv submission queue without introducing a separate binding-local counter.

The state serializes registration completion and cleanup. Cleanup takes an unstarted input or waits for the same running registration; it then destroys that input or closes the exact retained listener. A separate Node-API asynchronous work item owns this cleanup before registration is submitted. A Node-API asynchronous environment cleanup hook retains the work, state and environment until the work's completion callback removes the hook. Multiple public close calls share one Promise; finalization and environment teardown signal and schedule that same work. Original provider release and native admission release precede completed explicit close.

Normal JavaScript callbacks never run provider cleanup inline. If native work admission itself fails during environment teardown, JavaScript execution is already disabled; the hook completes retained cleanup before releasing its authority. A queueing failure during normal operation instead reports a typed failure and leaves the cleanup hook owning the resources. The ownership argument assumes valid Node-API handles and completion callbacks; it does not claim progress after process abort, arbitrary native API corruption or operating-system I/O that never returns.

An asynchronous receive awaits Engine's standard-library Future on the runtime managed by N-API. It occupies neither an idle libuv worker nor one blocking thread per listener. A single-result Node-API thread-safe function carries completion back to the owning JavaScript environment. Its queue has capacity one and exactly one producer reference. Successful admission transfers the result allocation to the callback; unsuccessful admission releases it locally. A closing status ends that producer's ownership without further calls. During shutdown, a callback with no live environment destroys native data without attempting JavaScript conversion. These are the [Node-API thread-safe function lifetime rules](https://nodejs.org/api/n-api.html#asynchronous-thread-safe-function-calls); the separate [asynchronous cleanup hook](https://nodejs.org/api/n-api.html#napi_add_async_cleanup_hook) forms the provider-release barrier.

Thus a successful registration maps to native readiness, every yielded event maps through $\Psi$ to a native receive, and completed explicit close maps to actual native cleanup. Runtime scheduling adds suspension transitions only. `isClosed` means ended delivery and may precede completed resource release; callers needing the latter must await `close()`, iterator `return()` or loop exit. An outstanding receive retains its JavaScript facade. Garbage collection is a best-effort fallback without a promised collection deadline; environment teardown retains its independent native cleanup authority.

## Bounds, errors and acceptance limits

JavaScript validates channel count before reading elements and UTF-16 length before scanning or copying a name. Native validation independently checks count, strict UTF-16 conversion and the 63-byte UTF-8 limit. Copied short strings do not retain arbitrary caller parent buffers. The existing five explicit native limits continue to govern Engine admission, channels, inbox count/bytes and provider registry scanning. Each adapter state adds one registration input, one listener reference, at most one receive, a single-result delivery slot and one shared cleanup operation. Completed event objects belong to the application.

These per-owner bounds and the shared direct submission limit do not establish a whole-process memory ceiling: runtime pools, Node/V8 objects, provider caches and operating-system handles remain part of required resource qualification. No deployment capacity, timeout default, latency margin or RSS claim follows from the functional fixtures. Shared-core startup/cleanup and supported-platform coverage remain in their fixed owner units.

Failures expose closed, content-free `NotificationError` codes. Original provider diagnostics require explicit `diagnostic` access; ordinary event, owner and error representations omit channels, payloads and credentials. Native failures remain observable after cleanup. AbortSignal and iterator termination cancel the original work; they do not start HTTP, reopen the provider or substitute a new Engine. Actual-addon tests must verify transaction boundaries, independent subscriptions, exact values, runtime starvation, original encrypted providers, cancellation, concurrent close and Worker exit. HTTP package and Cloud evidence remain distinct from this native adapter.
