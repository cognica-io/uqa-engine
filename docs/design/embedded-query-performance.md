# Embedded query profiling and optimization

UQA is measured as a native macOS Rust process calling embedded `Engine::sql`. PostgreSQL 18, pgvector and Apache AGE run in Docker. UQA query timing starts immediately before `Engine::sql` and ends after complete `SQLResult` materialization; driver transport and JSON serialization are excluded. The PostgreSQL client measurement includes execute, fetch and transport. Its separately collected `EXPLAIN ANALYZE` planning-plus-execution measurement excludes parsing and transport. These boundaries must remain separate in comparisons.

## Profiling findings

All twelve workloads whose unprofiled UQA median exceeded 10 ms in the comparison were profiled: `full_scan_aggregate`, `group_by_1000`, `join_group_by_1000`, `top_10_scan_sort`, `GIN_common_term_count`, `graph_batch_match_20`, `graph_1_hop`, `graph_2_hop`, `graph_1_to_3_hops`, `SQL_insert_100`, `SQL_update_100` and `SQL_delete_100`. Vector queries, point lookups, indexed aggregates, the indexed window and selective text counts were below this threshold; their correctness and vector quality remain part of the complete comparison.

The accepted profiles contain 21 traces and 35,657 samples with `Engine::sql` ancestry. The sampler observes stacks and waits at a 1 ms interval. Inclusive percentages overlap and cannot be added; they are neither CPU utilization nor exact elapsed-time fractions. Twenty-six captures with no SQL ancestry were explicitly excluded and retained with their rejection reasons. Each accepted write trace contains one original mutation, with preparation outside the capture window.

| Workload family | Observed cost | Owning implementation and implication |
|---|---|---|
| SQL scan, grouping, join and scan-sort | SQLite stepping is 61.1-66.4%; document decoding is 19.1-22.2% of SQL stack samples. | `uqa-storage-sqlite` owns predecessor and payload cursors; `uqa-storage` owns document decoding. Removing repeated storage traversal has higher diagnostic priority than aggregate arithmetic. |
| Common-term text count | `dense_identity_presence` is 91.8% of SQL stack samples. | `uqa-storage-sqlite` verifies retrieved identities in the captured MVCC view. Presence checks must retain historical visibility and missing-document diagnostics. |
| AGE-compatible graph queries | Start candidate selection is 58.8-67.0%; batch property matching adds 12.1% in its case. | `uqa-graph` selects starting candidates by label or graph membership and then checks properties. Native membership enumeration belongs to `uqa-storage-sqlite`. Label enumeration remains the principal graph bottleneck after the changes described here. |
| INSERT, UPDATE and DELETE | Transaction frame commit is 44.3%, 42.9% and 57.9%, respectively. | Durable record publication belongs to `uqa-storage-sqlite`; cross-process row change publication belongs to `uqa-execution`. File writes, `fcntl` and synchronization waits must not be interpreted as evidence to disable durability. |
| DELETE text bookkeeping | Per-document text removal is 10.7%, even on the integer-only mutation fixture. | `uqa-execution` can group complete text removals across an observer-free prepared publication interval. Column types alone are insufficient evidence to skip index integrity checks. |

## Changes and invariants

The relational path uses projected borrowed document input, projected integer aggregation, pruned columns and stable bounded Top K selection. Window partitions retain buffered spill access and PostgreSQL ROWS and GROUPS frame behavior. Graph matching borrows vertex payloads and shares eligible starting-node scans across batch bindings. HNSW uses a bounded visited bitmap; exact vector search can retain canonical coordinates only under matching owner, committed data revision and monotonic private revision identities. The [ordered native read proof](ordered-native-reads.md), [window partition proof](window-partition-storage.md), [exact vector reuse proof](native-exact-vector-reuse.md) and [prepared text publication proof](mutation-text-publication.md) describe the ownership and equivalence conditions.

Profiling led to a further payload-cursor optimization in the SQLite MVCC owner. For a visible non-compacted head, the validated predecessor has exactly the head sequence. A left join on the unique `(key, sequence)` therefore supplies its exact payload without another correlated predecessor subquery. Heads remain the ordered outer traversal, and the unique joined key cannot multiply rows. A head newer than the snapshot boundary retains the historical predecessor seek; a visible compacted head retains its tombstone behavior. The SQL `CASE` reads the joined payload only in the validated visible branch, so a future or compacted payload is not materialized. Metadata validation still precedes payload admission and checks selected revision, payload type and length. No visibility or integrity validation is omitted.

The existing paired key-size and metadata cursors retain admission, point-over-run precedence, exclusive continuation, emitted-record counting and early-stop behavior. The payload cursor still advances once per point head, including invisible heads and tombstones, and compacted run entries do not advance it. Keys and values remain charged before payload stepping and until their SQLite rows are released, including failure cleanup. The deterministic owner test compares the joined cursor with an independently written predecessor query over 1,024 latest heads and analytically specified tombstones, requiring identical payloads and fewer SQLite VM steps rather than a host timing threshold.

Eligible prepared DELETE operations now retain their original document, vector, value-index and row-change publication, and group empty complete text replacements through the existing bounded text batch. Repeated identities, cascading actions, movement and runtime index-expression observers force the same publication barriers as replacements. Text is published before AFTER triggers, transition consumers, results and transaction completion. This removes repeated provider setup without assuming that integer-only relations have empty text storage and without changing `fsync`, full synchronization or row journal durability.

## Verification and provenance

Owner tests compare selected predecessors and deterministic SQLite VM work, exercise long keys, tiny allowances, retained payloads, historical versions, tombstones, compacted records, orphan versions and typed corruption errors. SQL integration tests cover memory and persistence, AFTER-trigger visibility, savepoint and failure rollback, cascading deletion and reopen. Independent PostgreSQL fixtures remain the oracle for SQL behavior; vector checks also compare exact IDs and recall against an independently computed exhaustive result.

The fixtures contain 100,000 relational rows, 1,000 categories, 10,000 clustered vectors with 128 coordinates, 512 SciFact vectors with 384 coordinates, and a graph with 5,000 vertices and 15,000 edges. Both engines use 512 MiB work memory and single-query execution; UQA retains a 512 MiB storage allowance. Profiling and latency collection run separately, without concurrent builds or tests. The shared host has no independently established acceptance noise bound. Reported timing changes are observations, not a passed performance acceptance gate or a claim of PostgreSQL parity.
