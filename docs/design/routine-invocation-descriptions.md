# Routine invocation descriptions

Related issue: [#1108](https://github.com/cognica-io/uqa-engine/issues/1108). The [implementation and acceptance ledger](../plans/open-performance-corrections.md#scoped-routine-invocation-descriptions) records delivery separately from this contract.

## Ownership and scope

SQL owns the complete function binding, selected catalog function and resolved assignment descriptions. Execution owns their lifetime in the existing prepared-expression state, invocation scheduling and memory admission. Native Engine adapters supply catalog revision, weak routine-registry identity and the invoking role's OID and incarnation. They do not select an overload or implement conversion. The public EngineHook extension defaults to its original bound-call method, so custom adapters retain live behavior unless they explicitly implement scope validation.

A reusable binding has a stored function identity, complete supplied-source and argument mappings, and fixed source, target and parameter names: catalog identities or parsed two-part names. Unqualified names and legacy incomplete bindings keep ordinary resolution. The complete binding is compared before a description is read; a syntax address alone never establishes semantic identity. Execution indexes slots by the owned invocation allocation, which stays distinct for zero-argument calls and stable when the prepared owner moves. The original binding remains the source of the concrete invocation mapping.

The native scope retains a weak reference to the selected routine registry, and the description holds a weak reference to its selected function. A retired function body is not kept alive by optional invocation metadata; a failed weak upgrade uses ordinary selection. A registry replacement or copy-on-write mutation cannot reuse that weak allocation identity; catalog revision and the complete role identity must also agree. The scope does not keep an entire superseded registry alive. Qualified and identity-bound type names avoid dependence on search_path; conversions still read current settings and callbacks. A mismatching scope declines reuse; the description retains its original selecting scope rather than accumulating catalog generations.

## Evaluation order

The first invocation follows the existing order: resolve supplied source types, select the bound routine with SQL's original signature/kind checks, then convert arguments and evaluate defaults in their established order. A successful selection may retain its identity and source descriptions. Each target description is selected lazily at that target's original conversion boundary. Failed lookup or conversion does not publish a target description.

Every later invocation evaluates its SQL operands before consulting the retained state. Each argument source and target read rechecks the native scope after preceding conversions, since domain/input callbacks can execute SQL. A conversion publishes its newly selected description only if that scope still agrees afterward. No cache lock is held across user code. Changing values, domain membership, defaults, variadic construction, strictness, EXECUTE privilege checks, security/settings guards and routine bodies remain live. A stale description falls back at the same point, without reevaluating an operand or replaying a callback.

The correction retains metadata, not results. SQL-language body and return conversion paths continue to own their existing declared-result checks; retaining an invocation description alone does not establish that all routine execution metadata or row-time name resolution has been eliminated.

## Preservation argument

Let $B$ be the complete immutable binding, $C$ the selecting catalog/registry/role scope, $V$ the current input values, and $H$ the ordered live callbacks and session state. Write ordinary invocation as $I(B,C,V,H)=E(R(B,C),V,H)$, where $R$ resolves supplied types and selects the function and argument mapping, and $E$ performs the original conversions, defaults, authorization and body execution. Under the adapter's identity contract and fixed names, $R(B,C)$ is invariant. Therefore replacing repeated $R(B,C)$ by its retained value leaves $I$ unchanged while $B$ and $C$ agree.

For each argument position $i$, let $D_i(C)$ be its target assignment description and $A_i(D_i,V_i,H_i)$ the existing assignment kernel. Metadata is first selected at the original position, and the current scope is checked after all earlier effects. If it agrees, $D_i(C)$ is identical to the original lookup and $A_i$ receives the same value, source description and live callbacks. If it differs, the ordinary lookup runs at that position. Induction over the ordered argument/default positions preserves values, errors and effects, including a callback that invalidates a later position. Publication after successful conversion cannot change an earlier observation, and post-callback scope validation prevents stale metadata from entering the retained state.

The final authorization and execution steps use the original selected function and current authority. Metadata reuse neither treats strict NULL input as permission to skip EXECUTE checks nor makes a function replacement or rollback invisible. The SQL bag carrier, multiplicity, NULL behavior, result types and UnifiedPlan structure are unchanged; no new algebraic operator or rewrite rule is introduced.

## Resource and work contract

There is at most one optional description per prepared logical call, independent of input row count. SQL reuses the scalar lowerer's admitted complete-binding copy. The header, source vector, lazy target slots and copied type payloads retain their original production reservations; no independent cache budget is introduced. Insufficient optional allowance declines retention, while cancellation and malformed metadata remain errors. Dropping the prepared owner releases its leases, and cloning prepared expressions creates independent empty state.

Reuse eliminates repeated registry traversal and type-name resolution for the eligible invocation, while complete-binding comparisons and constant-size native scope checks still occur. It does not cache converted values or remove per-value domain checks. Deterministic work counters and exact output/resource assertions qualify this claim separately from controlled elapsed-time measurements and the original historical benchmark obligations.


## SQL body and result descriptions

Bound scalar SQL calls may extend their existing invocation description into the function body. SQL owns concrete parameter descriptions and the final result-layout decision; Execution passes the same native validity guard through routine entry, body preparation and output conversion. Public routine context and body-entry APIs retain their existing signatures. PL/pgSQL declaration metadata follows the separate compilation-bound contract below. Bound table invocations use the same body interfaces under the table-call contract below; unbound calls retain live resolution.

A body parameter slot must have the exact selected invocation position among all declared parameters and type spelling, including when OUT parameters precede inputs. Its first successful resolution still follows invocation/default coercion. Only fixed result declarations can be retained; a search-path-sensitive unqualified result type keeps live name resolution. Eligibility is checked when the first successful layout is published, so later identical checks do not revisit the parsed-name cache or allocate descriptions. A retained result decision additionally compares the complete analyzed output type vector and the first column's anonymous-record field vector, precisely the inputs consumed by the existing result checker. Caller-specific anonymous-record validation runs at its original boundary. A different schema, expired native scope or failed check uses the original path; failed checks never overwrite successful metadata.

Let $S$ denote the selected function and complete bound invocation, $C$ its immutable native type/registry/role scope, and $A$ the final statement's analyzed type and record descriptors. The original ordered checker computes $L(S,C,A)$. Retention substitutes a previously successful $L$ only when $S$, $C$ and $A$ remain identical. The first check is executed in the same position, and the separate caller-target check remains live. Thus the result kind, source-record metadata, target types and first diagnostic are unchanged. The checker evaluates no runtime row expression, so this substitution preserves SQL bag multiplicity, ranking, effects and UnifiedPlan structure.

For each output value $v_i$, conversion still invokes the original kernel $K(v_i,T_i,C_i)$ with its original source type and live settings/domain/input callbacks. The scope is checked again after body execution and before every conversion. A body DDL or earlier output callback that changes the catalog therefore prevents reuse for the next value. Conversion descriptors are published only after successful conversion and a second scope check. No value, failure or domain-check result is cached. The first successful publication and later identical checks borrow the same owned layout. Output conversion recognizes that exact retained layout by identity, avoiding a complete layout comparison for each tuple attribute; an unretained layout uses ordinary conversion. Thus metadata selection for an $n$-attribute tuple remains $O(n)$ rather than adding $O(n^2)$ descriptor comparisons. Whole-composite values continue to use the declared whole-row target; tuple results use each declared attribute target. Existing lazy retained-tuple reads and the approved out-of-bounds XX001 contract are preserved.

Retention owns at most one description per original parameter slot and one successful output-layout/input pair per bound call. Names, type payloads, vectors and conversion slots are admitted before copying. An optional allowance failure leaves the ordinary path available; cancellation remains an error. All leases expire with the existing invocation owner, and no function body or catalog generation is newly retained. A changed result signature does not accumulate another cache entry.


## Procedural datum and conversion descriptions

SQL's prepared-variable resolver can return a concrete typed parameter directly. Its default method preserves the existing textual-resolution interface for external implementations; Execution's activation resolver shares name, positional and record-field selection between the original expression adapter and the typed parameter adapter. Concrete types already selected for a current record field do not pass through catalog-name formatting and reparsing. Scalar declaration resolution remains live for adapters without a native validity guard. Both adapters read the current datum value, NULL, record schema and exception diagnostics; the original parameter numbering, collation binding, missing-field and unassigned-record errors remain unchanged.

A bound scalar native call may admit one procedural metadata table tied to the existing parsed body's compilation identity and datum count. Each position retains at most one exact fixed declaration name, one successful type and one successful conversion description; the scalar result has its own conversion slot. A different compilation, declaration name, position or expired call scope uses ordinary resolution. Namespace-sensitive names and unresolved results are never retained; SQL built-in aliases that parse to a fixed catalog name remain eligible. Merely entering a body resolves no local declarations. Declaration defaults, assignment, CONSTANT and NOT NULL checks, source-type reads, record-return checks and return conversion keep their original order. Records continue to select their current field schema instead of sharing scalar declaration slots.

Let $P$ be the compiled body identity, $i$ a scalar datum position, $n$ its fixed declared type name and $C$ the selecting native scope. The original type resolver is $T(C,n)$; its result is invariant while the fixed name and scope agree. Reuse additionally requires the same $P$, datum count, $i$ and $n$. Thus substituting a successful saved $T$ preserves the declared type. With no matching descriptor, the original lookup occurs at the original read site, including an unresolved result. A record field instead provides the concrete type selected by its current row schema; transporting that type directly preserves its width, modifiers and identity without introducing another resolution decision. Current values are read on each access and are never part of retained metadata.

For each declaration, assignment or return conversion, the existing kernel receives the same target, current value, selected source type and live callback environment. The native scope is checked after all preceding effects, and conversion metadata is published only after successful conversion and another scope check. Induction over execution's ordered datum operations therefore preserves values, SQL bag multiplicities, NULL behavior, domain membership, callbacks, first errors and transaction effects. A changed catalog, role or routine registry causes the same live fallback before the next operation; a domain callback cannot publish a descriptor from its expired scope. Record-schema changes continue through the original prepared-parameter type checks and lazy retained-tuple reads, including the approved in-bounds/out-of-bounds contract. No new algebraic operator, query rewrite or plan representation is introduced.

The table, inline slots, copied names and retained type/conversion payloads use the existing invocation owner's production allowance. The table contains one slot per compiled datum, independent of loop count, input rows or catalog generations. Empty slots may be admitted before first resolution but contain no cached lookup failure, value or callback result. Optional allocation failure preserves live processing, partial reservations release on failure, and cancellation propagates. Each successful fixed scalar lookup or conversion resolves once per valid retained slot; dynamic record metadata and all value checks remain live. The [procedural acceptance record](../plans/open-performance-corrections.md#procedural-datum-descriptions) separates this deterministic work claim from elapsed-time qualification and original historical comparisons.

Unassigned-record reads and writes share the SQL-owned PostgreSQL diagnostic. Prepared variables retain DETAIL and HINT when an invalid value is deferred, while an unexecuted expression still does not raise it. The serialized carrier accepts its earlier primary-only form and omits absent optional fields. SQLParam boxes this uncommon error so its diagnostic payload does not enlarge the ordinary typed-value carrier.


## Bound table calls and set projections

Execution owns one optional description per fixed set-projection call or direct lateral function source. SQL owns the selected result declaration and the existing body/conversion descriptions. A set projection resolves and materializes a native invocation once before choosing its scalar or set result path; it does not execute a classification invocation followed by another materialization. Custom routine adapters retain the original trait methods through default implementations. Current arguments, defaults, output rows, domain checks, EXECUTE checks and body effects remain live.

A successful fixed table declaration may be borrowed only while the complete bound call and native scope remain valid. The initial declaration check runs in its original position, and publication rechecks the scope after the catalog callback. Caller-specified anonymous record layouts continue to resolve and validate at their original boundary, including search-path-sensitive declarations. Named composite layouts use their current catalog scope. Failed lookup, missing/changed scope and insufficient optional allowance use the original path; cancellation is never converted to an ordinary fallback. Retention reserves the layout allocation and its owned payloads before copying, and releases them with the call owner.

A direct lateral source retains its expression hook only when that hook explicitly supplies a currently valid native description scope. Custom/default hooks and invalidated native hooks are reconstructed at the original boundary. The fixed source retains argument expressions and its input schema, but each invocation supplies the current outer row. Repeated source resolution can use a successfully retained bound routine only with the identical input schema and live scope. Explicit column-definition checks remain live. Reusing a declaration does not authorize a row or bypass EXECUTE initialization for a surviving scan, including runtime-empty inputs and LIMIT 0. Statically removed scans follow the separate Planner-owned contract below. ROWS FROM and nested source assembly keep their existing group lifetime and receive the common table invocation behavior; this unit does not claim that all correlated group construction is eliminated.

For selected binding $B$, immutable native scope $C$ and declaration $D$, the existing table checker computes $L(B,C,D)$. Fixed declarations and the adapter validity contract make $L$ invariant while these inputs agree. A retained successful $L$ therefore supplies the same column types and result kind at the same call boundary. The original caller-descriptor checks and body/value operations then run in their original order. Induction over outer rows preserves the SQL bag, each set's multiplicity, zip-longest padding, NULL extension, ordinality, errors and effects. No produced row is memoized, no new algebraic operator is introduced, and UnifiedPlan remains the only plan representation.


## Statically removed function inputs

Planner proves when an already-analyzed source has no executable scan from folded false/NULL qualifications and join structure in the existing UnifiedPlan. Execution then constructs an empty source with the same analyzed row descriptor, after original relation/column authorization, instead of initializing removed functions or evaluating their arguments. This is a physical input decision, not a permission-check exception or another plan representation. LIMIT 0, runtime-empty data, implicit aggregate groups, surviving output expressions and CTE scheduling retain their initialization contracts. A flattened UNION ALL of eliminated relation-backed inputs may disappear only when its analyzed column types agree without coercion and its arms have no surviving grouping, ordering, duplicate elimination or slice boundary. Source-free UNION ALL, coercing appends and other set operators retain initialization even when their final bag is empty. Surviving result projections and argument/default/body processing remain separate from the removed scan.

For SQL bags, an inner product with an eliminated empty input is empty. A LEFT JOIN with a false match predicate instead produces each left row once, padded with NULLs for the right descriptor; RIGHT JOIN is symmetric, and FULL JOIN retains both unmatched inputs. Planner's proof respects those preservation boundaries and declines removal when surviving projection expressions or LIMIT/OFFSET evaluation require initialization. Thus the physical substitution preserves multiplicity, row types and NULL extension. Name/type analysis and relation authorization still consume the original plan, while function permissions follow the executable scans as independently observed in PostgreSQL 18. The #1283 comparison includes folded false/NULL, LIMIT 0, implicit aggregates, LATERAL/ROWS FROM, removed argument-function initialization, retained relation privileges and distinct set-operation boundaries. Initialization visits surviving FROM arguments in their original left-to-right order before the block expressions; it does not rediscover arguments of removed physical inputs through the complete source-expression traversal.

Description APIs accept the original caller's ProductionControl. Controlled callers admit header and payload leases against that allowance; ordinary scalar/table execution retains its existing uncontrolled producer contract. The bounded-retention tests exercise the explicit controlled interface and do not claim a process RSS or universal ordinary-query memory limit.


## Correlated function sources

Execution owns immutable call inputs and the successful preparation of a single correlated ROWS FROM source. A deferred call shares its name, selected binding, prepared expression state, aliases, declared columns and routine descriptions through one owned reference. Each deferred stream owns the current outer row separately. The stream calls the runtime only at its first pull and does not retain returned rows in the shared description. The ordinary one-shot source uses the same initialization and deferred-call code.

A group retains at most one successful description under the hook's explicit native scope and complete input row schema. The group's source syntax, statement parameters and CTE arena belong to its original immutable query owner. Every member must have a selected binding and a statically described result; explicit anonymous-record column definitions remain on the live preparation path. The scope is checked again before publication. A changed scope or schema, an unbound member, a runtime-defined output schema or an adapter without a validity identity uses ordinary ordered initialization. A failed member or group alias validation publishes no partial description. The retained declaration contains no strong reference to a routine body or current outer row.

Let $P$ be the immutable group syntax, $C$ its native catalog/registry/role scope, $S$ the complete input descriptor and $p$ the fixed statement parameters. Initialization computes each successful member descriptor $D_j(P,C,S,p)$ in source order. With these inputs unchanged, resolving the same selected identity, validating its declared columns and checking its privileges yields the same descriptor and successful checks. Reusing $D_j$ therefore changes no value or diagnostic. The first unsuccessful initialization is never cached. A changed or absent $C$ or changed $S$ declines reuse, and the original checks run again. Separate scan-initialization authorization remains at the join construction boundary even if there is no outer row.

For each current outer row $r_i$, the observable member stream remains $F_j(r_i,p)$, with arguments, defaults, domain checks and body effects evaluated at the original first-fetch boundary. Group preparation completes for every member before any deferred member is fetched. The existing RowsFromOperator computes $Z_i=\operatorname{ZipPad}(F_1(r_i,p),\ldots,F_m(r_i,p))$ with the same NULL padding, member order, row multiplicities, per-call ordinality, cancellation and close behavior. Reusing its already assembled physical schema changes only metadata; fresh child operators and counters are created for each $i$. Thus the ordered rows and effects of each $Z_i$, their relational composition and their output types are preserved. There is no new algebraic operator or UnifiedPlan representation.

For $n$ outer rows and immutable argument syntax of retained size $A$, call ownership changes the extra syntax-copy volume from $O(nA)$ to $O(A)$ plus fixed per-stream handles. Evaluated argument values retain their original ownership and conversion costs; this does not claim to remove their copies. Member descriptors and joined row layout are retained once; per-row stream and output qualification remain ordinary operators. Retention belongs to the prepared query and is bounded by its fixed members and argument syntax, not by the outer row count. Ordinary query preparation keeps its existing allocation contract; explicitly controlled routine conversion descriptions keep their existing admission/fallback behavior. These properties establish no universal RSS ceiling or measured latency claim.

Native name-only scalar/table entry points remain value-dependent overload selection interfaces: they receive current values without a complete analyzed invocation identity. The prepared bound source path supplies the selected identity to those same invocation kernels. Extending reuse to an actual repeated name-only caller requires its own complete typing, namespace and validity proof; this correction does not substitute a name-based cache for that contract.

## Selected scalar results

SQL analysis retains an arithmetic expression's selected result type in the existing scalar result-metadata carrier, including expressions whose row or parameter scope will disappear during simplification. This uses the existing `UnifiedPlan` and scalar representation. Concatenation retains its selected operator identity and polymorphic input declarations through the same SQL-owned binding constructor used by controlled introspection; strict text concatenation and non-strict array concatenation therefore remain distinct before Planner runs. Engine supplies no new operator or inference algorithm.

If analysis selects $o : (T_1,T_2) \to T$ and a strict operand is a constant NULL, the replacement is $\operatorname{NULL}_T$, independent of the discarded operand's runtime value. Planner simplifies children before this replacement, preserving PostgreSQL's constant-error order, then uses the retained $T$ instead of resolving an operator after losing its input schema. Unanalyzed optimizer callers without that result and with unresolved row or parameter inputs retain the expression. Runtime NULL values and generic parameters do not establish the constant-NULL premise; their operands remain executable. Non-strict concatenation and set-returning calls are not covered by this scalar elimination law.

The retained metadata is fixed by analyzed syntax and belongs to that plan, so it does not cache current argument values, change row multiplicity, retain returned rows or alter transaction publication. Arithmetic descriptions grow with expression count, not execution count or input cardinality. The existing produced-value leases own the concatenation binding and its argument declarations under controlled introspection; ordinary preparation keeps its existing producer contract. Exact values, result OIDs, effects, child errors, generic/custom parameters and provider reopen are checked against the independent PostgreSQL corpus; allocation and bounded-work acceptance remain separate requirements.

## Grouping identity before scalar simplification

SQL analysis records the retained grouping-set positions from the original typed expressions after applying input coercions and selected call bindings. The descriptor belongs to the existing query plan alongside transient source and output schemas; serialization omits it. Planner consumes the selection before rewriting scalar expressions. Execution continues to use SQL's grouping owner for deferred binding. Stored views retain their original `GROUP BY DISTINCT` syntax and duplicate written sets, and restored definitions obtain fresh selections in their current catalog scope. Ordinary queries without `GROUP BY DISTINCT` allocate no grouping selection or scope copy and skip its traversal.

Let $G$ be the ordered list of grouping sets, let $D$ retain one representative per analyzed expression-set identity, and let $F$ perform a semantics-preserving scalar rewrite. The executable list is $F(D(G))$. Applying $D(F(G))$ instead is invalid because $F$ need not be injective: different strict expressions such as $n+\mathrm{NULL}$ and $n\times\mathrm{NULL}$ both become the same typed NULL. Their grouping sets still contribute independent rows to the SQL bag. Retaining the pre-rewrite positions preserves the sum of those per-set result bags, including empty-input behavior; only sets already equivalent during analysis are removed. No value or effect is evaluated to establish the selection, and scalar rewriting keeps its existing child-error order.

The independent PostgreSQL 18.4 corpus at `crates/uqa-sql/src/binding/preparation/tests/pg18_grouping_identity.json` covers 45 commands, including generic and custom plans, CTE and LATERAL scopes, view definitions, SQL routines, transaction rollback and persistent reopening. Input SHA-256: `d412a6a21a26b3964f13999e3019b8414aa7e7e32c9cafd2feb7128c81d80647`. PostgreSQL's [parse-time grouping-set expansion](https://github.com/postgres/postgres/blob/REL_18_4/src/backend/parser/parse_agg.c) provides the independent ownership/order reference.

The same scope boundary applies when a correlated aggregate finishes: its enclosing row remains fixed for that invocation even when the local input is empty. Execution carries the shared enclosing physical fragment and its original slot range separately from finalized group keys, preserving it across hash aggregation, spill and sort fallback. Appended local set-projection slots cannot acquire enclosing-column status. Selected and absent group keys are resolved first; only remaining enclosing references read that fragment, so an absent grouping key stays NULL while an independent outer value remains available. SQL resolves local bare grouping columns to their bound relation identities so equal spellings in different query levels cannot become the same group input. No argument, user function or cast is evaluated by this transfer.
