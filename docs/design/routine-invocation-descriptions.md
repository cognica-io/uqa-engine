# Routine invocation descriptions

Related issue: [#1108](https://github.com/cognica-io/uqa-engine/issues/1108). The [implementation and acceptance ledger](../plans/open-performance-corrections.md#scoped-routine-invocation-descriptions) records delivery separately from this contract.

## Ownership and scope

SQL owns the complete function binding, selected catalog function and resolved assignment descriptions. Execution owns their lifetime in the existing prepared-expression state, invocation scheduling and memory admission. Native Engine adapters supply catalog revision, weak routine-registry identity and the invoking role's OID and incarnation. They do not select an overload or implement conversion. The public EngineHook extension defaults to its original bound-call method, so custom adapters retain live behavior unless they explicitly implement scope validation.

A reusable binding has a stored function identity, complete supplied-source and argument mappings, and fixed source, target and parameter names: catalog identities or parsed two-part names. Unqualified names and legacy incomplete bindings keep ordinary resolution. The complete binding is compared before a description is read; a syntax address alone never establishes semantic identity. Execution indexes slots by the owned invocation allocation, which stays distinct for zero-argument calls and stable when the prepared owner moves. The original binding remains the source of the concrete invocation mapping.

The native scope retains a weak reference to the selected routine registry, and the description holds a weak reference to its selected function. A retired function body is not kept alive by optional invocation metadata; a failed weak upgrade uses ordinary selection. A registry replacement or copy-on-write mutation cannot reuse that weak allocation identity; catalog revision and the complete role identity must also agree. The scope does not keep an entire superseded registry alive. Qualified and identity-bound type names avoid dependence on search_path; conversions still read current settings and callbacks. A mismatching scope declines reuse; the description retains its original selecting scope rather than accumulating catalog generations.

## Evaluation order

The first invocation follows the existing order: resolve supplied source types, select the bound routine with SQL's original signature/kind checks, then convert arguments and evaluate defaults in their established order. A successful selection may retain its identity and source descriptions. Each target description is selected lazily at that target's original conversion boundary. Failed lookup or conversion does not publish a target description.

Every later invocation evaluates its SQL operands before consulting the retained state. Each argument source and target read rechecks the native scope after preceding conversions, since domain/input callbacks can execute SQL. A conversion publishes its newly selected description only if that scope still agrees afterward. No cache lock is held across user code. Changing values, domain membership, defaults, variadic construction, strictness, EXECUTE privilege checks, security/settings guards and routine bodies remain live. A stale description falls back at the same point, without reevaluating an operand or replaying a callback.

The correction retains metadata, not results. SQL-language body and return conversion paths continue to own their existing declared-result checks; retaining an invocation description alone does not establish that all routine execution metadata or row-time name resolution has been eliminated.

## Preservation argument

Let $B$ be the complete immutable binding, $C$ the selecting catalog/registry/role scope, $V$ the current input values, and $H$ the ordered live callbacks and session state. Write ordinary invocation as $I(B,C,V,H)=E(R(B,C),V,H)$, where $R$ resolves supplied types and selects the function and argument mapping, and $E$ performs the original conversions, defaults, authorization and body execution. Under the adapter's identity contract and fixed names, $R(B,C)$ is invariant. Therefore replacing repeated $R(B,C)$ by its retained value leaves $I$ unchanged while $B$ and $C$ agree.

For each argument position $i$, let $D_i(C)$ be its target assignment description and $A_i(D_i,V_i,H_i)$ the existing assignment kernel. Metadata is first selected at the original position, and the current scope is checked after all earlier effects. If it agrees, $D_i(C)$ is identical to the original lookup and $A_i$ receives the same value, source description and live callbacks. If it differs, the ordinary lookup runs at that position. Induction over the ordered argument/default positions preserves values, errors and effects, including a callback that invalidates a later position. Publication after successful conversion cannot change an earlier observation, and post-callback scope validation prevents stale metadata from entering the retained state.

The final authorization and execution steps use the original selected function and current authority. Metadata reuse neither treats strict NULL input as permission to skip EXECUTE checks nor makes a function replacement or rollback invisible. The SQL bag carrier, multiplicity, NULL behavior, result types and UnifiedPlan structure are unchanged; no new algebraic operator or rewrite rule is introduced.

## Resource and work contract

There is at most one optional description per prepared logical call, independent of input row count. SQL reuses the scalar lowerer's admitted complete-binding copy. The header, source vector, lazy target slots and copied type payloads retain their original production reservations; no independent cache budget is introduced. Insufficient optional allowance declines retention, while cancellation and malformed metadata remain errors. Dropping the prepared owner releases its leases, and cloning prepared expressions creates independent empty state.

Reuse eliminates repeated registry traversal and type-name resolution for the eligible invocation, while complete-binding comparisons and constant-size native scope checks still occur. It does not cache converted values or remove per-value domain checks. Deterministic work counters and exact output/resource assertions qualify this claim separately from controlled elapsed-time measurements and the original historical benchmark obligations.


## SQL body and result descriptions

Bound scalar SQL calls may extend their existing invocation description into the function body. SQL owns concrete parameter descriptions and the final result-layout decision; Execution passes the same native validity guard through routine entry, body preparation and output conversion. Public routine context and body-entry APIs retain their existing signatures. PL/pgSQL declaration metadata follows the separate compilation-bound contract below. Unbound/table-function activation descriptions remain outside these bound scalar call paths.

A body parameter slot must have the exact selected invocation position among all declared parameters and type spelling, including when OUT parameters precede inputs. Its first successful resolution still follows invocation/default coercion. Only fixed result declarations can be retained; a search-path-sensitive unqualified result type keeps live name resolution. Eligibility is checked when the first successful layout is published, so later identical checks do not revisit the parsed-name cache or allocate descriptions. A retained result decision additionally compares the complete analyzed output type vector and the first column's anonymous-record field vector, precisely the inputs consumed by the existing result checker. Caller-specific anonymous-record validation runs at its original boundary. A different schema, expired native scope or failed check uses the original path; failed checks never overwrite successful metadata.

Let $S$ denote the selected function and complete bound invocation, $C$ its immutable native type/registry/role scope, and $A$ the final statement's analyzed type and record descriptors. The original ordered checker computes $L(S,C,A)$. Retention substitutes a previously successful $L$ only when $S$, $C$ and $A$ remain identical. The first check is executed in the same position, and the separate caller-target check remains live. Thus the result kind, source-record metadata, target types and first diagnostic are unchanged. The checker evaluates no runtime row expression, so this substitution preserves SQL bag multiplicity, ranking, effects and UnifiedPlan structure.

For each output value $v_i$, conversion still invokes the original kernel $K(v_i,T_i,C_i)$ with its original source type and live settings/domain/input callbacks. The scope is checked again after body execution and before every conversion. A body DDL or earlier output callback that changes the catalog therefore prevents reuse for the next value. Conversion descriptors are published only after successful conversion and a second scope check. No value, failure or domain-check result is cached. The first successful publication and later identical checks borrow the same owned layout. Output conversion recognizes that exact retained layout by identity, avoiding a complete layout comparison for each tuple attribute; an unretained layout uses ordinary conversion. Thus metadata selection for an $n$-attribute tuple remains $O(n)$ rather than adding $O(n^2)$ descriptor comparisons. Whole-composite values continue to use the declared whole-row target; tuple results use each declared attribute target. Existing lazy retained-tuple reads and the approved out-of-bounds XX001 contract are preserved.

Retention owns at most one description per original parameter slot and one successful output-layout/input pair per bound call. Names, type payloads, vectors and conversion slots are admitted before copying. An optional allowance failure leaves the ordinary path available; cancellation remains an error. All leases expire with the existing invocation owner, and no function body or catalog generation is newly retained. A changed result signature does not accumulate another cache entry.


## Procedural datum and conversion descriptions

SQL's prepared-variable resolver can return a concrete typed parameter directly. Its default method preserves the existing textual-resolution interface for external implementations; Execution's activation resolver shares name, positional and record-field selection between the original expression adapter and the typed parameter adapter. Concrete types already selected for a current record field do not pass through catalog-name formatting and reparsing. Scalar declaration resolution remains live for adapters without a native validity guard. Both adapters read the current datum value, NULL, record schema and exception diagnostics; the original parameter numbering, collation binding, missing-field and unassigned-record errors remain unchanged.

A bound scalar native call may admit one procedural metadata table tied to the existing parsed body's compilation identity and datum count. Each position retains at most one exact fixed declaration name, one successful type and one successful conversion description; the scalar result has its own conversion slot. A different compilation, declaration name, position or expired call scope uses ordinary resolution. Namespace-sensitive names and unresolved results are never retained; SQL built-in aliases that parse to a fixed catalog name remain eligible. Merely entering a body resolves no local declarations. Declaration defaults, assignment, CONSTANT and NOT NULL checks, source-type reads, record-return checks and return conversion keep their original order. Records continue to select their current field schema instead of sharing scalar declaration slots.

Let $P$ be the compiled body identity, $i$ a scalar datum position, $n$ its fixed declared type name and $C$ the selecting native scope. The original type resolver is $T(C,n)$; its result is invariant while the fixed name and scope agree. Reuse additionally requires the same $P$, datum count, $i$ and $n$. Thus substituting a successful saved $T$ preserves the declared type. With no matching descriptor, the original lookup occurs at the original read site, including an unresolved result. A record field instead provides the concrete type selected by its current row schema; transporting that type directly preserves its width, modifiers and identity without introducing another resolution decision. Current values are read on each access and are never part of retained metadata.

For each declaration, assignment or return conversion, the existing kernel receives the same target, current value, selected source type and live callback environment. The native scope is checked after all preceding effects, and conversion metadata is published only after successful conversion and another scope check. Induction over execution's ordered datum operations therefore preserves values, SQL bag multiplicities, NULL behavior, domain membership, callbacks, first errors and transaction effects. A changed catalog, role or routine registry causes the same live fallback before the next operation; a domain callback cannot publish a descriptor from its expired scope. Record-schema changes continue through the original prepared-parameter type checks and lazy retained-tuple reads, including the approved in-bounds/out-of-bounds contract. No new algebraic operator, query rewrite or plan representation is introduced.

The table, inline slots, copied names and retained type/conversion payloads use the existing invocation owner's production allowance. The table contains one slot per compiled datum, independent of loop count, input rows or catalog generations. Empty slots may be admitted before first resolution but contain no cached lookup failure, value or callback result. Optional allocation failure preserves live processing, partial reservations release on failure, and cancellation propagates. Each successful fixed scalar lookup or conversion resolves once per valid retained slot; dynamic record metadata and all value checks remain live. The [procedural acceptance record](../plans/open-performance-corrections.md#procedural-datum-descriptions) separates this deterministic work claim from elapsed-time qualification and original historical comparisons.

Unassigned-record reads and writes share the SQL-owned PostgreSQL diagnostic. Prepared variables retain DETAIL and HINT when an invalid value is deferred, while an unexecuted expression still does not raise it. The serialized carrier accepts its earlier primary-only form and omits absent optional fields. SQLParam boxes this uncommon error so its diagnostic payload does not enlarge the ordinary typed-value carrier.
