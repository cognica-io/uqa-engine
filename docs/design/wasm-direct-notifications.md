# Direct browser notification ownership

The browser `Engine.subscribeNotifications` adapter binds the existing retained Engine listener to its original Emscripten instance. The public async iterator, input snapshot, typed errors, abort precedence and close owner come from the same portable JavaScript module as the native Node binding. The browser ABI, wake bridge and retained listener registry belong to `uqa-wasm`; publication, SQL authorization, admission and bounded queues retain their existing owners. No dependency, Cargo feature, query operator or HTTP endpoint is added. The [complete notification contract](sql-notifications-and-sse.md) and [implementation ledger](../plans/0015-sql-notifications-and-sse.md) remain authoritative for qualification beyond this adapter.

## Runtime and source identity

Registration uses the existing synchronous `uqa_call` bridge and returns only after the original Engine has registered every selected channel. The resulting registry entry owns an `Arc<NotificationSubscription>`, independently of the query-handle registry. Its opaque positive identifier is never reused. The JavaScript handle captures the original module and registration identifier; later query close or wrapper-field changes cannot redirect it to a different Engine. Memory-only registration uses the existing hub and never requests an unsupported persistent session. Browser persistent providers retain their actual MEMFS/IDBFS identity; matching paths in separate runtimes do not create cross-runtime notification delivery.

An idle receive owns one boxed native `next_event` Future. Polling it either yields one value, returns a typed terminal failure, or installs the existing inbox wake slot. Its waker queues a JavaScript microtask on the original module and never re-enters Rust under native locks. That microtask resolves a weak, module-scoped handle reference and polls only an existing pending receive. There is no condition-variable wait, polling interval, extra Worker, per-listener thread or duplicate event queue. Application-created Workers use the same adapter within their own module. Registration and cleanup retain the binding's synchronous WASM call boundary over its virtual filesystem; this implementation does not establish a latency bound for those calls. IndexedDB synchronization remains explicit through `UQA.persist` and startup restoration.

Stopping delivery closes the original inbox before discarding the pending Future. Explicit cleanup removes the registry entry and closes that same retained source before completing its Promise. A queued wake sees an absent pending receive or removed weak entry and does nothing. Existing failures are captured before cleanup and remain available afterward; a failed listener still executes the close call and releases admission. Abort, iterator return, iterator throw and finalization use the shared owner. Explicit close is the deterministic resource boundary; garbage-collection finalization is best effort, and page or Worker destruction releases that runtime as a whole.

## Value-preservation proof

Let $N$ be the Core event carrier, containing its variant, identity, optional $u64$ sequence, optional signed $i32$ process identifier, Unicode channel and payload, and optional closed failure category. Define $J:N\to V$ as the browser ABI encoding. It writes the sequence as canonical base-ten text, other exact bounded integers as JSON numbers, Unicode strings through JSON escaping, absent fields as null, and the Core variant and failure category by their fixed public spellings. Define $B:V\to N$ as the conceptual inverse of the public wrapper: parse the sequence with `BigInt`, recover strings and exact integers, and reconstruct the variant from its tag.

For every admitted sequence $s$, canonical decimal formatting and integer parsing are inverse, so $\operatorname{BigInt}(\operatorname{decimal}(s))=s$ even when $s>2^{53}-1$. Every process identifier is within $[-2^{31},2^{31}-1]$, which is exactly representable as a JavaScript number. Rust strings contain valid Unicode scalar sequences; JSON escape decoding preserves those sequences, and input validation rejects isolated JavaScript surrogates before registration. Core identity formatting has its existing unique inverse. Fixed variant tags distinguish the alternatives, and null preserves absence rather than inventing a value. Thus each component is recovered and $B(J(n))=n$ for all $n\in N$. Freezing the public value changes mutability and ordinary inspection, not any event getter. In particular no notification sequence enters the general SQL safe-number bridge.

## History and lifecycle preservation

Let $H$ be the existing committed notification history and $P_{C,b,e}(H)$ its ordered projection for channel set $C$, registration boundary $b$ and delivery-ending boundary $e$. Registration obtains $b$ from the original Engine and does not execute SQL on the caller session. The adapter never republishes, deduplicates or reorders events. One Future and one JavaScript consumer permit at most one completed receive at a time, and every successful completion applies $J$ once to the next Core value. By induction on the number of completed receives, inverse-converting the successful prefix gives exactly the corresponding prefix of $P_{C,b,e}(H)$. Empty histories and concatenation across a fixed projection are therefore preserved. The same argument applies to control events already admitted by Core; the adapter does not invent reconnect or replay.

Closing sets the Core end boundary before resolving pending application work. The shared owner checks abort or explicit close again after an awaited receive, so a value already dequeued but not yet observed cannot escape an observed terminal transition. Native overflow may discard the unread suffix and retains its typed failure, matching the existing direct-listener contract rather than asserting lossless delivery beyond capacity. Removing the registry owner and dropping its Future release the original wake slot, provider ownership and admission; later queued microtasks cannot recreate them because identifiers are not reused and absent entries are ignored. These state transitions preserve SQL rollback, transaction-local duplicate suppression, original selected authorization and existing queue limits without introducing an algebraic operator or changing document, graph or ranked-result carriers.

## Verification scope

Owning-crate tests exercise full-width sequence conversion, control events, real inbox wakeups, receive-slot release, retained query-close behavior, latched overflow and capacity reuse. Shared executable binding fixtures cover transactions, channel boundaries, invalid input, cancellation, event-loop progress, iterator cleanup and original memory/plain/compressed source retention. Browser acceptance additionally opens a fresh Worker against persisted IDBFS state and checks that SQL state restores while notification epochs and delivery remain isolated. Actual artifact runs and their source identities are recorded in the ledger; the proof is not a substitute for those runs or for complete process-resource, platform and serving-path qualification.
