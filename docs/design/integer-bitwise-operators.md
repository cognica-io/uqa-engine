# Integer bitwise operators

This design accompanies [#1287](https://github.com/cognica-io/uqa-engine/issues/1287) and [PR #1288](https://github.com/cognica-io/uqa-engine/pull/1288). SQL owns operator syntax, overload identities, coercion, result typing and value evaluation. Execution uses the existing scalar dispatch and stored-expression renderer; Engine supplies sessions and persistence. The change adds six numeric-operator variants to the existing scalar expression representation and does not add a plan representation, execution layer or dependency.

## Typed scalar domain

For $w\in\{16,32,64\}$, define $I_w=\{-2^{w-1},\ldots,2^{w-1}-1\}$ and $B_w=\{0,1\}^w$. Let $e_w:I_w\to B_w$ encode two's complement and let $d_w:B_w\to I_w$ decode it. They are mutual inverses: every bit vector represents exactly one residue modulo $2^w$, and exactly one member of $I_w$ has that residue. Define AND, OR, XOR and complement on $I_w$ by transporting their coordinate-wise Boolean operations through $e_w$ and $d_w$. For example, $x\mathbin{\&}_w y=d_w(e_w(x)\land e_w(y))$. Their domain and codomain are $I_w^2\to I_w$ or $I_w\to I_w$ for complement. The result's declared SQL type remains part of the observation; the shared integer value carrier alone does not determine $w$.

Closure follows because each coordinate result is in $\{0,1\}$ and $d_w$ is total. The Boolean truth tables imply coordinate-wise associativity, commutativity and idempotence for AND and OR, distributivity of each over the other, and the complement laws. Applying the bijection transports each equality to $I_w$. OR has identity $0$ and AND has identity $-1$, whose encodings are all zero and all one respectively. XOR is associative and commutative, has identity $0$ and satisfies $x\mathbin{\#}_w x=0$; it is not idempotent. Complement is an involution because complementing each coordinate twice restores it. These are laws of already selected, non-NULL integer values, not permission to reorder SQL expression evaluation.

## Width-preserving shifts

Let $p(16)=p(32)=32$ and $p(64)=64$. Let $S_{w,p}:B_w\to B_p$ extend the sign bit, $T_{p,w}:B_p\to B_w$ retain the low $w$ bits, and $k(c)=c\bmod p$ for a selected 32-bit count $c$, with residue in $[0,p-1]$. Define $L_p(b,k)$ to shift left with zero insertion and discard high bits, and $R_p(b,k)$ to shift right with sign insertion. The selected shifts are $d_w(T_{p,w}(L_p(S_{w,p}(e_w(x)),k(c))))$ and the corresponding expression with $R_p$. Every intermediate has its specified finite width, so both operations are total and closed on $I_w\times I_{32}\to I_w$. For $k=0$, truncating the sign extension returns the original bits, proving the zero-count identity. Shifts are not asserted commutative, and truncation prevents a general inverse law.

The Rust kernel first receives values converted by the existing selected coercions. Its 32-bit or 64-bit `wrapping_shl` and arithmetic `wrapping_shr` implement $L_p$ and $R_p$ with the masked count. Narrowing the result implements $T_{p,w}$; signed widening of that narrowed value implements $d_w$ in the shared carrier. In particular, shifting `smallint` by 32 uses $p=32$ and count zero, rather than a 16-bit shift implementation. The 32-bit promotion is visible in PostgreSQL 18.4's [int2/int4 source](https://github.com/postgres/postgres/blob/REL_18_4/src/backend/utils/adt/int.c); [int8 source](https://github.com/postgres/postgres/blob/REL_18_4/src/backend/utils/adt/int8.c) uses the 64-bit input. Signed overflow and out-of-width C shifts are not portable C guarantees: the modulo-count behavior is independently verified against PostgreSQL builds on AArch64 and x86_64, while the Rust implementation explicitly defines the same results without relying on undefined behavior.

## NULL, conversions and composition

Extend the value domain with SQL NULL. Each operator is the strict lift: after its reached arguments and required coercions have been evaluated, a NULL argument gives NULL; otherwise apply the selected operation above. Operator resolution precedes execution and uses the existing PostgreSQL signature selection, including mixed integer widening, domains, unknown literals and parameter inference. An invalid signature remains an analysis error, and a reached conversion or child expression error remains an error. This lift preserves the non-NULL equations on their original domain. It does not extend complement laws to NULL: for example, NULL OR its complement remains NULL, rather than all ones.

The embedding in a scalar projection evaluates the same input row and yields one selected typed value. It neither changes row support nor duplicates, removes or reorders rows. Filters and generated/index expressions consume that value through their existing typed interfaces. No posting payload, score, graph carrier, ranking or row multiplicity rule is changed. Since ordinary and controlled evaluation use the same conversion and value kernel, substituting the new implementation of a selected operator preserves the surrounding operation whenever its inputs, selected types, reached side effects and resource controls agree. This follows by structural induction on the surrounding expression: leaves and unchanged operators are identical, and at the replaced node the kernel realizes the defined typed operation with the same child evaluations. Planning-time constant evaluation uses the same selected identity and type; it may omit effects only under the existing PostgreSQL strict-NULL and immutability rules. The new Boolean value laws do not authorize additional optimizer rewrites.

Selected numeric input coercions are retained in the existing scalar tree before storage. Stored-constant transfer therefore preserves widening casts in views, defaults and index expressions; reconstruction prints those already selected conversions without introducing a second type-selection path. Binding the same stored expression again is idempotent. This applies equally to existing numeric operators and the integer bitwise family.

A retained `ResolvedNumericOperator` stores only the operation and fixed numeric conversion descriptors. The result conversion already records the width, so no duplicate type-name lookup or new retained object is needed. Every invocation converts its current arguments, observes the current allowance and both cancellation sources, then releases temporary owners. Retaining the description therefore cannot substitute an old input, bypass a current cast or hide a changed cancellation state. Stored definitions retain the existing serialized scalar dispatch and selected argument/result metadata; unrelated dispatch variants and physical record formats remain unchanged.
