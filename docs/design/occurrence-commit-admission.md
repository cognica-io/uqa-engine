# Occurrence commit read admission and ordered spill

Issue [#1075](https://github.com/cognica-io/uqa-engine/issues/1075) concerns occurrence preparation and native SQLite publication while new statement snapshots wait for the existing change-publication gate. The investigation starts from `e38848f8a664c8d53a9d77e61f4a5d7b0ef5ae19`. Its native occurrence layout stores score and positions together; the common Key/Value layout stores separate related records. The earlier spill-reader correction covered the latter layout and structural replacement. This correction shares unchanged-boundary read admission and preserves input order for effects replacing their own keys, including advanced-boundary merges. It introduces no storage format, SQL behavior, conflict exception, or new public API.

## Preserved observations

Let C_s(k) be the complete committed record at key k and sequence s, including absence, tombstones, revision, and the complete decorated occurrence graph. Let E be the immutable evaluated batch, including each original revision condition and record kind. The existing unchanged-boundary branch applies only when the base and current committed sequence are equal. It validates the base and evaluated graphs and retains the evaluated bytes and original condition. It does not infer equivalence from document support or score equality. When the sequences differ, the existing three-way per-document merge, statistics arithmetic, structural fences, and conflict handling remain required.

For combined cluster records at the same sequence, one ordered point-value visitor returns precisely the C_s(k) values that separate point visitors return. The committed snapshot lease retains s throughout that visitor. The common resolver still validates each source marker, each complete base graph, and each complete evaluated graph in the original order. Only immutable prepared lookups and private spill writes run inside the visitor; it cannot reenter committed provider reads. Canonical publication records can pass through without provider reads, while canonical command validation and other derived effects close the visitor before their ordinary committed reads begin. Thus the first record-validation failure and successful record contents retain their original order, without opening a SQLite transaction and checking its database source once per cluster.

The combined record replaces only its own key. Appending it to the ordered output therefore preserves the original key order, value, expected revision and mode-dependent record kind. The same argument applies to a computed combined cluster, a field-statistics replacement, and a format marker whose related marker key equals its input key. Computed replacements still obtain the current revision and execute the same arithmetic and validation. In contrast, split score/position records and derived related-key effects can change a different key; they retain the existing merge path. When a later derived effect requires that path, the completed sorted prefix is adopted once before applying that effect. No evaluated user change is replayed, and later overwrites keep their established precedence.

More precisely, before any related-key effect the unique input keys k_1 through k_n receive the same records T_1 through T_n that the previous overlay applied. After each prefix i, appending (k_i, T_i) represents the same partial map as M_i = M_(i-1)[k_i := T_i], because no earlier input has key k_i. Spilled input is key-ordered, so this append also satisfies the run writer's order condition. At the first related-key effect the existing builder-to-overlay conversion retains exactly M_i; subsequent replacements use the original overlay operation in the original order. Induction over the prefix and remaining effects therefore preserves every final record, not merely its live document support. A batch consisting only of own-key replacements writes each payload once rather than repeatedly merging its growing prefix.

Each visitor owns at most one copied request key and one selected prepared record, under the original `StorageReadControl`. Existing authenticated spill readers and writers retain their allowance, bounded buffers and cleanup rules. Cancellation and admission failures propagate before publication; dropping unfinished resolution releases its temporary output. A corrupt committed or evaluated occurrence graph remains an error. Physical publication still checks the same record preconditions and resolved sequence, and retry still resolves against a new committed snapshot.

Engine retains its existing exclusive publication gate across backend commit and row-change metadata publication. Storage snapshots and row-change metadata therefore continue to describe the same committed boundary. Reducing repeated work within that interval does not authorize bypassing the gate or weakening snapshot consistency.
