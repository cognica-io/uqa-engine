# Bounded SQL diagnostics and atomic batch location

HTTP errors may add an optional `diagnostic` object containing a five-character uppercase ASCII SQLSTATE, a closed category, a zero-based `statement_index` into the submitted batch and a one-based character `position` within that member. Missing fields mean unknown; they never imply the first statement or character. Categories distinguish syntax, absent relations and columns, vector dimensions, missing text indexes and the remaining documented SQL failure classes. Clients validate the optional object and do not interpret remote SQL, identifiers, messages, details or hints as diagnostic metadata. Human guidance is derived from the closed category. Old servers without this object remain readable.

`Engine::sql_batch_diagnosed` runs the same transaction and admission path as `sql_batch`, preserving the original SQL error with its failing member. The existing `sql_batch` and `sql_batch_with_labels` interfaces discard only that additional location and retain their prior error and result types. Parser failures preserve their original diagnostic, including its character position. Missing physical text indexes acquire an explicit variant with the same SQLSTATE and primary message. Beginning, committing or cleaning up a transaction can fail independently of any member; those failures have no statement index. This metadata does not prove rollback when transaction completion itself fails and never authorizes automatic replay.

Rust `HttpEngineError::Server` retains `diagnostic`; Python `HttpEngineError` remains a `RuntimeError` subclass with `code`, `status`, `request_id` and a diagnostic dictionary. The public Node.js HTTP entry points retain `error.diagnostic` with `statementIndex` and `position`. Error frames retain the same object. `Display`, exception messages and diagnostic debug output contain only validated fields and source-owned guidance, while existing explicit access to a server's message remains separate.

## Preservation argument

Let `S` be the engine state, `Q = [q0, ..., qn]` the ordered batch and `T(S,Q)` the existing transaction computation, producing either `(S', [r0, ..., rn])` or a SQL error after its existing rollback/commit handling. The diagnosed computation applies a pure map `e -> (e, i)` at each existing admission, execution and result-observation boundary for member `i`, and `e -> (e, unknown)` at transaction boundaries. It performs the same ordered calls exactly once, neither adding a state transition nor moving a check across another call. Erasing the index therefore gives exactly `T`, including its effects, notices, cancellation, panic and cleanup-error precedence. Success composition and the empty batch are unchanged because mapping an error does not alter a successful result. No new retrieval, ranking or algebraic operator is introduced.

For HTTP, define `P(e,i)` as the projection onto the error's typed category, validated SQLSTATE, known parser position and optional member index. Every component is selected from a finite enumeration or a bounded integer/ASCII carrier. `P` does not inspect primary message, SQL, values, identifiers, detail or hint. Consequently replacing any of those private strings while holding the typed fields fixed leaves `P` unchanged. Serializing and decoding `P` preserves those observations; malformed optional metadata is not promoted to a trusted diagnostic. Applying `P` after an error does not modify `S`, retry `Q`, or change the transaction boundary. Tests exercise these obligations through real batch rollback, original parser locations, actual HTTP clients and native Python bindings.
