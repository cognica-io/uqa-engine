# Native MVCC read preservation

This correction removes full document scans from maximum-ID reads, repeated catalog scans from unchanged command views, repeated metadata reads from idle maintenance, and per-key statement execution from ordered point-record metadata reads. It changes no stored format, SQL operator, query result, commit protocol, isolation level, or maintenance deadline. The implementation starts from main `8a99d4fd3` (0.4.7). The motivating application samples showed native maximum-ID scans, pinned catalog restoration and maintenance metadata reads on active worker stacks; sample occupancy is not an elapsed-time benchmark or a CPU utilization estimate.

## Record carrier and visibility

Let K be finite byte strings with lexicographic order. A record is a tuple containing its encoded value or tombstone, committed precondition/revision and, for private replacements, its evaluated private identity. Absence is distinct from a tombstone. A committed snapshot C_s maps a key to the newest retained revision at sequence at most s, or to absence. A private root P_r is a finite partial map of evaluated replacements. The visible map is V(s,r) = P_r ▷ C_s, where (A ▷ B)(k) = A(k) when A defines k and B(k) otherwise. This operation is closed on partial record maps, has the empty map as a two-sided identity, and is associative: evaluating either parenthesization at k chooses the first defined operand in the same order. It is not commutative, and a private tombstone remains a defined operand. These laws concern the complete record tuple; equality of live document support alone is insufficient.

The correction does not change ▷ or any tuple field. Existing scans, document decoding, values, graph carriers, indexes, ranking and transaction publication therefore compose with the same V. The added seek returns a metadata projection of one member of this existing map, not a new algebraic operator on postings or scores.

## Greatest-key selection

For a prefix p and optional exclusive bound b, define S(p,b,V) = { k in dom(V) : k starts with p and (b is absent or k < b) }. The greatest-key operation returns no result when S is empty; otherwise it returns (max S, metadata(V(max S))), including a tombstone. The committed default implements this definition by a forward ordered scan with one retained candidate. SQLite uses descending indexed head seeks and descending run-member seeks, always resolving a point head at the retained sequence. Keys created after that sequence are skipped. Compacted runs use binary search on their bounded consecutive big-endian suffix interval; selection takes the greatest candidate across key lengths. This preserves variable-length byte-string order, exclusive bounds, prefixes ending in 0xff, point precedence and historical visibility without expanding a run.

Let a and c be the greatest eligible private and committed keys respectively, omitting an undefined candidate. Since dom(P_r ▷ C_s) is the union of the operand domains, its greatest eligible member is max(a,c). If a >= c, the private record supplies that member, including equality; otherwise the committed member supplies it. The merged seek implements exactly these cases. Seeking the private root uses the existing immutable ordered tree: each comparison discards a subtree whose keys cannot improve the eligible candidate. Balanced-tree height bounds comparisons by O(log |P_r|), with no traversal allocation and no payload copy.

Native document integer encoding preserves document-ID order. Maximum ID repeatedly applies the greatest-key operation, returning the first live record's decoded ID. A tombstone becomes the next exclusive bound. Each iteration removes at least the selected greatest identity, so termination and the result equal a forward scan's maximum live ID, or zero for empty live support. Cost depends on the trailing deleted or snapshot-invisible identities, not all preceding live documents; this is not a constant-time claim for a wholly deleted history. Autonomous identifier watermarks and their rollback behavior remain unchanged.

## Ordered physical reads and resources

A SQLite read window retains the original committed sequence and uses one physical read transaction for validation and all cursors. Its size cursor and data cursor use identical lower/exclusive and upper bounds and ascending head-key order. Therefore their i-th rows refer to the same physical head. Each cursor reserves its own copied variable-length bindings before binding them. The size cursor exposes only encoded key length. The operation reserves that length before stepping the data cursor, which then obtains the encoded key and visible revision metadata. Equality of measured and fetched key lengths is checked. The previous key's reservation remains alive until stepping releases its SQLite-owned buffer. Stopping a visitor does not step another data row. A rejected reservation never fetches that key or calls its consumer.

The data cursor selects exactly the same newest version at or before s as an individual point read, including compacted point tombstones and the existing encoding validation. Ordered run candidates merge with these point candidates in byte order; equality retains point precedence. A pending run identity stays in the run codec's bounded 1024-byte workspace for comparison. Only a selected run key obtains its payload and binding reservations before metadata access and visitor delivery; advancing a tied run happens only when the point consumer continues. Consequently a later run whose key exceeds the allowance cannot prevent an earlier small point from satisfying a limit or early stop. The visitor count includes visible tombstones and excludes identities absent at s. Thus ordered key metadata and value scans have the same order, bounds, limits, early-stop behavior and revision observations as the prior seeks. Value reads still check encoded size and reserve before fetching a live value. Retained leases continue to protect every required version; cancellation remains checked before materialization and after visitors. Prepared-statement caching retains validation queries, their results and their errors.

For an uncompacted point prefix, a key-only scan now uses a fixed set of statements and two streaming cursors, instead of executing size, key and visible-revision statements for every key. The cursor does not retain a page of arbitrary keys or values and does not call SQL or user callbacks from its internal visitors. The common fallback and physical reclamation paths retain their existing contracts.

## Complete command identity and cache validity

A cache token is (database history incarnation, committed sequence s, private root revision r). Every successful nonempty evaluated replacement batch receives an identity from the existing process-global checked allocator, whose identities are never reused. The allocator starts at one and increments only with checked addition, so zero is unreachable; `NonZeroU64` preserves the same numeric identity while allowing an optional identity to occupy one word without a separate discriminant. That identity is published only with the successfully constructed private root, including retained-source mutations. Failed preparation changes neither root nor identity. Savepoints retain both; undo restores both without allocation or consuming another identity. Empty roots have no private identity. Command rebase retains the committed sequence and newly evaluated private root as one pair. Tokens are process-local and never persisted.

All private record and source roots and the savepoint buffer are initialized with the same allowance. Replacement and cloning preserve that allowance, and rollback initializes empty roots from the current record root's allowance. Inductively the record root always retains the owner's original allowance, so preparation and snapshot reservation can obtain it from that root. Removing the owner's duplicate allowance handle offsets the added root identity without adding an allocation or weakening reservation ownership. The existing persistent indexing allocation ceilings remain unchanged.

Savepoints and private snapshots retain the source map as an immutable root and cardinality, without a duplicate mutable allowance handle. Every nonempty root owns nodes whose complete allocation leases retain the original allowance; an empty root owns no nodes. Capturing or cloning this representation therefore loses neither entries nor reservations. Restoration first requires a nonempty root's allowance to match the mutable map, then copies exactly that root and cardinality; the invariant that every node belongs to this allowance follows by induction on checked restoration and ordinary insertion. Lookup uses the same ordered-tree traversal. Thus this compact representation preserves source selection, lookup, cardinality, sharing, undo and final reclamation, while offsetting the added identity word in both saved representations. Private snapshot layout reservation still charges the complete actual type before capture or clone, and its field follows the roots so their references are released first. No payload or byte escapes admission.

Induct on root transitions. Empty roots have identical visible private state. A successful replacement receives an identity never assigned to another constructed root. Sharing, retaining or releasing a savepoint changes neither records nor identity. Undo restores a previously paired root and identity. These are all publication transitions; therefore equal private identities identify equal private replacements. Equal history incarnation and committed sequence identify the same C_s under existing provider retention and restore contracts. Equal complete tokens imply equal V(s,r), including tombstones, original preconditions and payloads. The implication is sufficient for reuse; different tokens may conservatively identify equal values.

Engine skips pinned cache restoration only when the complete token matches the last successful restoration, tracked catalog revisions remain present, and published table, data and registry epochs match their observed epochs. Providers without the capability retain the old conservative refresh path. Before a restoration that can mutate cached state, the old token is cleared; only complete success publishes the new token. A failed partial restoration followed by undo cannot reuse the prior token. Token comparison does not replace pinning, SQL isolation, serializable read/write observations, statement ownership, or autonomous value reads.

Initial restoration seeds a token only when the complete view before and after restoration agrees and tracked generations are stable. A public sibling factory retains its existing source statement gate, epoch checks and independent session binding. It seeds the copied caches only when the source's last successfully restored token, the source's current view and the sibling's current view all agree. Otherwise the sibling performs ordinary pinned refresh. An external commit racing these checks either changes a compared token or leaves the subsequent pinned view different, requiring refresh before reuse.

Analyzer restoration distinguishes declared SQL columns from document fields. For a declared table, a named binding still requires an existing TEXT column registered in the physical FTS index. A document table declares no SQL column contract; its persisted physical FTS field supplies the binding identity, and source indexing continues to select only stored strings. Restoration still consumes exactly one binding per physical field, validates named revisions and GIN ownership, and rejects bindings left over for missing tables or fields. This restores the existing document registration/reopen behavior without admitting a missing or non-TEXT declared SQL column.

## Maintenance state reuse

The maintenance worker synchronizes the table catalog and data once per pass and retains those table handles. Its decoded-state cache is keyed by qualified name, immutable relation object ID and tracked maintenance revision. Before caching a load it requires the stable backend generation used by the synchronized catalog; a racing commit prevents publication of that cache entry. Untracked or unstable providers and failures retain the ordinary load path. Successful analysis removes its entry, changed identities/revisions reload, and removed names are pruned.

For a tracked object and maintenance revision, the provider's existing revision contract identifies the same durable metadata, including absence. Reusing its decoded state therefore preserves every maintenance observation. Only the state is cached: missing-statistics and due predicates still evaluate the current table statistics, format and clock on every pass. In particular the dirty-age deadline remains 60 seconds and polling remains one second. Analysis obtains its existing transactional guards and refresh; a commit after a pass's initial observation is eligible on the next synchronized pass, as with the previous read/check/analyze scheduling.

## Prepared immutable spill ownership

A prepared spill contains exactly one final replacement per key, including its original precondition, kind, private entry identity and payload. An independently mutable private owner may retain the same immutable run when both owners share the exact same memory allowance. The new owner receives a fresh root revision and rebuilds only its optional key-scope identities; entry identities remain attached to unchanged evaluated replacements. Later writes form the ordinary newer overlay, and undo restores the saved run and root identity. Therefore every point or ordered read selects the same complete record tuple as copying the prepared run, without reading or rewriting its payloads during adoption. Crossing allowances still copies and charges a new run, so another owner cannot borrow metadata charged to a budget that it does not own.

When a private root has no resident tail and exactly one immutable run under the requested allowance, preparation retains that run directly and computes the same fingerprint from its authenticated entries and payload bytes. Multiple runs and nonempty tails still use the ordinary precedence-preserving merge. Cancellation checks, value authentication, complete fingerprints, mutation independence, savepoint rollback and final reservation release remain required. Owning Storage tests use independent synthetic records and exact byte counters, including a foreign allowance too small to accept the run.

## Shared ancestor spill admission

A resident spill map and unrelated private state can share an ancestor allowance whose remaining bytes are smaller than either component limit. Before growing the resident immutable root, admission temporarily reserves the complete disk-conversion workspace and the maximum encoded record against that same ancestor. Payload and tree growth occur while this reservation is held; failure returns ownership of the incoming value and converts the previous complete root before retrying the write on disk. This prevents the map from consuming the bytes required to spill itself. Conversion retains the input root until its independent encrypted file is complete, so read views, cloned roots, cancellation and failed writes retain the original atomicity rules. The owning regression retains unrelated ancestor bytes while exercising ordered construction, arbitrary inserts, independent mutation and complete lease release.

## Ordered batch metadata admission

Let an evaluated batch be the finite ordered sequence of edits E = (e_1, ..., e_n), applied to private root P_0 against the retained committed snapshot C_s. For a point edit at key k, its original precondition and effective write kind come from the current private replacement when one exists, otherwise from metadata(C_s(k)). A canonical or graph-preview deletion of an absent or already deleted record is the same no-op as before. Other kinds retain their existing replacement rules. Applying an edit constructs P_i from P_(i-1); a later duplicate key therefore observes the earlier private edit, not a second committed revision. Prefix deletion still enumerates exactly the current merged map and stages the selected live keys with their original revisions.

The request stream advances in this order, applying private-only point edits immediately and requesting metadata only when the current key lacks a private replacement. SQLite lazily admits one physical read transaction after the first such request and resolves every requested key at the unchanged retained sequence s. The snapshot lease protects C_s across later commits, so moving adjacent point metadata reads into one physical window changes neither their revisions nor tombstone visibility. The same scalar metadata decoder, length-only selection, binding reservation and diagnostics serve both interfaces. Retained snapshot wrappers forward the capability; other providers use its sequential point-read default. Empty and entirely private sequences acquire no physical read window.

Induct on i. The initial private root and committed snapshot agree. If the previous roots agree, the current key's private metadata or metadata(C_s(k)) agrees, so its precondition, kind, skipped deletion and replacement agree. A prefix edit ends the physical window before its unchanged ordered scan, and therefore sees the same merged state by the same hypothesis. This proves equal complete private record maps, original conflict conditions and edit order after every successful prefix of E. Atomic application keeps its original savepoint; any producer, metadata, reservation, journal, consumer or cancellation failure restores that savepoint and does not request a later edit. Savepoint undo, commit conflict detection and retained/reopened observations consequently remain unchanged.

The streaming cursor shares resident payload owners and decodes only one journal edit at a time, retaining the existing bounded authenticated block buffer. It opens the journal only after the resident prefix is consumed, preserving error precedence. No batch-sized metadata or value collection is introduced, and the provider window closes before a prefix scan or the next operation can reenter storage. The original source/history validation runs at each physical admission; it is not disabled or cached by elapsed time. Owning tests require one physical admission for 4, 128 and 512 point edits under 128 KiB, no admissions for private-only rewrites, exact duplicate/prefix/undo/conflict results, and historical live/absent/tombstone metadata under an allowance too small for its payload. Consumer failure and cancellation must stop before another key is produced.

## Prepared occurrence marker metadata

An occurrence replacement first selects its immutable prepared format marker, then checks whether the same batch supplies a structural fence or a canonical marker. In that branch the resolver preserves the evaluated replacement with its original write condition and canonical kind; it does not inspect the marker payload. `PreparedLookup::metadata` projects exactly the selected key, original condition, kind and optional value length from either the resident write or spilled entry. It never loads the value.

Let `M` be the marker selected from the immutable prepared batch and `F` the existence of its structural fence. The original structural branch predicate is `M exists && (F || kind(M) = Canonical)`. Replacing the first full lookup with the metadata projection preserves marker existence, the predicate and the order of the missing-marker and fence checks. The branch output depends only on the already selected input write and its validation, so removing the unused marker payload read preserves every output key, value, condition and kind. When the structural predicate is false, the resolver still requires an occurrence marker and loads its original payload before validating the exact format bytes and performing the existing rebase. No merge, validation or publication order changes.

One ordered spilled input cursor therefore reads each structural output value once, without a marker lookup repeatedly replacing its current decoded value block. The Storage regression checks exact value-read counts for 4, 128 and 512 paired terms under the original 128 KiB allowance in both command and publication modes. It also checks all output bytes, conditions, kinds and final lease release. A separate metadata regression covers resident and spilled records, a 128 KiB value under a 4 KiB consumer allowance, tombstones, absence and cancellation without reading any spill value. The deterministic CI inventory uses the same optimized dev/test profiles as full workspace qualification, retaining debug assertions, overflow checks, complete fixtures, work and memory assertions and the original stall guard. Timing claims still require the independent controlled-host process.
