# Bounded commit preparation and SQLite maintenance

Large native record commits repeatedly read authenticated spill values, copied each replacement into a persistent verification queue, then copied it again into native and MVCC tables. SQLite also ran its automatic WAL checkpoint on the foreground COMMIT while Engine excluded new statement snapshots. The investigation starts at main `38f41167e7e8c350c7b45718922e7621eb61a43e`. Existing native/KeyValue/redb text fixtures reproduce the paths; local elapsed times are diagnostic and are not controlled performance acceptance.

## Ownership and preserved behavior

Storage retains an immutable prepared record byte total during the existing fingerprint pass. Reading that total performs no spill I/O. SQLite uses it to size its existing connection-local commit page cache without another metadata scan; the ordinary cache and existing 256MiB maximum remain unchanged. Resident and spilled constructors count the same complete key and optional value bytes, with saturating arithmetic only for cache sizing. The fingerprint, record order, expected revisions and value bytes are unchanged.

The native verification queue retains record ownership and physical keys, with an empty BLOB as the presence marker for a live target. It no longer stores a second copy of each full replacement. Old-row validation scans prepared metadata without reading the replacement payload, except when comparing immutable standalone namespace or format bindings. After native materialization, the MVCC history pass verifies each live prepared record's owner and exact physical row bytes before writing its history. The queue still verifies absent targets, retired bindings, deleted old keys and unexpected trigger/cascade changes. Thus every live target equals its prepared value, every deleted target without a new owner is absent, and every captured native change has an expected owner or the existing provider-owned cache-generation classification. All verification, native writes and histories remain inside one SQLite transaction; any failure rolls back the whole transaction. The empty work queues retain their existing schema, so no database format migration is required.

Common logical Storage sessions expose optional precommit preparation. It seals the evaluated batch and prepares immutable derived inputs without publishing them. The existing physical commit still validates expected revisions and the resolved sequence, re-resolves derived effects when required, and retains its original receipt/fingerprint across uncertain outcomes. SQLite native, SQLite KeyValue and redb forward this operation to the common session. Legacy providers keep their existing commit path. Preparation failure remains rollbackable; later evaluated writes are rejected after sealing.

Execution owns a separate writer-preparation guard, with process-local exclusion and an advisory sidecar claim at previously unused byte 56. Engine acquires it before the existing change-publication gate and keeps it through final metadata publication. Statistics settlement still runs under the existing publication gate. Ordinary data transactions then release only the snapshot gate while Storage prepares their immutable inputs and reacquire it before physical commit and row-change publication. Other SQL writers cannot overwrite the settled statistics counters in that interval. Readers can capture an earlier complete committed boundary. Transactions retaining notification or temporary-role publication keep the previous gate ordering. The final data/row-change boundary remains atomic; physical publication itself is not moved ahead of the gate. Independent writers that do not use this Engine adapter remain subject to Storage's original expected-revision and resolved-sequence validation.

The SQLite pool owns one managed checkpoint worker for each ordinary file pool on native targets. Its WAL callback only signals maintenance after 1,000 frames; the callback replaces SQLite's synchronous automatic checkpoint. The worker owns a distinct connection, retains encryption configuration and database identity, coalesces requests, and uses PASSIVE checkpointing with no busy wait. Incomplete checkpoints and errors remain scheduled with a bounded retry interval. Source replacement is never adopted. Foreground MVCC commits keep FULL synchronization; moving checkpoint work does not defer commit durability. A 64MiB journal size limit bounds retained WAL space at a safe reset; active physical readers and a single larger transaction may retain more required frames, as with SQLite's automatic checkpoint. The worker never forces their release. Pool destruction joins the worker before closing pooled connections and releasing restoration exclusion. Memory, auxiliary DELETE-journal, compressed VFS and browser configurations retain their original maintenance path.
