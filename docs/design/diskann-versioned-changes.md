## Ownership and atomicity

Storage's `KeyValueDiskANNCanonical::replace` writes existing canonical coordinates, the complete tensor's origin and one immutable change record in the same evaluated MVCC batch. The change contains only origin/shape metadata; it does not duplicate coordinates. Empty replacements also create a change. Common MVCC supplies the actual publishing writer and non-reused mutation revision, preserves statement/savepoint rollback and seals evaluated bytes for receipt-safe retry. Engine, dependency direction and Cargo features are unchanged.

`SQLiteDiskANNCanonical::replace` uses the same common mutation scope and codecs with native object-owned rows. Coordinates remain in `_vectors`, origins remain in their existing family, and the journal accompanies both in one evaluated native publication. An acknowledgement failure after durable commit retains that outcome and completing the original attempt keeps the same origin and single change record.

Independent documents retain distinct canonical guards and change keys. A same-document writer still validates its original canonical precondition. Change keys include the complete mutation identity, so a subsequent replacement receives a different key; eventual deletion of an older covered key cannot overwrite a later writer's change. This avoids making ordinary writes depend on a shared index header or a mutable per-document maintenance slot. Writer allocation order is never interpreted as commit order.

## Live bound mutations and query snapshots

`KeyValueDiskANNCanonical::bind` and `SQLiteDiskANNCanonical::bind` consume a session-bound canonical owner and return `KeyValueDiskANNHandle` or `SQLiteDiskANNHandle`. Opening requires the actual table/index definitions, complete effective parameters, a resolver supplied by the SQL owner, and an already published physical generation. Storage owns this integration; native SQLite only adapts its catalog and raw record layout, and redb uses the common Key/Value owner. No SQL decoding, provider dependency or algorithm is added to Engine.

Let $I=(H,T,S,X,\theta)$ identify the actual transaction history, table object, table storage generation, index object and effective parameters. The live owner remembers this identity from its initial captured catalog, not from caller-supplied generation labels. Each replacement captures the current catalog on the very read supplied to the evaluated canonical mutation, resolves its immutable identities, and requires $I'=I$. Both catalog layouts validate the selected field and dimensions. The same batch retains exact current definition-record requirements, so a later competing definition commit rejects the write. Committing an unchanged private definition may change its record revision without changing $I$; recreating the table/index, changing its storage generation or configuration cannot silently rebind the handle. The catalog lifecycle must preserve its existing non-reused identity contract.

For one document $d$, complete tensor $V$ and freshly allocated origin $\nu$, successful mutation changes $D$ to $D[d\mapsto(\nu,V)]$ and adds the immutable change $(d,\nu)$ with the same complete origin and cardinality. These effects use the existing single evaluated mutation; either all canonical ordinals, the origin, the journal and definition guards become visible or none do. An empty $V$ has zero vector support. Distinct documents modify distinct canonical guards and journal keys, so they do not acquire a shared mutable index-header conflict. Competing writes to the same document retain the common original-precondition conflict. Savepoint undo restores the previous root without reusing $\nu$, and resolving an uncertain commit keeps the originally evaluated effects.

`handle.snapshot()` selects its current canonical, journal, catalog and head on one retained view, checks the same $I$, and returns the existing read-only `RetainedDiskANNIndex`. There is no exact fallback when a head or physical source is missing or corrupt. A newly prepared snapshot loads the selected generation's resident PQ/origin data; repeated searches and nested snapshots reuse that preparation. The live handle retains identity and controls without pinning its opening canonical corpus. Old query snapshots keep their original data and physical generation through later mutations, publication, rollback and source closure.

The document-search preservation argument applies to each fixed $(D_\tau,J_\tau,G_\tau)$ snapshot. Atomic complete replacements preserve its origin/count invariant, and every uncovered current replacement remains available through $J_\tau$. Therefore masking and full-tensor reranking use one visible version per document, raw cosine and the existing document ordering; no new score/probability conversion or algebraic operator is introduced. The live handle's original allowance charges adopted name capacities and wrapper state as well as ordinary capture/query workspace; cancellation remains active for mutations and fresh reads. Definition failures and admission failures leave prior canonical effects intact.

These handles expose ordinary complete replacements and owned query snapshots for already published indexes. `PersistentDiskANNIndex` supplies their mutable runtime interface through the provider-owned structural operations below. Execution connects SQL create/drop/truncate and logical SSI observation through merged PR #189, and schedules automatic finite journal maintenance through the existing database worker. Complete lifecycle acceptance remains unfinished.

## Transaction view acceptance

Let $C_{\sigma(s)}$ be the committed canonical state selected for statement $s$, and let $M_t$ be the transaction's already evaluated document replacements and deletions. Its query state is

$$
C_s=C_{\sigma(s)}\oplus M_t,
$$

where $\oplus$ replaces a document's entire tensor, including an empty replacement, or removes that document. READ COMMITTED selects a new $\sigma(s)$ at each command; REPEATABLE READ keeps the first data snapshot through later statements and savepoint rollback. Undo changes $M_t$ without changing that fixed committed boundary or reusing a mutation identity. Storage captures canonical values, current journal origins, catalog and head on this same view, so the existing masking and reranking argument applies to $C_s$ without mixing row versions with newer vector scores. A row-lock recheck instead substitutes the updated target tuple and evaluates its retrieval membership and score through the existing committed retrieval adapter; only that pinned target can survive the recheck. A conflicting fixed-snapshot lock reports `40001` through the existing transaction owner. This is the existing [PostgreSQL 18 transaction contract](https://www.postgresql.org/docs/18/transaction-iso.html) applied to the DiskANN storage adapter.

The [Engine isolation schedules](../../crates/uqa-engine/src/tests/catalog/index_registry/diskann/isolation.rs) exercise native SQLite, SQLite Key/Value and redb. They cover first-read admission after BEGIN/SAVEPOINT, peer commits, private update/delete/insert, rollback before and after snapshot selection, durable rows/scores after session reopen, and observed row-lock waits. The locking schedules check changed scores, loss of top-k membership, failed residual predicates and deletion under both isolation levels. A duplicate-key failure reports `23505`, later SQL reports `25P02`, and rolling back to the earlier savepoint preserves preceding private vectors without leaking failed rows or scores to a peer.

Independent reference execution on 2026-09-27 KST used Docker `postgres:18.4`, reporting `18.4 (Debian 18.4-1.pgdg13+1)`. The reference stores these single-vector unit tensors as `float8[][]` and projects `embedding[1][1]`, whose literal values are their cosines against $(1,0)$. The same visibility, savepoint, constraint-error and observed locking schedules establish SQL results and SQLSTATEs independently of UQA. The reference uses an ordinary scalar row predicate for locking; DiskANN top-k membership is checked separately against the fixed three-vector ordering.

## Mutable persistent lifecycle

Both canonical owners provide `create_index`, `rebuild_index` and `retire_index`. Structural operations require the caller's active definition transaction. Creation requires an actual stored index definition with no published head. It takes a private savepoint, validates existing raw ordinals in document order, and stamps complete origins and changes without copying or rewriting coordinates. Construction failure rolls back only this operation, preserving earlier caller effects and leaving the original raw field intact. Structural operations never commit the enclosing transaction.

Field lifetime requirements and immutable data-revision markers coordinate adoption with every versioned raw-vector writer, including brute force, IVF and HNSW. Ordinary document writers share a mergeable marker and retain the field's lifetime precondition. Adoption and clear fence both records. A racing insertion absent from the captured corpus therefore conflicts in either commit order: a data-first commit invalidates the structural marker precondition, while a structure-first commit invalidates the writer's lifetime requirement. Enumerating or rewriting existing keys alone would not prevent that phantom insertion. Key/Value guards use a separate field namespace; native guards encode the complete object/storage/field address in existing metadata records. The main-record format fence below rejects predecessor writers that omit these guards.

`DiskANNIndexOptions` carries the original parameters and explicit partition, merge, generation and read limits. Memory and persistent owners run the same bounded construction sequence. `KeyValueDiskANNStage::build` captures one retained source, constructs encrypted partitions and adjacency, writes and seals the real generation, and returns its original source-bound coverage. Native SQLite uses this same builder. Before publication, the owner prepares an actual query against the sealed generation under the original read and resident-memory limits; a generation that cannot be admitted for queries is rejected before replacing the head. Publication retains the original expected head, exact catalog guards and private canonical input; a competing head or definition cannot be refreshed into acceptance.

`PersistentDiskANNIndex` binds one live provider handle, construction options and the shared temporary allowance. Opening validates actual resident data and fails on a missing or corrupt head; it never repairs an index during restoration. Ordinary mutations use the bound complete-tensor path. `initialize` builds a replacement generation from the current source; `clear` removes canonical membership in a private savepoint and publishes an actually empty generation before releasing that savepoint. Failure restores the old head and canonical data. Old committed and private query snapshots retain their original generations through replacement, rollback and connection closure. Count and membership use shared canonical metadata probes without preparing PQ data or loading graph pages.

`retire_index` removes the captured selected head and transitions its generation from Published to Retired in one evaluated batch before the SQL owner removes its catalog row. The same operation fences the field's lifetime and preserves raw vectors for a replacement exact index. Both private and committed heads retain their original observed publication requirements through retirement. A superseded capture cannot retire a newer head, and a failed batch cannot leave only half of the transition. Savepoint rollback restores the selection and catalog; reusing the SQL name allocates a different immutable index identity. Previously retained readers continue using their original sources, while an old live handle fails instead of attaching to the recreated index. The [bounded generation reclaimer](diskann-key-value-generations.md#committed-generation-reclamation) can then remove committed current records while retained readers keep their historical source; it never treats a private retirement as cleanup authority.

These operations establish owner-level creation, rebuilding, clearing, retirement and writable `VectorIndex` behavior. Backend/Engine registration and initial private-DDL scheduling are connected below. Finite VACUUM discovery now reclaims abandoned and retired payloads; automatic background reconstruction is connected, while final MVCC head-tombstone reclamation and complete recovery acceptance remain required before release. A failed dedicated physical build can leave unpublished records for that recovery owner; these records are not an accepted retention bound.

## SQL registration and table lifetimes

Execution resolves a single vector or tensor field before finalizing the effective DiskANN parameters, persists every effective option and revision, and publishes the actual catalog definition before the provider build. Storage binds the resulting table, storage and index incarnations on the caller's transaction; Engine supplies the table registry, provider, cancellation and existing memory allowance. Restoration uses the captured catalog row and already published generation without an implicit build or exact-index substitution. Memory execution uses the same bounded builder and a retained document source supplied to Execution for typed vector/tensor backfill.

The host defaults impose 256 MiB of resident generation data, 16 MiB of cache, 1 MiB of in-flight page data and 8 MiB per encoded record, additionally constrained by the caller's original memory allowance. Construction defaults use 8,192 points per admitted partition, 65,536 records per merge buffer and 4,096 entries per output batch. One session-shared encrypted temporary allowance caps coexisting builds at 8 GiB. These are finite admission ceilings, not measured performance settings; they do not increase the caller's original allowance or silently reduce algorithm parameters.

DROP INDEX retires its captured head before replacing the field with the existing exact index. Table and column removal retire while the old definitions still resolve. TRUNCATE removes canonical rows under the original incarnation, then Execution coordinates retirement, persisted storage-incarnation replacement and construction of the empty successor; index identity and effective parameters survive. The original statement/savepoint transaction owns undo across the complete sequence. Memory rollback restores the captured table object even when DROP followed by same-name CREATE has placed a different object in the registry.

Column rename detaches the live DiskANN handle while documents are rewritten, moves canonical vectors, origins and changes through the existing catalog owner, persists the renamed schema and binds the existing generation again. Memory execution retains the same physical owner. No clear or rebuild replaces the generation during rename. Table and index rename retain their existing immutable catalog identities; actual mutation, savepoint undo and provider-session reopen verify the binding after each rename.

For ALTER COLUMN TYPE, Execution retires the original generation and selects a canonical writer with the target dimensions before row conversion, within the existing table-definition lock and transaction. The target declaration governs converted values; USING expressions still receive the original source type. After the new schema and complete canonical vectors are stored, construction publishes one replacement generation under the original index identity and effective parameters. A scalar conversion acquires its index-definition locks while the original generation remains readable, then retires that generation and removes its definition; no lock-triggered refresh can try to reopen an already retired handle. Incompatible dimensions, options or values roll back the declaration, canonical data and physical selection together; preceding outer-transaction work survives a savepoint rollback. Retained readers continue selecting their original data and generation. The canonical rewrite writer is private to this schema operation and does not replace the completed public DiskANN index.

Execution's serializable snapshot wrapper forwards controlled KNN and threshold searches to the selected physical owner, preserving its original allowance and the independent invocation cancellation. Positive-k and threshold searches observe the entire canonical candidate field before searching. Every canonical document-write key lies in that range, independently of which graph nodes expand, which pages are cached or which candidates reach the result. Nested snapshots retain the original participant and range. Therefore a change to an unvisited candidate still contributes its read/write dependency; a reverse dependency on another relation forms a serialization cycle. Direct zero-k and EXPLAIN without execution add no candidate observation. SQL still rejects a non-positive k.

This runtime path merged in PR #189. SQL/planner acceptance, final physical metadata reclamation and full public operator/binding acceptance remain required before release. Local Engine SQL tests cover the listed memory/native SQLite/SQLite Key/Value/redb paths; they do not establish completion of those remaining gates.

## Predecessor writer negotiation

SQLite main record format 52 and redb main record format 51 fence binaries that lack the canonical field lifetime/reference, retained build-ownership, database-wide generation allocation or [atomic bound preparation and mapping reclamation](diskann-key-value-generations.md#catalog-mapping-reclamation) protocols. Native SQLite mapping 12, catalog version 49 and the immutable DiskANN page encoding remain unchanged. Opening an eligible predecessor upgrades its main metadata and [consolidates generation watermarks](diskann-key-value-generations.md#generation-allocation-retention) within the provider's existing atomic initialization transaction. The database identity, raw and historical records, transaction allocation watermark, unrelated identifier reservations, receipts, receipt capacity and any pending restore intent retain their original meaning; the maximum consumed generation number is preserved while obsolete per-index allocator rows are removed. An incompatible or incomplete schema fails without partial conversion.

Provider operations validate the current main format before accessing state, including retained snapshots and receipt retries. Upgrading a SQLite file therefore rejects both an older process reopening the file and an older session already holding a snapshot; that process cannot publish an unguarded vector write after the upgrade. redb admits only one physical database owner, so a predecessor process is rejected on subsequent open; retained handles additionally revalidate the format through the shared owner. The existing canonical guard proof then applies to every writer admitted by the new format, without inferring safety from record shape or an empty journal.

`scripts/verify-record-format-upgrade.py --old-ref fc4563f9 --offline` builds the actual predecessor and current adapters with each revision's pinned dependencies, reusing the configured Cargo target directory. Disposable native SQLite and SQLite Key/Value files exercise plain, encrypted, compressed and combined modes; a disposable redb file exercises exclusive-owner reopen. It verifies original records, revisions, database identity, commit sequence, pending/committed receipts and allocation state before and after upgrade, plus old-writer rejection. SQLite also exercises an already-open predecessor and its held snapshot. These are correctness checks, not performance measurements; no existing user database is involved.

The generation-allocation successor was additionally checked with an actual cached SQLite-format-50/redb-format-49 predecessor (binary SHA-256 `bc1be9fc13dfb0a724f7a217b48c8527f2726d3f9810dc28fc3f8e7c94ff123e`) in all nine configurations. This run linked the existing verifier driver against the exact five-package test artifacts instead of building another Cargo dependency graph. Fresh and retained predecessor operations rejected the successor, and original generic records, revisions and pending/committed receipts were preserved. Provider-owned tests separately verify the complete 130-row allocator fold, unrelated namespace preservation, maximum exhaustion and failed-upgrade atomicity; the generic binary probe alone is not DiskANN artifact-recovery acceptance.

The mapping-reclamation successor was checked with the PR #195 SQLite-format-51/redb-format-50 predecessor (binary SHA-256 `efcfd4606209507d247937244ae1a8a512446e659d46b38e4a6d59903452dfba`) in the same nine configurations, linking the successor driver against the verified five-package test artifacts. Cold predecessor opens and retained SQLite owners/snapshots reject formats 52/51; original generic records, revisions and pending/committed receipts survive. These checks establish the writer fence; shared mapping conformance and injected MVCC schedules establish the new reclamation protocol. Full DiskANN backup/restore acceptance remains separate.

## Representation

The Key/Value namespace is `\0uqa-diskann-changes-v1\0` followed by the existing canonical vector field prefix. Each fixed 40-byte suffix is a `DiskANNChangeIdentity`:

| Offset | Bytes | Meaning |
| --- | --- | --- |
| 0 | 8 | Document ID, big endian |
| 8 | 16 | Original writer history identity |
| 24 | 8 | Original writer allocation, big endian |
| 32 | 8 | Mutation revision, big endian |

The value is the existing fixed 56-byte [canonical origin envelope](diskann-canonical-origins.md#keyvalue-format), including dimensions and complete ordinal count. Unknown widths, zero allocation/revision and inconsistent current origin/count fail. History identity is preserved as data; this key format does not depend on restored record commit sequences.

### Native representation

Native mapping 12 adds object-owned family 59, `_uqa_mvcc_native_vector_changes(table_name, field, identity, origin)`. The `identity` BLOB is the same 40-byte change identity and `origin` is the same 56-byte envelope. Native record keys contain the stable table object/generation, field and ordered identity BLOB. The document remains inside that shared identity; native document IDs retain their existing nonnegative signed-64-bit range. Native row reads cap all four variable-width fields and their exact envelope before materialization.

Upgrade from mapping 11 preserves raw values, origins, the data namespace and existing record/receipt history while creating an empty journal. Earlier supported mappings also advance atomically. Failed upgrades restore the previous schema and guards. The current mapping rejects a predecessor writer's version check; missing tables/guards and changed layouts fail on reopen. Preserved origin-only data still needs explicit adoption before public query routing, and an empty journal is not a coverage claim.

## Retained enumeration

`RetainedDiskANNCanonical` retains vector, origin and change prefixes through one fixed provider read. `next_change_after` seeks the next document's journal range, validates that document's complete canonical ordinal set, and probes the exact key for its current origin. It returns that identity once, including an explicit empty replacement. Superseded mutations and deleted documents do not contribute. A cursor seeks past the entire preceding document range, so repeated historical mutations do not require a resident deduplication map or a scan of their values. The terminal document ID remains valid.

`RetainedSQLiteDiskANNCanonical` applies the same selection to one captured native object/field view. Its key cursor skips physical tombstones, decodes the shared identity and seeks past all historical identities for the preceding document. Current journal payloads must match the complete canonical origin/count on that same view; malformed keys, mismatched scope and oversized current rows fail. Original-source and invoking controls also apply to absent owners and terminal cursors.

Current change metadata must equal the retained canonical origin/count. Encoded point reads are capped before materialization. Original-source and invoking controls remain active on empty cursors and between seeks. Duplicate/out-of-order journal callbacks, missing change-value callbacks and suppressed consumer errors fail; temporary cursor buffers are released on failure. Callers obtain raw values and complete tensor scores through this same canonical source and the [canonical scorer](diskann-canonical-scoring.md).

Table and field cleanup removes the journal with canonical data. Rename and legacy-name migration move its namespace with the original identities. Retained readers keep their original journal and canonical boundary across those operations and undo. Ordinary non-DiskANN replacement invalidates the canonical origin, so populated unstamped data still fails instead of accepting a stale journal entry.

## Coverage and retention boundaries

This journal enumerates currently recorded replacements; it is not a build-coverage token. Atomic publication proves which actual committed/private origins the selected immutable generation covers and preserves late commits excluded from its capture. A missing journal entry cannot itself establish that a generation covers a document. Existing origin-only data requires explicit adoption, and incapable older writers require negotiation before public enablement.

One physical change record remains per successful mutation until the bounded pruner removes its exact key under the actual selected generation and catalog conditions. Complete published origins authorize covered-version deletion; the command’s committed canonical view independently establishes obsolescence. Private input cannot authorize cleanup, and a late uncovered current version remains journaled. Current-row deletion and retained MVCC history reclamation are distinct: older snapshots preserve their original journal view, while savepoint undo and original receipt recovery preserve evaluated cleanup. Mutable query integration, automatic finite journal pruning, exact captured byte/count accounting and threshold-driven graph rebuilding are implemented. Final physical metadata reclamation and complete recovery acceptance remain required; these paths alone do not establish a whole-runtime persistent-retention bound.
