# Owned notification listener preservation

This implementation boundary adds an independent Rust receiver over Engine's original notification hub. It implements the retained-listener portion of [SQL notifications and SSE](sql-notifications-and-sse.md); HTTP, runtime adapters, complete deployment-resource qualification and end-to-end startup/cleanup bounds remain separate obligations in the [fixed implementation ledger](../plans/0015-sql-notifications-and-sse.md). It introduces no retrieval, ranking or query-algebra operator.

## Ownership and observable state

An Engine creates a handle with `subscribe_notifications(channels, options)`. The handle retains the original hub, provider, backend, row-lock session namespace and selected authorization, without creating a SQL session or reopening the database path. Memory databases use their existing hub. Persistent listeners use the existing encrypted registry, original recovery backend and independently owned lease. Registration validates every exact channel before taking effect; SQL identifier folding and truncation do not apply to these API strings. A caller's open transaction, later role changes and low-level SQL queue remain independent of the new handle.

Each handle owns a fresh UUIDv4 epoch, a positive exact `u64` receive sequence and a bounded inbox. `poll` performs no database I/O. `wait` reports a value, a receive timeout or closure; elapsed receive time leaves registration intact. `next_event().await` waits on the same inbox through one executor wake slot without occupying a thread. Close wakes receivers before releasing the listener and retained provider resources. Registration and close may perform native provider I/O and must be placed outside an asynchronous runtime's event-loop worker. Controlled registration interrupts Engine gates and native registry lock/statement waits; operating-system file opening, provider construction already in progress, total cleanup bounds and complete language-runtime qualification remain separate obligations.

External Engine and subscription ownership is separate from the polling worker's temporary hub reference. The last external owner explicitly stops and joins polling before releasing its hub and provider fields. A worker cannot prolong its own authority by temporarily upgrading its weak hub pointer. Retaining an independent handle keeps this external ownership alive after its creating Engine closes. This ordering prevents storage or encryption work from continuing beyond the last owner's completed destruction; it is not a latency bound for native I/O already in flight.

Options specify positive active-listener, channel, queued-message, queued-byte and registry-scan limits. Pending registrations and retained listeners share the active-listener ceiling: the next admission must satisfy the minimum of every retained permit's ceiling and the proposed handle's ceiling. A failed registration releases its permit; a ready handle retains it through resource cleanup. Queue byte accounting includes string capacity, retained deque capacity, transient preparation vectors and replacement-buffer overlap. Fixed handle/channel/authorization/admission state, original registry/provider caches and application-owned values returned by polling are additional resources; the queue allowance alone is not a complete process-memory bound or a deployment default.

## Observation preservation

The asynchronous receive uses exactly the existing inbox poll transition under the same mutex. Its additional state is one pending-owner flag and at most one executor waker; it introduces no queue, provider read, timer or notification copy. A pending poll registers its waker before releasing the state mutex. Publication and termination change that same protected state before taking and waking the registered task, so a racing receive either observes the change or has a waker available to the producer. Taking the waker does not release the pending-owner flag: another asynchronous receive is rejected until the first receives its result or is dropped. Waker replacement, wake callbacks and destruction occur outside the mutex, permitting an executor to reenter safely. Dropping a pending future clears only its wake registration; it cannot consume a queued value or unregister the listener.

Erase the pending-owner flag, waker, poll suspension and wake transitions from an asynchronous execution trace. Each remaining receive transition is the original inbox poll, with the same returned value, sequence and terminal result. Therefore the resulting trace is an allowed synchronous receive trace and inherits the ordered observation proof below. Cancellation of a still-pending future erases to the identity transition on the notification history. This argument assumes callers serialize consumption of one handle; synchronous polling must not compete with an asynchronous consumer. A second pending asynchronous receive returns `InvalidRequest` without changing the original receive or listener.

`stop_delivery` closes the inbox and wakes receivers without touching provider resources. The original registration, provider references and admission permit remain retained until `close` completes their existing cleanup. Consequently an adapter may wake a pending receive before scheduling native cleanup without admitting a replacement listener too early. The signal is not itself a cleanup-completion boundary.

Let $T$ denote the totally ordered committed notification entries already produced by the SQL implementation, including its transaction-local duplicate suppression. Let $b_i$ be the effective registration boundary of handle $i$ and let $C_i$ be its fixed set of exact channels. The intended live observation before any terminal failure is the ordered subsequence $O_i = [t \in T \mid t \geq b_i \land \operatorname{channel}(t) \in C_i]$. A fresh handle has an empty inbox and starts its source cursor at the hub's committed head, so it cannot observe entries preceding $b_i$. Registry admission commits all channels as one listener row, while the common commit gate prevents local publication from observing a partially installed listener. The native registry writer supplies the corresponding ordering against another process.

For memory delivery, the hub traverses committed entries in source order, copies only matching values into the handle's own inbox and advances that handle's cursor to the observed head. For persistent delivery, the provider visits one bounded ordered prefix from the retained cursor. Each visited row advances physical page accounting through Storage's existing alignment operation; a nonmatching row advances the source cursor without allocating an output value. A matching row first reserves its event count, eventual destination capacity and private delivery storage. Its copied value remains unpublished until the transaction containing the new durable cursor commits. Aborting the transaction drops the private batch and releases its reservations, leaving the original durable cursor unchanged. Consequently a failed preparation cannot expose an event or consume its source entry.

Induct on accepted source prefixes. The empty prefix yields the empty observation. A nonmatching next entry leaves the output unchanged; a matching next entry appends precisely that original value. Commit publishes exactly the prepared suffix, and abort publishes no suffix. Therefore each successful step preserves $O_i$ and source order. A missing source entry or provider failure terminates visibly rather than silently advancing across a gap. A count or byte admission failure terminates the affected handle with backpressure rather than silently discarding an event while continuing the stream. No other handle shares its cursor or consumes its inbox, so polling or closing one handle cannot remove another handle's observations.

A failed cursor commit publishes no private batch and terminates each affected independent receiver even when a SQL caller, rather than the background worker, initiated consumption. This failure does not assume that a storage commit error proves rollback. The original SQL error is preserved for the initiating caller and cloned with all diagnostic fields into the explicitly inspected subscription cause; neither event diagnostics nor the stable subscription error code expose that cause implicitly. SQL error cloning copies the same variant and fields without reevaluation, so its values and SQLSTATE are unchanged.

The emitted metadata counter is assigned under the inbox lock: event $j$ receives sequence $j$, starting at one. Checked addition emits the maximum `u64` once and then terminates instead of wrapping. Erasing identity and sequence recovers the original `SQLNotification` value exactly. Thus the representation extension preserves the existing shared-value erasure law, text, process identity and order; UUID freshness names a registration rather than asserting durable replay or exactly-once delivery.

## Resource and transaction preservation

Let $Q_i$ be published queued events, $R_i$ be private delivery reservations, $N_i$ the event limit and $B_i$ the byte allowance. Under the inbox mutex, admission checks $|Q_i| + R_i < N_i$ before adding one reservation. Commit moves an existing reservation into $Q_i$ without increasing their sum; abort releases the reservation; polling removes one member of $Q_i$. By induction, $|Q_i| + R_i \leq N_i$ holds for every live handle. Byte reservations are shared across published and private buffers; all growth is admitted before copying, and a buffer's charge remains alive until its allocation is freed or transferred. Therefore charged retained/transient queue capacity never exceeds $B_i$. This is an allocation-accounting argument, not an RSS or latency measurement.

For admission, let $A$ count retained permits, including pending registrations, ready handles and cleanup still in progress, and let $L$ be the minimum retained/proposed ceiling. A separate metadata mutex serializes pruning expired weak records and inserting a permit; contention rejects admission before creating another waiter. Registration acquires a permit only when the recorded count is below $L$. Expired records racing with inspection can conservatively reject capacity but cannot undercount a retained permit. Inserting a permit yields $A + 1 \leq L$; transitioning from pending to ready keeps that same permit; final destruction only decreases $A$. No provider call or other Engine gate is entered while holding the metadata mutex. Therefore admitted waiters and ready listeners together remain within the selected ceiling, without tying idle subscriptions to SQL concurrency. Legacy SQL listeners retain their existing SQL queue rules and are not silently reclassified as high-level subscriptions.

Existing SQL producers still own evaluation, transaction-local duplicate suppression, outer commit and rollback. The new receiver consumes only their committed effects. Its backpressure failure neither rolls back a committed producer nor changes the receiver's caller transaction. Relational, posting, graph, score and ranked-result carriers are untouched, so existing UQA compositions retain their domains, codomains and observations. This argument does not grant optimizer rewrites over notifications: notification publication remains an ordered transactional side effect.

## Native registry cancellation

Controlled registration and recovery reuse the already established [SQLite cancellation boundary](notification-registry-cancellation.md). That provider proof supplies native callback ownership, typed cancellation, rollback, moved/nested operation preservation and authoritative publication completion. Engine contributes the retained original control and its admission/gate ordering below; it does not implement native lock retry or replay evaluated publication. The provider boundary does not establish interruption of operating-system file opening or encryption-key initialization already in progress, a total registration/close deadline or a complete process-memory profile.

## Controlled Engine registration

`Engine::subscribe_notifications_with_cancellation` accepts a separate registration signal. It validates the input and reserves capacity before waiting for the statement gate, selected authorization, coordinator/registry initialization state, recovery state, hub commit gate or hub listener state. Timed native mutex waits recheck that same signal. The existing statement-gate delegation and same-thread reentrancy rules are preserved; unrelated SQL cancellation neither stops this listener nor gets reset by registration. Native registry admission and commit reuse the original recovery allowance with the registration signal, while the long-lived recovery owner keeps its independent cancellation authority.

The listener's cleanup owner is constructed only after successful all-channel registration. Earlier failure drops the private inbox, original native attempt, any new listener lease and admission permit; it does not run `unregister` on an unregistered session or acquire the same blocked gate during error cleanup. A registration identifier alone owns no row locks or session resources. For memory registration, insertion under the retained commit/state gates supplies the boundary. For native registration, successful registry commit supplies it, followed by local installation while retaining the same commit/state gates. No fallible cancellation check follows that commit. Thus cancellation observed before the boundary returns no handle and no partial listener; a successful boundary that wins the race returns its ready handle and preserves the observation sequence already proved above.

After readiness, the registration signal does not become a hidden subscription lifetime limit. The application or runtime adapter closes the owned handle to cancel its active lifetime. Initial provider-session construction still retains its original independent authority and is checked before publication into recovery state; it is not made permanently dependent on a transient request signal. Native construction already executing remains synchronous, so the timed gate interval is a cancellation polling granularity rather than a claimed end-to-end deadline.

### Capacity before runtime submission

`reserve_notification_subscription` returns an opaque, non-cloneable `NotificationSubscriptionPermit` using the same hub allowance as synchronous registrations and live handles. It waits on no Engine or provider gate. `subscribe_notifications_with_permit` consumes that reservation and its immutable options instead of reserving a second slot. The permit contains a weak reference to its original hub; pointer equality rejects another hub, even after the original Engine is destroyed and a pathname or allocation would otherwise be reused. A permit neither retains the Engine nor conveys role authority: adapters retain their original Engine separately, and registration still reads its actual selected authorization under the existing gate. Dropping an unused permit only releases metadata ownership, with no provider I/O.

Let $P$ be reserved registrations before runtime submission, $W$ submitted/running registrations, $R$ ready subscriptions and $C$ cleanup in progress. Each element of their disjoint union owns exactly one original permit, so $|P|+|W|+|R|+|C|=A$. Reservation is the previously proved checked insertion; scheduling moves one member from $P$ to $W$, readiness moves it to $R$, and close moves it to $C$, all without changing $A$. Failure, abandoned input destruction and completed cleanup decrease $A$. Opaque construction and by-value consumption prevent duplication or a second reservation during transition. Thus the same $A\leq L$ invariant covers an adapter that reserves before submission and retains exactly this permit through registration and cleanup. The permit API supplies that ownership boundary; actual Node and Python adapter qualification remains separate. No language-local counter may replace or weaken the original hub's ceiling.

This preparation changes only admission timing. It does not create a listener or set its effective history boundary; successful native registration still supplies $b_i$ and the same $O_i$ proved above. A full allowance may reject an asynchronous factory before a worker runs. Native validation checks cancellation before allocating its bounded borrowed-name set and between names; set membership replaces repeated prefix scans while preserving exact name equality and rejecting duplicates. Count and positive-option checks bound this workspace by explicit channel limits. These invariants cover retained direct submissions, not runtime pool overhead, unrelated HTTP owners, provider caches or an operating-system latency bound.

## Global listener metadata and local channel ownership

The [provider read and summary proof](notification-registry-metadata.md) establishes that SQLite's `listener_metadata_after` returns one fixed-width record in exclusive primary-key order, without selecting or decoding `channels_json`. Its statement ends before the caller receives that record, so removing a dead listener and seeking past its original key cannot invalidate a live SQLite cursor. The original registry transaction and cancellation signal remain retained. Engine supplies its existing local lease identities, probes remote liveness and passes surviving metadata to common Storage's `NotificationListenerSummary`. Only an individually selected local listener loads channels. An expired high-level inbox is removed without falling back to legacy session materialization.

Let $L$ be the surviving listener records after the current transaction's local changes, with immutable key $k=(\mathrm{owner},\mathrm{session})$, cursor $s$, byte position $p$ and wake port $w$. Define $S(L)=(\min_{l\in L}s_l,\operatorname{argmin}_{l\in L}(p_l,k_l),\bigcup_{l\in L,\,l\text{ remote}}\{w_l\})$, with absent minima and an empty port set for the empty input. Combining summaries takes minima and set union. These operations are associative and have the empty summary as identity, so induction over the ordered single-row reads gives exactly $S(L)$ without retaining $L$. The next exclusive key is recorded before deletion; every subsequent key is strictly greater, and no unrelated key changes within the retained transaction. Thus deletion neither repeats a record nor skips its successor. The minimum position and key preserve the previous ordered scan's choice among equally old blocking transactions.

Delivery persists each accepted local cursor, or removes its closed row, before the final summary is built. Queue reclamation therefore deletes precisely the entries strictly below the final minimum cursor, using the queue head only when $L$ is empty. Queue capacity and warning calculations use the same minimum position; publication without listeners still retains its identity while emitting no queue entries. A bit for each of the $2^{16}$ possible ports represents the exact union; setting a bit is idempotent and iteration emits each selected port once in ascending order. The bitmap contains 1,024 `u64` words (8 KiB) when allocated, independent of remote listener count. These changes leave committed notification values, transaction deferral, independent receiver histories and the existing decoration/erasure argument unchanged; they introduce no query or scoring operator.

For a high-level local lookup with channel limit $M$, the provider rejects encoded JSON longer than $B=2+M(6\cdot63+3)$ bytes before constructing channel strings. This contains two array brackets and an upper bound for each channel's quotes, separator and worst-case JSON escaping of its 63 UTF-8 bytes. The array visitor admits at most $M$ strings, rejects a decoded string longer than 63 bytes, and rejects an excess element before decoding it. Its one fallible header reservation is at most $\min(M,\lfloor B_{\mathrm{actual}}/3\rfloor+1)$; any valid string array fitting the actual input has no more elements than this bound. Decoder scratch and a rejected current string are bounded by the encoded input. Explicit legacy session reads retain their existing caller-owned materialization boundary.

The global fold keeps one metadata record, one summary and the process's existing local owner list; it retains no per-remote-listener vector or channel strings. It still performs one indexed seek and one liveness decision per registry row, and native SQLite pages, caches, local legacy queues and runtime overhead have separate resource boundaries. Cancellation is checked around each provider operation. A constant-size returned record does not establish a fixed duration for an entire pass, an operating-system I/O deadline or a complete process-memory envelope; those remain part of integrated qualification.

## Cleanup completion and recovery shutdown

Closing the inbox ends delivery and wakes waiting consumers before provider cleanup starts. The resource mutex remains held through listener removal, row-lock release and destruction of the retained hub/provider/admission owners. Let $R$ be the optional resource owner and $G$ that mutex. Taking $R$ out of its slot does not establish completed cleanup: that owner may still hold leases or be joining recovery. A close operation returns only after destroying its extracted owner while holding $G$. Every concurrent close must subsequently acquire $G$, so its return follows the same destruction even when it finds an empty slot. Thus idempotence preserves the cleanup-completion boundary rather than merely the delivery-closed flag. The existing admission permit remains retained throughout destruction.

The last external hub owner cancels the recovery owner's independent signal before waking and joining its one polling thread. The signal is installed in the retained recovery control when that session is created; it is never reset or replaced by a query's cancellation. Native registry admission, recovery reads, cursor commit and the polling path's Engine gates observe that same signal. Error propagation also uses cancellable gates, so shutdown cannot leave the worker waiting again to record the cancellation it just observed. A nonblocking accept loop is awakened with the retained thread's unpark operation and rechecks cancellation before accepting more work.

Before a successful cursor commit, cancellation rolls back the original private attempt and drops its unpublished deliveries. Successful commit retains its outcome; an optional diagnostic clear does not reclassify it as failed if shutdown races afterward. Authoritative SQL publication still uses its existing completion operation, unchanged by this cursor-control boundary. Already committed source intent remains recoverable by its existing immutable fingerprint. Therefore this shutdown policy changes task lifetime without changing committed notification triples, their order, SQL duplicate suppression or the observation-erasure law above.

An individual handle closes only its listener. Other Engine and subscription owners keep the hub's external owner alive, so closing one does not cancel their shared recovery signal. The last external owner joins recovery before its retained provider fields are released; the worker's temporary internal hub reference cannot extend its authority past that join. These statements assume ordinary scheduler and operating-system progress. They do not establish a measured cleanup duration or an operating-system deadline for lease-file and provider destruction; complete adapter cleanup budgets and provider/file-lifetime qualification remain required.

### Native lease retirement

Independent-handle cleanup removes its local listener under the existing commit/state ordering and destroys its unique native liveness lease before releasing provider references and admission. It performs no shared-registry transaction. This removes a dependency in which another registry writer could retain a closed subscription's resources until its own transaction ended. Ordinary SQL session unregistration retains its existing transaction path. Registration, publication, queue-usage and recovery scans already test native lease liveness and reap dead registry rows before including their cursors in live-listener summaries. A completed local close therefore releases owned resources while remaining database metadata is collected by the next such operation.

For a listener $s$, let $L_s$ mean that its unique native lease is held, and let $Q_s$ be its registry row. A row is live only if its lease remains held or the same owner is retained in the observing process's local owner set. Retirement removes that local owner while holding the commit gate, then releases $L_s$. No subsequent local publication can install the old listener after that boundary. A remote operation that already observed $L_s$ may finish its earlier snapshot, but it cannot recreate the unique lease, and the next liveness scan excludes $Q_s$. The closed inbox prevents any later observation by $s$. Thus delaying physical deletion of $Q_s$ cannot add a notification to the retired listener's history, remove another live listener, or change transaction-local duplicate suppression.

No per-retirement task, pending-work list or new allocation is retained. Every successful registration already scans and removes previously dead rows before installing its own row, so repeated registration/close cycles cannot accumulate a row per historical subscription. While another writer holds the registry, successful new registrations cannot commit; local close still releases its lease and capacity. Existing queue retention remains governed by live cursors on the next registry operation. Tests hold a real registry writer through the close-completion observation, verify released native leases and reusable admission, and verify that ordinary publication/registration subsequently removes the obsolete rows. Final-owner tests additionally observe the original provider/backend weak references disappear after the recovery worker is joined across all seven native provider configurations.

## Retained native SQLite source

The already established [SQLite source-preservation boundary](sqlite-retained-source.md) freezes the selected native source and rejects observed file replacement or loss. Engine retains that same registry/provider owner through registration, recovery and cleanup; it neither substitutes a new pathname nor changes credentials on a provider failure. Source failure terminates the independent inbox as `SourceUnavailable`, with the original cause available only through explicit private inspection. Cleanup keeps its original leases. This composition cannot present replacement-source notifications as a continuation of the original history. Separate-process/provider/platform lifetime and complete cleanup/resource qualification remain obligations in the implementation ledger.

## Receive-timeout preservation

Receive waiting subtracts elapsed monotonic time from the supplied Rust `Duration`, with saturation at zero. For timeout $\tau$ and elapsed time $e$, each unfinished wait retains $\max(\tau-e,0)$; a spurious wake cannot restart or extend that budget. No absolute deadline addition can overflow before an available event, explicit close or retained source error is observed. The existing condition variable supports a relative duration beyond the platform's absolute instant range, including `Duration::MAX`, and publication or close still wakes it. A receive timeout leaves the listener registered. Tests cover zero and finite timeouts, the maximum duration, queued values, close and original terminal failures.

## Verification obligations

The inbox tests exercise unpublished preparations, abort release, count and byte exhaustion, close during preparation, timeout versus closure, independently observable terminal errors, private-diagnostic redaction and exact full-width sequence boundaries. Public API tests exercise memory isolation, overlapping channels, old-history exclusion, SQL queue independence, transaction/savepoint duplicate behavior, selected `NOLOGIN` role identity, capacity and slow-consumer isolation. Persistent tests require the actual SQLite, SQLite Key/Value, redb, compressed and encrypted providers, short scan prefixes including nonmatching rows, caller transaction isolation and delivery after caller destruction. Test execution and remaining lifecycle/provider qualification are recorded in the implementation ledger rather than inferred from this argument.

The existing SQL session expectations are checked against the independently captured [PostgreSQL 18.4 session transcript](../../tests/parity/pg18/notification_session_oracle.expected.txt) and [rule/transaction transcript](../../tests/parity/pg18/rule_notify_oracle.expected.txt). These establish committed delivery, transaction deferral, duplicate suppression and rollback boundaries; the additional owned handle preserves those producer histories while supplying its independently registered projection. The isolated Engine notification selection exercises both existing SQL scenarios and the new direct API. It does not establish a new PostgreSQL run, an HTTP server or language artifact.
