# Stateless SQL notification policy

This implements the SQL execution boundary of the [notification/SSE design](sql-notifications-and-sse.md). The [Rust API contract](../manual/reference/02-rust-engine-api.md#notification-policy-for-stateless-sql-hosts) describes host configuration. The actual HTTP server must configure each request session before execution and map the typed error; this boundary alone does not implement or qualify that endpoint.

## Ownership and state

SQL owns the typed `SQLError::NotificationRequiresSubscription`, its stable application code `NOTIFICATION_REQUIRES_SUBSCRIPTION`, SQLSTATE `0A000`, and parser-node classification of direct `LISTEN`/`UNLISTEN`. Execution owns admission and actual command dispatch. Engine retains one nontransactional, monotonic session flag and supplies it through its existing execution adapters. No HTTP dependency, reverse crate dependency, SQL substring scan or eager compilation of a routine body is introduced.

`require_notification_subscriptions()` holds the session statement gate. Initial configuration requires no active SQL execution, transaction or committed SQL listener; otherwise SQLSTATE `55000` leaves the policy unchanged. A successfully configured session cannot enable SQL listening again, including through rollback or `DISCARD`. Nested/portal workers share its session context, and subsequently created sibling sessions copy its restriction. Existing independent peers retain their own policies. Independently owned notification handles and outgoing transactional notifications remain available.

## Preservation argument

Let $S$ denote the existing SQL state, including transactional catalog/data, pending notification publications, pending SQL listener changes and committed listener state. Extend it with a host policy $p\in\{0,1\}$, where $p=1$ requires independently owned subscriptions. Let $L$ contain exactly the compiled `LISTEN` and `UNLISTEN` commands, and let $T_c$ be the ordinary transition for command $c$ with its existing rollback behavior and the original error retained by bare `RAISE`. The restricted dispatch is

$$
T'_c(S,p)=\begin{cases}(\operatorname{reject}_{\mathrm{subscription}}(S),p),&p=1\land c\in L,\\(T_c(S),p),&\text{otherwise}.\end{cases}
$$

The rejection creates no listener effect and enters the original statement failure boundary. Therefore a failure rolls back precisely the original statement/subtransaction scope; it does not undo nontransactional effects or preceding explicit commits. If a SQL exception handler deliberately catches SQLSTATE `0A000`, its original subtransaction rollback and handler execution remain valid, while the rejected listener was never registered. Bare `RAISE` retains the original typed cause and all diagnostic fields; it cannot erase the application code or infer it by parsing a message. Retaining the cause also corrects the earlier conversion of every caught error to a generic `Routine` error: SQLSTATE and primary message remain identical, while typed causes and separate detail/hint fields now survive. The baseline $T_c$ includes this diagnostic-retention correction. `SQLError`'s derived clone preserves each variant and each owned field, and the handler still exposes the same independently retained SQLSTATE/SQLERRM pair.

For $p=0$, erasing the added policy yields the original transition for every command, so induction over a finite command trace preserves every value, state effect, completion and failure observation. For $p=1$ and every executed command outside $L$, the same induction holds. In particular, `NOTIFY` and `pg_notify` retain their original pending-publication accumulation, duplicate suppression and commit/rollback boundaries. The policy does not read or rewrite notification payloads, ranked values, document support or query algebra operators. Thus existing carrier domains, operations and applicable identities/associativity/composition laws are unchanged on admitted executions; no new optimizer rewrite or approximate equality is asserted.

For a directly submitted batch $B=(c_1,\ldots,c_n)$, admission under $p=1$ rejects before executing any $c_i$ if a direct parser/retained AST node belongs to $L$. This is an explicit host admission rule, not an equality claim between partial execution and rejection. Each message's syntax parsing precedes admission, but semantic lowering still occurs at each original statement boundary. Consequently preceding DDL and settings can affect later admissible statements as before. An API batch checks every submitted SQL message inside its existing transaction wrapper before its first SQL statement, so rejection rolls back that wrapper's scope and preserves the caller's outer transaction. A simple-query message checks all direct nodes before the first result callback or SQL transaction boundary. This prevents even nontransactional sequence consumption by a batch already known to require a persistent listener. The bounded cursor/columnar entry also rejects direct listener commands before reporting a query-shape error and retains nested dispatch checks for function calls.

Routine bodies, dynamic SQL, cached plans, prepared queries, triggers and portal workers remain subject to the live dispatch guard when their commands actually execute. A definition containing listener SQL can be stored without being executed. Since the flag cannot change from $1$ to $0$, snapshot restore, cache reuse and nested entry cannot regain the forbidden transition. These facts establish the execution restriction and preservation argument; HTTP authentication, wire errors, cancellation and transport qualification remain separate requirements in the [implementation ledger](../plans/0015-sql-notifications-and-sse.md).

## Verification scope

SQL parser tests distinguish direct commands from comments, literals, payloads and unevaluated bodies. Execution tests require direct and cached admission to precede transaction work, context capture, optimization and result callbacks. Actual Engine cases cover memory and native persistent sessions, nontransactional sequence effects, dynamic and compiled nested commands, prepared queries, triggers, portals, typed rethrow, catch/rollback, session inheritance and ordinary transactional publication. Independent PostgreSQL 18.4 execution confirms that ordinary SQL/PLpgSQL functions and cursors permit notification commands and that nested bare `RAISE` retains SQLSTATE/message; the policy is enabled only by the embedding host and changes no ordinary PostgreSQL-shaped session default.

The independent PostgreSQL reference uses version `18.4 (Debian 18.4-1.pgdg13+1)`. Its compact provenance is SQL input SHA-256 `a22e87dfe1b77aedbad26d42d7a0bfbe42fb3eb1027c0e382ace677a98f97d77` and captured output SHA-256 `7adf1ba2e8a132f09433b225a4cf2d3bb1f9e533b62b3b3d976f274612934226`. The existing Engine cases execute those function, prepared-query, cursor and nested-rethrow boundaries; the reference capture is not a new measurement or a test dependency on a machine report.
