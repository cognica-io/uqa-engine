# DiskANN physical generations

The Storage-owned `KeyValueDiskANNStore` persists physical DiskANN generations through existing versioned Key/Value sessions. SQLite Key/Value, redb and native SQLite share staging, physical sealing and retained page sources. Bound canonical sources use the [generation publication contract](diskann-generation-publication.md) to select a sealed generation and its complete coverage atomically; the [bounded journal pruner](diskann-journal-pruning.md) consumes that coverage under the same provider transaction. [Query generation selection](diskann-query-generations.md) retains committed and private physical sources with the canonical view. Merged runtime integration connects candidate merging and SQL creation. The existing worker schedules automatic journal pruning and [graph rebuilding](diskann-maintenance-capture.md#automatic-reconstruction); complete retention acceptance remains unfinished.

## Ownership and identities

`connect` requires a versioned provider, an independent session with the same transaction-history and persistent-provider identity, durable identifier allocation, authoritative resource leases, and retained reads. It opens a dedicated staging session and probes retained-reader affinity before initialization writes. No caller SQL transaction is committed or rolled back by the repository. Clones share a short staging-operation mutex; graph stream validation releases that mutex and all provider guards between reads.

An initialized 16-byte data identity is distinct from the provider's transaction-history identity. Autonomous identifier allocation reserves generation numbers from one database-wide watermark, independent of table/index churn. Allocation survives rollback and cleanup, so a consumed generation number is never reused. The low-level physical API accepts nonzero 64-bit table/index handles. `allocate_bound_stage` instead obtains those handles from durable mappings of a retained canonical source's full 128-bit catalog incarnations; it never truncates or hashes an object identity.

`index_scope` resolves the stored index identity from the canonical source's fixed catalog view. Execution's `DiskANNIndexIdentityResolver` invokes the existing SQL definition decoder and validates the index against the captured table object. Storage retains the actual table object, storage generation, resolved index object, exact record history and original controls. Native SQLite supplies its captured native row; SQLite Key/Value and redb supply their retained catalog record. Missing definitions, zero identities, foreign history and cancellation fail explicitly. A scope is preparation evidence: the source's current-definition guard is still required at publication.

The table mapping keys the complete table object and storage generation; the index mapping adds the complete index object. Both mappings are inside the existing physical provider and use its durable, non-reused allocator. Names do not participate, so renaming preserves a handle and recreating an index with another object identity does not. Bound allocation publishes mappings and its first Writing generation state in one lease-owned evaluated batch; an explicit later `start` is idempotent. Competing creators retry only definite rejected metadata conflicts, consuming fresh identifiers; an unknown outcome retains its original attempt and lease for explicit completion. Allocation opens no caller transaction and never completes one. Unused mappings left by private definition rollback are reclaimed after their last physical generation, as described below.

## Persistent namespace

The binary root is `\0uqa-diskann-v1\0`. The database marker uses root plus tag 0, with value revision 1 followed by the nonzero 16-byte data identity. A generation prefix is root, tag 1, data identity, table incarnation, index incarnation and generation number; its three integer components use big-endian 64-bit encoding.

Root tag 2 followed by the data identity, 16-byte table object and 16-byte storage generation addresses a table-handle mapping. Root tag 3 adds the 16-byte index object and addresses an index-handle mapping. Each value is exactly nine bytes: revision 1 and a nonzero big-endian `u64` handle. Root tag 4 plus the data identity is the allocator namespace for these handles. Generation allocation uses `\0uqa-diskann-generations-v1\0` in the existing physical identifier table; mapping and generation identifiers have independent watermarks.

Root tag 5 remains the selected-head namespace, keyed by the complete catalog identities without the data identity. Tags 6 and 7 address table and index preparation guards using the corresponding mapping key suffix, including the data identity. Their values are exactly eight bytes: the nonzero big-endian reserved generation number. Every bound preparation updates the index guard; creating an absent index mapping also updates the table guard. Immutable mapping bytes and their revisions remain stable across later preparations, so an unrelated build does not invalidate an existing publication's observed mapping requirements.

| Suffix after generation prefix | Value |
| --- | --- |
| Tag 0 | Fixed 18-byte state: revision, status, nonzero 16-byte staging owner |
| Tag 1 | Encoded manifest |
| Tag 2 | Encoded PQ codebook |
| Tag 3 + big-endian 64-bit first node | Independently addressed encoded code batch |
| Tag 4 + big-endian 64-bit first position | Independently addressed encoded numeric-side batch |
| Tag 5 + big-endian 64-bit page ID | Exactly 4,096 encoded graph-page bytes |
| Tag 6 + big-endian 64-bit first document position | Complete encoded document-origin batch for manifest revision 3 |

Unknown tags, extra key bytes, unsupported state revisions and absent required records fail closed. The existing [generation](diskann-generation-format.md) and [page](diskann-vector-index.md#node-and-page-encoding) codecs own payload validation. Metadata, staging records and pages remain inside the original provider's encryption and backup domain; no sidecar payload files or unrelated SQLite connections are opened.

## Generation allocation retention

A generation reservation survives rollback, failed construction and DROP. Keeping one watermark per historical index therefore grew the physical identifier table without a bound from live indexes. Storage now reserves every new generation from one nontransactional database-wide watermark. Generation keys still include the unchanged data identity, table/index handles and generation number; generation records and page encodings do not change. Reservation exhaustion is an error and never wraps or rewinds the watermark.

SQLite main format 51 and redb main format 50 atomically consolidate predecessor reservations during their existing initialization transaction. The common Storage domain descriptor identifies exactly root/tag 1 plus a 16-byte data identity and two 64-bit handles; shorter/longer keys and other allocator domains are not selected. Each provider scans and removes at most 64 selected namespace keys per cursor page, folding their maximum with any existing global watermark. The whole conversion, including the new format marker, commits together. Fixed stack scratch bounds the cursor's owned memory independently of the number of dropped indexes; physical page caches and the initialization transaction retain their provider ownership. This is one atomic upgrade, not a series of independently committed pages.

Let $w_i$ be each predecessor watermark and $w_g$ an existing global watermark, treating an absent watermark as zero. The atomic conversion establishes $M=\max(\{w_g\}\cup\{w_i\})$ before deleting any predecessor domain durably. A successful new reservation returns $g>M$ and advances the same independent allocator; concurrent reservations serialize under its existing physical writer. Induction therefore gives a strictly increasing sequence of future generation numbers, each greater than every number consumed before conversion. If $M=2^{64}-1$, reservation fails without changing state. An interrupted upgrade exposes either the complete predecessor format and watermarks or the complete successor format and maximum, never a reusable number between them. The format fence excludes predecessor allocators, including already-open SQLite owners.

Custom versioned providers may retain predecessor watermarks. Storage reads the selected index's legacy watermark and uses its checked successor as the global reservation minimum, preserving that index's nonreuse invariant even without a built-in provider migration. Such providers must independently exclude incompatible predecessor writers before admitting the new allocator; this fallback is not a format fence or a claim that their old rows have been reclaimed. New allocations never create another per-index watermark.

The conversion changes allocation metadata only. It preserves data/history identities, generation keys, head selection, raw vectors, page bytes, transaction receipts and snapshot boundaries. Existing search inputs and canonical scores therefore stay identical; future builds differ only in fresh physical identities and preserve the same ranked-result and composition contracts. The global generation watermark and physical-handle allocator remain retained to prevent reuse. Table/index handle mappings and final MVCC head tombstones follow the separate reclamation protocols below; allocation consolidation alone does not establish the complete physical metadata bound.

## Staging and physical sealing

`allocate_stage` returns the reserved generation and its owner before `start` attempts any state write. The caller retains that identity even when creation loses its commit reply. `resume_stage` requires existing state and retains the original repository owner or exclusively claims an abandoned owner; it cannot create an absent generation. A handle that attempted creation or cleanup cannot recreate its namespace after removal.

| State | Permitted action and next state |
| --- | --- |
| Writing | Append absent record/page keys; atomically write the manifest and move to Frozen; discard |
| Frozen | Read and verify complete physical streams; move to Sealed only after successful verification; discard |
| Sealed | Open retained sources and verify repeated sealing requests against the same manifest |
| Discarding | Continue bounded deletion until the namespace and state are gone |
| Published | Remain selected by the logical head; atomically become Retired when a verified replacement publishes |
| Retired | Keep retained readers valid; begin bounded committed reclamation and move to Discarding |

Each append requires the unchanged database marker and staging-state revision at commit. Freezing changes the state revision, fencing even writes evaluated before freezing. Records cannot be replaced through the staging API. Verification scans at most 64 fixed keys per page, releases the key visitor, copies one bounded record or graph page, then invokes the common artifact sealer. It validates every ordered code/side/page stream and its final digest. Revision-3 generations additionally require complete ordered origin batches, including empty tensors, and matching total tensor cardinality and digest. All logical origin records use the same native binary mapping and encryption domain; no native family or schema change is needed. An incomplete or corrupt generation remains Frozen and unavailable to ordinary readers.

The final Sealed transition conditionally requires the original owner, Frozen state and unchanged manifest. Sealed means complete physical artifacts; bound publication additionally validates exact captured coverage, catalog parameters/incarnations, expected head and physical mappings. Public query routing and SQL lifecycle integration remain separate obligations.

`discard_step` accepts a positive record count capped at 64. It fences later writers and deletes at most that many payload records in one atomic mutation, retaining Discarding until the final empty/partial page removes the state. Cleanup is explicit and resumable, never a fallible destructor operation. Sealed-generation reclamation is rejected: failed verification, an absent head or elapsed time does not establish abandonment.

## Committed generation reclamation

`reclaim_retired_step` uses the dedicated physical session and accepts only a committed Retired or Discarding state. A positive caller limit is capped at 64 payload records. It selects only fixed-size keys, validates their generation and ordering, fences the unchanged data marker and state revision, and evaluates exact deletions in one batch. A full page leaves Discarding; an empty or partial final page removes the state after its payloads. A missing state is complete only when no current generation key remains. Repetition is idempotent, and a new physical session resumes from the durable Discarding state without an in-memory cursor. The same deletion routine serves an owner's explicit unsealed discard.

Committed retirement establishes the necessary reachability invariant: the publication or retirement transaction removed the selected head or installed a different generation in the same atomic batch as Published-to-Retired. Publication accepts only its originally observed Sealed state, so no later successful publisher can select a generation that reached Retired or Discarding. Every append, seal and cleanup uses the state precondition; a competing stale evaluated operation cannot recreate a consumed generation. Consequently deleting current payloads changes no newly selected query's physical support. A prior reader retains its original MVCC view, including private publication's actual sealed source, and continues reading historical bytes until its final lease is released. Provider history reclamation enforces that lease boundary independently of current-row deletion.

Cleanup retains the provider's original receipt semantics. An uncertain attempt blocks further operations on that repository until `commit_pending` or `rollback_pending` resolves the exact evaluated bytes; no deletion callback is replayed to reconstruct an outcome. Cancellation, quota exhaustion, corrupt key completion or a precondition conflict aborts the whole current batch. The key workspace is bounded and released after each step; no graph, PQ or side payload is loaded to decide which key to delete. Historical payload release and the provider's head tombstones are separate from removal of current generation records. Current mapping and physical tombstone reclamation follow below; complete recovery acceptance remains unfinished. Unpublished recovery additionally follows the resource-ownership contract below.

## Finite generation maintenance

`KeyValueDiskANNMaintenance` discovers generations on one retained committed snapshot captured at startup. A key-only seek returns at most one state key; the next seek starts beyond every valid record tag of the previous generation, without traversing its payload keys. The cursor stores one generation identity and keeps no identity directory. State-key length, data identity, ordering and completion bounds are checked, including visitor errors suppressed by a faulty provider. A malformed or orphaned first record aborts discovery without deleting it.

Discovery supplies candidates, not deletion authority. Every step independently examines current committed state using the existing reclamation owner. Published generations and live build/source/recovery leases are retained; Retired, Discarding and exclusively acquired abandoned builds use the existing 64-key deletion bound and exact state/data guards. Retained generations advance the cursor so they cannot prevent reaching later candidates. Partially deleted generations remain current until complete. Errors preserve the cursor and original evaluated attempt; `commit_pending` and `rollback_pending` resolve that attempt without replaying its callback.

The startup snapshot contains finitely many records. Each completed or retained candidate advances strictly beyond its generation; each successful partial deletion removes at least one bounded page from an append-fenced generation. Therefore a successful pass finishes even while other sessions keep creating generations. New identities, including identities sorting before the current cursor, are considered by the next pass. Concurrent publication or recovery cannot gain authority from an old discovery snapshot: current state, physical ownership and commit preconditions are checked again before deletion. Existing MVCC leases preserve the discovery keys and earlier readers' historical payloads independently of their current-row removal.

Native SQLite, SQLite Key/Value and redb run one finite pass through `reclaim_obsolete`, after rejecting an active caller transaction and before provider history reclamation. Ordinary SQL `VACUUM` invokes this path without rewriting the physical file; `VACUUM FULL` additionally uses the existing provider compaction operation. `ONLY_DATABASE_STATS` invokes neither operation. The pass uses an independent physical session and the original invocation's cancellation/allowance; it releases its discovery snapshot before ordinary version collection. Empty databases acquire no DiskANN identities or write records. `run` drains generation cleanup and then a separate finite mapping pass; generation-only `step` retains its existing return contract. Automatic rebuild scheduling and covered-journal pruning use the database worker. After ordinary history collection, physical tombstone reclamation additionally retires obsolete generation, mapping, canonical-origin and journal identities as described below.

## Catalog mapping reclamation

`KeyValueDiskANNMappingMaintenance` captures one independent retained snapshot, visits its index mapping keys first and table mapping keys second, and keeps only one fixed-size cursor/current key. Each step rechecks the current data marker, mapping and physical generation prefix. A selected-head prefix conservatively retains the mapping, including an invalid head requiring separate repair; a table mapping also stays while any child index mapping remains. Otherwise one evaluated transaction requires the original marker, mapping and preparation-guard revisions, then deletes the mapping and its optional guard: at most two current records. Missing predecessor guards are supported after incompatible writers are fenced. Malformed catalog identities, handle envelopes and guard values fail before deletion. Original cancellation and allowance apply to discovery and mutation.

Let $c$ denote a complete catalog scope, $m(c)$ its physical handles, $G(c)$ its index guard and $T(c)$ its shared table guard. A successful bound allocation of generation $g$ establishes the mapping, Writing state and $G(c)=g$ atomically while holding its original resource lease; if the index mapping was absent it also writes $T(c)=g$. Thus a live bound allocation never exposes a mapping without its owned generation. Generation cleanup cannot remove that state while a build, source or unresolved attempt retains the lease. Private catalog undo alone neither grants recovery authority nor changes that ownership.

For an index cleanup $D$ and a concurrent bound preparation $P$, if $P$ commits before $D$ evaluates, the generation-prefix check retains the mapping. If both evaluate the old state, $P$ changes the guard revision required by $D$, while $D$ deletes the mapping revision required by $P$; whichever commits first rejects the other's original attempt. If $D$ commits before $P$ evaluates, $P$ allocates fresh non-reused handles. The same cases hold for a table: an existing child prevents cleanup, and creation of an absent child changes the table guard. Therefore no successful cleanup removes a mapping needed by a valid live preparation. Publication requires the original mapping revisions and a real retained sealed source, so a stale scope cannot publish through a deleted or recreated mapping.

Only a definite MVCC read/write conflict may be rolled back and reevaluated. A missing, rejected or indeterminate completion retains the evaluated transaction and cursor until explicit original-outcome resolution. Bound allocation additionally retains its resource lease. Neither receipt completion nor cleanup reconstructs a callback. Consumed generation and physical-handle watermarks are never deleted or rewound; abandoning a failed preparation cannot make a previous address reusable.

Let $S$ be the finite set of mapping keys in the discovery snapshot. Each completed step advances strictly in index-first/table-second order on $S$ and removes at most two current records. A racing preparation is retained for another pass after a definite conflict, so continuous new allocation cannot enlarge this pass. The cursor uses constant-sized identity storage; fixed-width value reads and key-only existence checks load no graph or canonical payload. With no concurrent lifecycle changes, successful generation and mapping passes leave current mappings only for retained generations, selected heads or remaining child mappings. Concurrent release or reclamation can make a previously retained mapping eligible for the next pass. This bounds current obsolete mapping rows independently of the historical number of dropped definitions, while retained MVCC versions and final head tombstones follow the separate physical reclamation protocol below.

For semantic preservation, fix any valid query snapshot $s$ and let $Q_s$ be its existing decorated postings or ranked result, including support, payload, score, origin and order. Cleanup changes only current addressing metadata for unselected, unowned generations; retained snapshot $s$ continues seeing its original mapping, head and payload bytes through existing MVCC retention. Fresh queries either select the unchanged live head or use the existing canonical path when no head exists. Non-reuse and observed publication requirements exclude aliasing between those cases. Therefore $Q_s$ is equal before and after reclamation as a full value, not merely by document support. Every existing algebraic composition receives identical operands and thus keeps its previous result; no new scoring operation, optimizer rewrite or approximation is introduced.

SQLite main record format 52 and redb main format 51 fence writers that could publish mappings before an owned Writing state or omit preparation guards. Their atomic initialization preserves the earlier generation-watermark consolidation, native mapping 12, catalog 49, histories, receipt outcomes and existing nine-byte mapping values. Older guardless mappings are collected only under the new admission protocol. Custom versioned providers must independently exclude incompatible writers, including already-open owners, before enabling this reclamation API.

## Physical tombstone reclamation

Deleting a generation, mapping or journal entry leaves an MVCC deletion revision. Ordinary history collection must keep that revision: an already prepared replacement with `expected = None` must not succeed after another writer inserted and deleted the same key. A prepared batch can outlive its read lease, so merely waiting for readers and erasing the last head would admit this stale write. Scoped retirement therefore preserves the absence observation through a separate reclamation epoch.

Storage owns `TombstoneReclamationRequest`, the charged 64-entry `TombstoneReclamationPage`, original observation validation and finite pass scheduling. SQLite and redb own snapshot admission, physical key selection and atomic deletion. Common Key/Value maintenance selects the generation/mapping root, canonical-origin root, change-journal root and shared vector-field guard root. Native SQLite selects existing families 57, 58 and 59 plus the exact database-owned `vector_field_guard::` TEXT-key prefix in Metadata. These are four fixed database-wide domains, independent of the number of historical tables, indexes or generations; canonical data does not need a previously initialized graph marker. Other record namespaces retain ordinary head-tombstone semantics.

Let $c$ denote the logical committed sequence, $e$ a reclamation epoch and $f_P$ the most recent retirement epoch for an enrolled physical prefix $P$. A snapshot captures $(c,e)$ under the same admission that publishes its liveness lease. A prepared batch retains that original $e$ in its sealed fingerprint; derived-effect resolution preserves it rather than substituting the resolver's newer snapshot. The public `PreparedRecordCommit::new_at_snapshot` constructor accepts the actual evaluating snapshot. The raw `new` constructor supplies no epoch evidence. Common logical sessions attach their original snapshot automatically.

An ordinary expected revision is still checked exactly against the current head. For an absent observation, including a read-only `require_unchanged` requirement, the physical writer additionally requires either that the key has no enrolled prefix or that its sealed epoch satisfies $f_P \leq e \leq e_{\mathrm{current}}$ for every enrolled prefix containing the key. A missing or stale epoch produces `ReclaimedObservation` before head comparison. This may conservatively reject a detached raw batch for another key in the same prefix; it never replays an application callback to obtain a fresh observation. Active SQL transactions retain their evaluating snapshot and therefore cannot cross a retirement epoch. A matching committed receipt is resolved before these checks, preserving the original outcome even after the record itself has disappeared.

Retirement holds the provider's shared snapshot admission and requires that no record snapshot is alive, including another connection's or process's lease. It first checks the original cutoff $c_0$ against current visibility. A page visits at most 64 ordered eligible identities with head sequence at most $c_0$, retains only charged key/revision metadata and advances an exclusive cursor. Later revisions do not join the pass. Ordinary history collection runs first; a head with older versions still present is skipped for a later invocation. Consequently each selected deletion removes at most one remaining logical head and one version. SQLite may split a bounded, revision-preserving run to remove that identity; no graph, vector or journal payload is decoded to choose a candidate.

When a page removes at least one fully pruned tombstone, one physical transaction deletes those identities and sets $e' = e_{\mathrm{current}} + 1$ and $f_P' = e'$. The global epoch and prefix floor use reserved namespaces in the existing identifier table. Public identifier reads and reservations reject those namespaces before provider admission, so application allocation cannot alter the epoch or a domain floor. It does not advance $c$, allocate a logical transaction, change generation/handle watermarks or remove receipts. All fallible in-memory reservations precede publication; cancellation, quota exhaustion and provider errors cannot expose a deleted head without its floor. Epoch exhaustion is an error. A provider commit with an uncertain physical outcome is subsequently observed as all old or all new state; another maintenance invocation consults that durable state rather than replaying a logical mutation.

The observation invariant follows by considering a prepared absent-key write evaluated before an intervening insert/delete. If its read lease survives, snapshot admission prohibits retirement and the retained deletion revision rejects its `None` expectation. Otherwise retirement increases the relevant floor past its captured epoch, so validation rejects it even though the head has been removed. If the key is recreated before the retirement writer acquires admission, the current live head is not a deletion candidate; if it is recreated afterward, the new writer uses the new epoch and the ordinary revision check orders subsequent replacements. A known nonzero revision cannot equal a removed head, so positive observations need no additional absence token. Atomic floor/deletion publication preserves these cases after interruption or restart. Receipt-first resolution covers the separate case in which the original write already committed.

For query preservation, project each physical view to the complete live record values selected by its logical sequence, including canonical tensor bits, mutation origins, selected generation, graph/PQ/side bytes and journal identities. A retained view cannot overlap retirement. For a newly captured view, every retired identity already denotes absence and every live value is unchanged, so this projection is identical before and after retirement. New raw MVCC snapshots may observe no deletion revision instead of the retired positive revision; the epoch protocol above replaces that internal evidence explicitly. Full query inputs, document multiplicities, decorated payloads, canonical scores, ranking ties and result order remain equal, not merely document support. Therefore each existing UQA operator receives identical complete arguments, and induction over a composition preserves its full result and applicable algebraic laws. No optimizer rewrite, approximation bound or scoring transformation is introduced by reclamation.

With no concurrent lifecycle changes and after all retained snapshots close, successful generation/mapping cleanup, ordinary history collection and these finite prefix passes leave no obsolete physical DiskANN deletion identity. Live and explicitly retained state remain proportional to the current workload; ongoing writes or live readers can defer reclamation, so this is a quiescent retention guarantee rather than a deadline. The additional retirement metadata is one global epoch and at most four prefix floors. Existing receipt, snapshot/resource lease and unrelated provider metadata retain their own retention contracts.

SQLite main record format 53 and redb main record format 52 fence predecessors that do not capture and validate reclamation epochs. Their initialization preserves existing rows, receipts, pending restore intents, identifier maxima, native mapping 12 and catalog 49. No tombstone is discarded during the format conversion itself. Custom physical layouts must override `VersionedPersistence::reclaim_diskann_tombstones`; wrappers must forward its selection, `reclaim_tombstones` and the original snapshot epoch. An unimplemented retirement capability fails explicitly when a populated owned namespace requires it. A custom provider must exclude incompatible older writers before enabling retirement.

## Commit outcomes and retained reads

The dedicated writer uses the existing MVCC evaluated-batch and receipt protocol. An unresolved attempt blocks subsequent staging operations. `commit_pending` and `rollback_pending` resolve that original session attempt, preserving typed committed/indeterminate outcomes; they do not replay staging callbacks or create a second recovery protocol. After process loss, existing provider receipt recovery and `resume_stage` supply durable state. Autonomous allocation may leave harmless unused generation numbers when creation fails.

`open_source` retains one immutable provider read boundary and reads only the fixed database marker and state. It does not enumerate or load graph/PQ records. The retained source holds its MVCC lease after the live repository closes; historical values remain available through later replacement, deletion and version reclamation. Page batches contain at most 32 unique IDs and report actual I/O concurrency 1.

Point reads enforce each encoded-size cap before provider materialization. Source metadata, copied key pages and reader buffers retain the supplied memory allowance; provider private batches and retained sessions keep their existing separate session allowance. Every read uses the current operation's cancellation and workspace control, so cancelling the opening query does not cancel independent readers. Canonical query selection additionally retains the original query cancellation while preserving that physical opener contract. Bounded physical construction follows the [generation build contract](diskann-generation-build.md); public index integration and complete runtime resource acceptance remain later obligations.

## Native SQLite mapping

`ManagedConnection::diskann_generations` requires an already bound native record session and returns the same Storage-owned generation repository. It obtains an independent staging session from the existing pool, retaining its encryption credential, native data namespace, transaction-history identity, retention allowance and receipt protocol. It does not construct a SQLite Key/Value database over a native file. Opening it during a caller transaction does not publish or undo the caller's changes.

Native mapping format 10 registers database-owned family 57, `_uqa_mvcc_native_diskann_records`, with BLOB key/value columns. The logical bytes above become the physical table's binary key/value; native MVCC keys and row envelopes wrap those bytes without JSON or text conversion. A graph-page value remains exactly 4,096 bytes in the physical table. Native materialization and history publication share the existing guarded atomic commit. Upgrade preserves earlier family identities and format 9's independently persisted data namespace; failed upgrades leave the previous schema/history intact. Current malformed tables or missing guards reject reopening.

The private translation adapter implements the existing ordered Key/Value interface. Native key encoding owns both complete BLOB components and unterminated byte-prefix encoding, preserving empty keys, embedded zero bytes, binary order and strict continuation. Key-only scans never fetch payloads. Point-read limits include the checked native row/key envelope before the provider loads a value; decoding checks the complete native identity and logical key before exposing borrowed payload bytes. Compound reads, retained prefix scopes, original revisions, conditional writes, savepoints and typed commit outcomes retain their existing common MVCC owners. No generation state machine is duplicated in SQLite.

## Verification

The reusable conformance suite writes an actual graph page, codebook, code batch, side batch and manifest; checks raw signed-zero bits and original vector versions after reopening; verifies caller-transaction isolation; rejects late writes, missing/oversized pages and corrupt seals; and exercises bounded cleanup plus retained reads across replacement, deletion and collection. Both native SQLite and SQLite Key/Value run it through plain, encrypted, compressed and encrypted-compressed connections. redb closes all prior shared-owner handles before its cold reopen.

Common MVCC fault tests cover lost creation replies, rejected publication, lost replies before/after durability, original commit fingerprints and a previously evaluated writer racing freeze or discard. Fixed metadata tests preserve typed quota diagnostics and reject missing, repeated or suppressed invalid completions. These are deterministic correctness/resource checks, not timing or SSD performance evidence.

## Abandoned build ownership

Each new stage reserves a non-reused 63-bit owner allocation from the database-wide resource namespace, independently of the generation watermark. Allocation one is permanently reserved for legacy-state transition admission, so new build allocations start at two. State revision 2 stores the build allocation in the existing 18-byte envelope. SQLite main record format 50 and redb format 49 introduced the ownership fence; the generation-allocation successor described above retains it; native mapping 12, catalog 49 and artifact bytes are unchanged. Revision-1 published/retired generations remain readable. After that predecessor fence, resuming an unpublished legacy owner atomically replaces only its state identity under the original state/data requirements; abandoned legacy cleanup instead claims a fresh resource owner before its conditional deletion. Both retain the reserved legacy transition lease until the first revision-2 outcome resolves, because an uncommitted new owner number is not yet discoverable in the old state.

`ResourceLeaseProvider` separates Claim, Share and Recover admission from SQL SSI. Claim requires that no build/reader/recovery owner is alive. Share can retain an immutable source alongside the build and other readers; an active recovery owner excludes sharing. Recover requires every normal and recovery owner to be absent and excludes new claims and readers until release. SQLite uses a database-incarnation-tagged `.uqa-resource-leases` file with OS byte locks; the existing slot transport stores normal/recovery tags without holding an admission lock across a database operation. This sidecar contains liveness tags, never vector payloads or encryption credentials. redb and local/browser SQLite reuse the existing exclusively owned local transport in a separate resource namespace without admitting SSI participants. Restore excludes native resource leases and their detached physical owners before replacing the history incarnation.

A stage, an opened immutable source, nested retained reads and private head publication all retain the actual physical lease. The source places that lease inside its retained `KeyValueRead`, because private publication retains the read itself. Repository bookkeeping contains budgeted weak references only; retaining an idle repository does not keep dead builds alive. An uncertain original staging or recovery attempt additionally holds a strong lease in the repository until its original commit/rollback protocol resolves it. Releasing a lease performs no transaction work and does not infer rollback from process death.

`reclaim_abandoned_step` reads the current committed generation state and rejects Published. A live Writing/Frozen/Sealed owner returns `false` without deletion. After exclusive recovery admission, the operation rechecks the exact state and performs the same bounded, conditionally fenced key-only deletion as committed retirement; partial cleanup persists Discarding. Absent states and previously committed Discarding/Retired states reuse the existing idempotence and retirement rules. Another cleanup process can resume after a crash. No timestamp, PID lookup, absent SQL head or failed build is evidence of abandonment.

Preservation follows from the admission and publication invariants. Any valid private publication retains a normal source lease until its transaction and retained views release it, so recovery cannot claim that generation concurrently. If recovery claims first, new sources cannot acquire ownership; its unchanged-state requirement also rejects a conflicting publication or legacy owner upgrade. A committed Published state cannot enter abandoned cleanup. Consequently cleanup deletes no generation that can become a selected head through a valid retained source. Existing queries over retired committed generations remain protected by their ordinary MVCC snapshots, so payload history, scores, document identities and all existing algebraic compositions remain unchanged. Unknown physical commit outcomes retain their exact evaluated attempt and lease; cleanup never reconstructs or replays that attempt.


## Vector field guard retention

A vector field uses a lifetime revision $L_F$ and an immutable reference marker $R_F$. Ordinary document writers require the original $L_F$ and touch $R_F$ as a mergeable marker. A structural transition conditionally fences both keys. The marker's payload is coordination state, not a canonical tensor or query input. Table/column deletion, renaming and ordinary last-document deletion can leave this marker after every canonical vector in the addressed field has gone. Its lifetime follows the actual physical vector domain, including standalone fields that have no catalog table or DiskANN graph marker.

Common Storage's `VectorFieldGuardMaintenance` retains one finite discovery snapshot, visits only guard keys and reevaluates one field per step through an independent logical writer sharing the invoking allowance and cancellation. `VersionedPersistence::vector_field_guard_layout` supplies provider-owned decoding, the exact paired keys, immutable reference value and canonical-vector prefix. Common Key/Value uses its existing length-delimited table/field codec. Native SQLite validates its complete Metadata identity and the hexadecimal object/incarnation/field prefix with its native key codec; it does not reinterpret key bytes in common Storage. Malformed names, changed marker values and a live lifetime payload reject before deletion.

Let $V_F(s)$ be the set of live canonical vector records in field $F$ at the cleanup writer's evaluated snapshot $s$. Cleanup acts only if $R_F$ has its exact immutable value and $V_F(s)=\varnothing$. One ordinary conditional commit requires unchanged $L_F$ and replaces $R_F$ with a deletion revision. Cleanup does not change canonical data and therefore does not create a structural lifetime transition. Native row projection and cache-generation history participate in that same logical commit. A nonempty field remains unchanged. Each step writes at most one guard record; one native registry cache revision may additionally be materialized by the existing trigger protocol. There is no table-directory or historical-field materialization. The pass releases its discovery view before ordinary history collection and the four scoped physical tombstone passes.

To prove the concurrency invariant, consider a document writer $W$ racing cleanup $C$. If $W$ commits first after $C$ evaluated the empty field, its touch advances $R_F$ and $C$'s conditional deletion rejects. If $C$ commits first, $L_F$ stays unchanged and $W$ can rebase its mergeable reference marker, then publish its evaluated canonical data. Cleanup has no canonical effect to invalidate that writer. If $W$ committed before $C$ captured its view, a live vector makes $V_F(s)\ne\varnothing$ and cleanup does nothing. Independent document writers continue to merge after any completed cleanup because they capture the same fresh lifetime and keep the existing mergeable reference protocol. Structural writers retain canonical comparisons on the two guards; concurrent marker retirement can invalidate an original positive reference revision, so a structural operation may still report its ordinary optimistic conflict. Cleanup does not weaken that revision check or replay its caller. A definite revision conflict is deferred to later maintenance; an uncertain original attempt stays owned by the step object and is resolved through its original receipt before the cursor advances.

Retained snapshots continue seeing their original values and revisions through ordinary MVCC history. After the final reader closes, physical retirement removes the reference tombstone and any existing lifetime tombstone under the existing absence-epoch proof. An old prepared absent observation therefore cannot become valid through guard deletion and recreation. Positive observations fail their ordinary revision check after the old identity disappears. Original committed receipts still resolve before either validation. Physical deletion never bypasses native materialization of a live metadata row: live-marker deletion is an ordinary logical transaction, and the physical pass removes only fully pruned NULL heads.

For semantic preservation, define $\pi(s)$ as the complete query-visible state: canonical tensor bits and origins, selected graph/PQ/side records, catalog definitions and journal identities. Guard cleanup leaves every component of $\pi(s)$ unchanged, for both retained and fresh views. Consequently every decorated posting and ranked result, including support, payload, score and order, is identical, and all existing algebraic compositions receive equal operands. No scoring conversion, operator, optimizer rewrite or approximation is introduced. Cache revisions retain their ordinary invalidation meaning because they are published with the logical metadata deletion.

Once writes quiesce and retained readers close, a successful finite pass removes every empty-field reference, its paired lifetime and their physical histories. Remaining live guards are bounded by currently populated fields, not by historical table/column lifetimes. Concurrent writes and retained snapshots can defer collection. SQLite main format 53 and redb main format 52 already seal original observation epochs and validate every enrolled physical prefix, so this extra fixed domain requires no new on-disk format: the writer protocol and key/value encodings remain unchanged. Earlier formats remain excluded by the existing format fence. Compatibility verification must include an actual format-53/52 predecessor writer after the new domain has been reclaimed.
