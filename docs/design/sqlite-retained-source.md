# Retained native SQLite source

This provider boundary preserves the original physical database selected by native SQLite and auxiliary registry pools. It supplies a prerequisite for the retained listeners in the [notification design](sql-notifications-and-sse.md) without adding an Engine subscription API.

Native SQLite and auxiliary registry pools freeze the selected canonical file path and retain the original SQLite connection as their shared, never-mutating change monitor. The monitor remains alive even when every checkout connection is discarded. It pins the original physical identity without opening an independent Unix file descriptor: closing such a descriptor could release another connection's process-wide advisory locks, as described by [SQLite's locking contract](https://www.sqlite.org/howtocorrupt.html#posix_advisory_locks_canceled_by_a_separate_thread_doing_close_). All connections, including this monitor, close through SQLite before the pool releases its database owner. The compressed VFS retains its separate format identity and compaction protocol; physical inode replacement is legitimate for that format.

Let $s$ be the retained native file identity, $p$ its fixed path and $f$ a monotonic source-failed flag. Unix identities contain device and inode; Windows identities contain volume and the complete 128-bit file identifier. Pool checkout and monitor access require $\neg f$ and $\operatorname{id}(p)=s$. Missing or different identity sets $f$ and returns the content-free `DatabaseSourceChanged` error. Once $f$ is true, restoring the earlier pathname cannot reopen admission. Additional physical opens omit SQLite's create flag and validate the retained identity before and after opening; native VFS implementations supporting `SQLITE_FCNTL_HAS_MOVED` also validate the newly opened connection's own file. No error path substitutes a new credential, clears $f$ or adopts a replacement source. Existing leases remain usable for their original rollback and destruction paths.

For any admitted execution under the existing requirement that callers close owners before externally replacing database files, the added checks read only metadata and SQLite file-control state. They neither evaluate SQL nor modify rows, transaction outcomes or notification payloads. Therefore the observation projection is unchanged on valid-source traces. Inductively, the first observed source mismatch sets $f$, and every later admission fails independently of filesystem restoration; a retained receiver can report source failure but cannot present a replacement database's suffix as continuation of its original notification history. This is failure detection and retained-source admission, not a filesystem namespace lock or a guarantee against arbitrary external overwrite or adversarial replacement during an already executing operation.

The stable monitor occupies the existing one-monitor allowance; a pool retains at most its configured checkout limit plus that monitor. Native file pools establish the monitor at construction instead of opening it lazily, so it is available before the first checkout and remains independent of every logical transaction. The source guard adds one shared canonical path, a physical identifier and a failure flag, with no polling thread or per-listener connection. Complete provider/cache/process-memory accounting and runtime cleanup deadlines remain separate acceptance obligations.
