# Python notification ownership and preservation

The Python binding adapts the [owned direct listener](owned-notification-listeners.md) and [Rust HTTP subscription](owned-http-notification-subscriptions.md). Engine retains the direct hub and original provider; Client owns HTTP transport, decoding, retry state and cancellation. Python adds object conversion and runtime scheduling, with no new dependency edge, query operator, publication path or deployment default. Actual authenticated Cloud service and complete cross-platform/resource qualification remain requirements of the [fixed implementation ledger](../plans/0015-sql-notifications-and-sse.md).

## Value and observation preservation

Let $\mathcal{E}$ be the disjoint union of the existing Core notification, resynchronization and reconnection event variants. The conversion $\Phi:\mathcal{E}\to\mathcal{P}$ produces a frozen Python event: `kind` distinguishes those three variants; epoch/request identity and every applicable value are exposed without modification; fields absent from a variant are `None`. A notification's unsigned sequence $q\in[1,2^{64}-1]$ becomes a Python integer, and its process identifier $p\in[-2^{31},2^{31}-1]$ becomes a signed Python integer. Neither conversion passes through floating point. UTF-8 channel and opaque payload text are converted to the corresponding Unicode scalar sequence without normalization or JSON interpretation.

Define $\Psi$ on this image by selecting the Core variant from `kind`, converting its integer fields to their original finite domains, UTF-8 encoding the exposed Unicode strings and restoring the same metadata. Integer exactness, reversible UTF-8 conversion and disjoint variant tags imply $\Psi(\Phi(e))=e$ for every admitted event $e$. Therefore $\Phi$ is injective on the observable carrier. Its pointwise extension preserves the empty history, ordered concatenation and every original field observation: $\Phi^*([]) = []$ and $\Phi^*(x\mathbin{+\!\!+}y)=\Phi^*(x)\mathbin{+\!\!+}\Phi^*(y)$. Metadata erasure after this conversion yields the same SQL notification projection established by the direct/HTTP proofs. `ResyncRequired` is never relabeled as data, and visible identity changes only when the consumer receives `Reconnected`.

Both iteration styles consume exactly one event at a time from the same native owner. They neither republish notifications nor evaluate SQL on the creating Engine. Registration uses its selected original database/role and independent listener; asynchronous registration calls that same native operation. SQL commit, rollback and duplicate suppression occur before this adapter sees a value. Consequently existing relational, document, graph, scoring and ranked-result operations retain their operands and observations; no optimizer rewrite or numeric approximation is introduced.

## Runtime state and cancellation

A registration owns a native cancellation signal before it is submitted to Python's executor. The returned awaitable may be started once, and readiness requires successful native registration or the HTTP `ready` handshake. Cancelling registration signals that same operation and shields/joins its actual worker. If readiness wins the race, cancellation closes the returned handle before propagating Python `CancelledError`. The HTTP registration signal is retained for the stream lifetime; destruction of the completed registration does not cancel a successfully returned stream.

Direct registration also reserves the original Engine's opaque permit before returning the awaitable. Unstarted, queued and running registrations share the same hub ceiling with ready subscriptions; executor submission cannot create an unaccounted native owner. Running registration consumes the same permit, and failure or retained-input destruction releases it. The [shared admission proof](owned-notification-listeners.md#capacity-before-runtime-submission) supplies the count invariant without adding a Python-local capacity policy.

A synchronous receive detaches the GIL while awaiting the native source. An asynchronous receive awaits Engine's standard-library Future or Client's Tokio receiver on the existing native runtime; it does not retain a Python executor or Tokio blocking-pool thread while idle. Only completion conversion and thread-safe loop notification need a short blocking task. Python receives that completion on its owning loop, and a second concurrent consumer is rejected before submission.

Receive cancellation first signals delivery closure, then joins the native receive and the separately scheduled provider cleanup before rethrowing `CancelledError`. Repeated cancellation cannot detach either operation because the wrapper continues shielding the same owned futures. Explicit close shares a single cleanup future and joins any pending receive; deliberate closure ends iteration normally, while independent source/transport failures retain their typed error. Direct cleanup preserves the native registration permit until actual resource destruction, and HTTP cleanup joins the original worker/response release.

This gives a refinement from Python lifecycle traces to native lifecycle traces: successful registration maps to native readiness; each yielded value maps through $\Psi$ to one native receive; completed explicit close or cancellation maps to completed native cleanup. Scheduling and shielding add only suspension transitions. No Python completion claims a release before the corresponding native work finishes. Provider I/O and executor scheduling must themselves eventually finish for cleanup to finish; this establishes ownership/completion ordering, not a hard latency bound.

Native receives keep weak Python references to their future and loop. A consumer/future/task cycle therefore cannot become an external ownership root through the Rust waiter. Destruction of the Python subscription signals delivery even while the waiter retains the native owner. Its last native owner schedules retained provider destruction outside the Python loop. A dead loop or released completion target also triggers that cleanup. Garbage collection is a fallback without a synchronous completion promise; applications needing a release boundary must use context exit, `close()` or `aclose()`.

## Resources and failures

Each subscription retains one source, one receive guard, one identity and at most one pending receive/wake slot. HTTP transport and event memory retain Client's original accounting; direct queues retain Engine's original accounting. The adapter does not add a prefetch queue or a thread per idle listener. Completed Python event objects belong to the application and lie outside native queued-byte accounting. Runtime pools, HTTP registration owners, Python interpreter allocation and original provider caches remain part of whole-process resource qualification; the bounded direct submission count does not establish an endpoint capacity default.

Native errors map to `NotificationError` with a closed content-free code and a typed retained `NotificationFailure`. Retry exhaustion retains both the original and last attempt's failure. Provider/transport/server diagnostics are available only through explicit `diagnostic` inspection; exception, event, subscription and failure representations omit channels, payloads and credentials. Python argument type/range conversion can additionally raise ordinary Python errors before native admission. Tests must verify actual wheel behavior and peer response release; a loopback test server does not substitute for authenticated Cloud integration.
