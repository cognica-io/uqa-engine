# Browser notification Fetch ownership and preservation

The browser `HttpEngine` adapts the existing [JavaScript notification owner](javascript-http-notifications.md) to Fetch. Node and the browser share request validation, framing, exact event values, bounded queues, readiness and idle handling, retry episodes and terminal ordering. The browser owns Fetch, its AbortSignal and its response reader. This boundary adds no Engine or WASM algorithm, dependency, query operator or deployment policy; [direct WASM and integrated qualification](../plans/0015-sql-notifications-and-sse.md) remain separate requirements.

## One implementation across module formats

The [package generator](../../scripts/build-browser-notifications.py) wraps an explicit finite set of portable CommonJS sources in module-local closures and exposes their existing exports through an ES module. Each source is included unchanged, with a source hash; its relative dependencies must belong to the same explicit set. Modules retain separate lexical environments and one cached instance per name. There is no runtime evaluation, remote module loader, second decoder or rewritten arithmetic. The generated module and declarations are build artifacts, and custom WASM output directories receive the same Fetch adapter.

Let $M$ denote the original module graph and $B(M)$ its packaged form. The wrapper maps each module's lexical environment and export object to exactly one corresponding environment and object in $B(M)$. A dependency access selects the same module name and cached object. Induction over the finite dependency initialization order therefore preserves exports, private state and every subsequent function application. No payload representation changes at this boundary. The shared request/decoder/queue [preservation proof](javascript-notification-protocol.md) consequently applies to the generated browser code, including exact unsigned sequences, Unicode, frozen events and chunk-partition invariance.

## Shared attempt and browser transport

The shared `runStream` owns one attempt's connection and readiness budgets, advertised idle budget, decoder and forwarding order. It consumes one runtime-provided response iterator and awaits the same runtime's cleanup before returning. Node supplies an HTTP/TLS request, response and socket; Fetch supplies a request signal and response reader. A timer or cancellation records the first observed failure and aborts that attempt. Readiness still requires the complete validated ready event, and the absolute readiness deadline is not restarted when response headers arrive.

Fetch exposes response headers rather than a socket-establishment callback. The browser connection budget therefore bounds the Fetch promise through response headers, including preflight; its readiness budget continues through the valid ready frame. This is the browser's observable connection boundary, not a claim to observe TCP or TLS phases. Idle expiry resets only on nonempty body input after readiness, and the advertised timing relationship is validated by the same decoder as Node. The retry owner retains its original episode deadline and only obtains a new epoch after a new ready. Its bounded jitter uses real Web Crypto words with rejection sampling over the requested integer interval; it does not substitute a floating-point random source.

For an admitted ordered event trace $E$, the shared driver forwards its notification prefix in decoder order. It never generates a notification from a transport error. The queue inverse and lifecycle projection are unchanged, so erasing transport metadata gives the same selected committed history as the existing HTTP client. A replacement is separated by `resync_required` and `reconnected`; these disjoint variants cannot be mistaken for uninterrupted data. Cancellation and observed authority loss discard unread events. Other terminal failures retain the already admitted prefix before their typed error. Existing SQL and algebraic carriers are unchanged.

## Request authority and cleanup

Every attempt posts only to the original origin's fixed subscription path. Bearer credentials occur only in the authorization header. Fetch uses CORS mode, omitted ambient credentials, no referrer, no cache and manual redirects. An opaque redirect is a terminal protocol failure; no redirected request obtains the bearer value. The [Fetch standard](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque-redirect) defines that filtered response, and its [CORS header rules](https://fetch.spec.whatwg.org/#cors-exposed-header-name-list) govern which response fields JavaScript can inspect.

A supported cross-origin endpoint must expose `X-Request-Id`, `Retry-After` and `Content-Encoding`, use identity encoding and supply the protocol's content type and no-store/no-transform policy. Missing visible request identity prevents readiness. Visible duplicate identity, encoding and content-type values fail the shared validators after Fetch combines duplicate fields; cache directives retain HTTP list semantics. JavaScript cannot validate a header hidden by CORS, so correct server exposure and the real serving path must also be qualified. The remaining Cloud work explicitly includes that configuration; browser fixtures alone do not establish it.

The shared owner aborts the actual Fetch request on every exit and the adapter awaits cancellation of its original reader before releasing that reader's lock. A response-body error caused by abort is already terminal and does not prevent lock release. Public close and iterator return join the same attempt owner; a second attempt cannot begin while that cleanup is pending. Browser-managed connection pooling is outside this reader's ownership, and local completion is not acknowledgement of a remote listener transaction. A pending receive does not block unrelated browser tasks.

The request, event queue, frame/line parsing, observable response headers and application-retained body chunk have explicit limits. The browser's internal networking, decompression and buffering remain browser resources; these checks do not establish a whole-process memory ceiling. The endpoint must disable content transformation. Whole serving-path resource accounting, supported-platform coverage and controlled-host timing qualification remain in their original completion units.

## Evidence

The shared-driver extraction passes all forty-six existing Node HTTP/package cases, including actual TLS cancellation, socket joins, strict headers, protocol fixtures and an offline packed installation. Real Chrome additionally exercises the public browser package through a distinct loopback origin: bearer preflight, cookie/referrer omission, exact values, gated readiness, connection/readiness/receive cancellation, one-consumer admission, typed HTTP and protocol failures, invisible identity, gzip rejection, malformed UTF-8, redirect refusal, epoch-separated reconnection, cancellation during real Retry-After backoff, slow/healthy receiver isolation, authority discard and silent-peer expiry. Backoff observation retains the actual Web Crypto result; it changes neither transport behavior nor the sampled value.

The first browser reconnection run exposed a mismatched random-function interface in the new adapter; eleven earlier cases passed and reconnection failed before a replacement request. The corrected adapter uses the shared owner's integer-interval interface, and all sixteen browser cases pass. Fixture expectations for initial HTTP failure and admitted-prefix overflow were checked against the authoritative manual; they do not redefine those existing semantics. The [reproducible verifier](../../scripts/verify-notifications-browser.py) rejects stale generated code, incomplete case inventories and failed reports, records source hashes and closes its browser and peer. Reports and screenshots remain ignored artifacts. These tests qualify browser HTTP delivery; they do not claim direct WASM, actual Cloud, cross-platform or measured resource/timing acceptance.
