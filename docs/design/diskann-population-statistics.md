# DiskANN canonical population statistics

The shared count contract, immutable memory roots and versioned native SQLite, SQLite Key/Value and redb owners provide exact populations without reconstructing them during planning. Counts for composed canonical sources remain required by the existing [SQL integration unit](../plans/0014-diskann-vector-index.md#sql-lifecycle-and-planning). Their missing statistics remain unknown; this change does not complete that unit.

## Definitions and ownership

Fix a retained canonical view $S$ and physical generation $g$. For each document $d$, let $n_S(d)$ be its current tensor cardinality, $o_S(d)$ its current canonical origin, and $b_g(d)$ the complete origin captured by the build, or $\bot$ when absent. Define:

$$N(S)=\sum_d n_S(d),\qquad C(S,g)=\sum_d n_S(d)\,\mathbf{1}[o_S(d)\ne b_g(d)].$$

$N$ counts all current ordinals, including zero-norm side vectors. $C$ counts the current ordinals whose document origins are outside this exact build coverage. It does not count mutation operations, journal entries, changed documents or deleted historical ordinals. Empty replacements preserve their origins while contributing zero. Rewriting identical coordinates with a fresh origin contributes the current tensor's complete cardinality to $C$.

Storage owns `DiskANNCanonicalCounts`, mutation arithmetic and the canonical source's `population_counts(g, control)` capability. Its invariants are $0\le C\le N\le 2^{64}-1$. The capability returns exact counts only for the requested canonical/generation association; it may not enumerate the corpus, journal or origin pages to reconstruct them. Unsupported associations return `None`. Metadata capture and prepared readers project the same counts into Core's existing optional population fields. Planner consumes those fields through its existing [cost contract](diskann-physical-planning.md); Engine adds no counting algorithm or provider dependency.

## Memory maintenance and proof

Each immutable memory canonical root retains $(N,C,g)$ with its document and latest-change maps. Before initial construction the empty root has $(N,C)=(0,0)$ and no covered generation. A completed build installs its actual generation and clears the candidate root's change map. Every fork shares the allocator of non-reused origin identities while keeping its own canonical root.

For a replacement of document $d$, let $a=n_S(d)$, let $h$ indicate that its previous origin is already outside $g$'s coverage, and let $z$ be the replacement tensor cardinality. A fresh origin cannot equal $b_g(d)$, so the owner computes:

$$N'=N-a+z,\qquad C'=C-ha+z.$$

All other documents retain their cardinality and origin. Removing $d$'s old summand and inserting its new summand therefore derives exactly $N(S')$ and $C(S',g)$ from the definitions. The memory change map supplies $h$: construction clears it only after capturing every current origin, and each later replacement inserts its fresh version together with the complete tensor. This invariant holds initially and is preserved by every replacement, including repeated writes and zero-cardinality replacements. Checked subtraction and addition reject underflow, overflow or an invalid subset before publication; neither saturation nor wrapping can fabricate a count.

The candidate contains both new maps and new totals. Live replacement occurs only after all validation, memory admission, path copies and control checks succeed. A failed candidate therefore preserves the old vectors, origins and totals together. Cloning or retaining a root preserves its complete tuple; changing a fork cannot change another snapshot's statistics. Restoring a saved root restores the same counts without evaluating SQL again.

A successful rebuild captures this exact immutable source and validates complete build coverage before preparing the replacement reader. For the new generation $g'$, every current origin equals its captured build origin, hence $C(S,g')=0$ while $N(S)$ is unchanged. The source's new counts and covered generation are installed together with that reader. Earlier readers retain their earlier $(S,g)$ association. A failed build never installs this reset, and a request against a different generation cannot borrow the new counts.

## Preservation and resource boundaries

The statistics extend each retained state with a deterministic observation of existing cardinalities and origins. Erasing that observation yields the same documents, coordinate bits, origin identities, physical pages and mutation effects as before. The update equations introduce no posting, payload, score, graph or ranked-result operation. They use exact nonnegative integer cardinalities rather than approximate floating-point counts.

Replacing unknown estimates with these exact inputs changes only the existing cost annotations and diagnostic fields. The established ordered decorated-intersection rule continues to preserve fold order, rounded scores and payload collision precedence; no new optimizer rewrite or candidate-admission rule is introduced. The preservation argument for [physical planning](diskann-physical-planning.md#preservation-argument) therefore applies with $\widehat V=N$ and the known changed population $C$. Approximate traversal, exact threshold behavior, complete-tensor scoring and probability conversion keep their existing definitions.

Memory reads copy fixed-size totals and perform the original owner and invoking control checks. They need no projection allocation or corpus walk. The additional fixed root fields are charged by the existing retained-root allocation. Transparent retained wrappers forward this capability through their existing guards; sources composed from different canonical selections do not inherit an unrelated root's counts. Their required aggregate maintenance remains a separate implementation boundary.

Persistent providers must update totals with actual canonical replacements, preserve evaluated effects when merging disjoint writers, reclassify against the correct generation across publication and late commits, retain private/savepoint/history views, and recover exact counts after reopen. The current field-reference marker and allocation watermarks are not counts. The Key/Value and native SQLite integrations below supply these owners through their respective mappings and writer-format fences.

## Persistent population records

Storage supplies a fixed-size population header and an explicit witness for each current document. The header associates the exact pair $(N,C)$ and dimensions with the full selected generation identity. A witness records that generation, the document identity, its complete current canonical origin and a Boolean coverage classification. Empty origins require witnesses even though their cardinality is zero. A missing witness for an existing origin must fail; it cannot stand for uncovered membership.

The publication census takes an existing `DiskANNQueryRead` and an already verified complete `DiskANNOriginReader`. It enumerates the current source's ordered origin metadata, validates complete tensor shapes through that source's owner, and performs exact document lookups against the immutable build origins. No coordinate decoding or journal scan supplies these counts. For each current document it emits:

$$W_{S,g}(d)=\left(g,d,o_S(d),\mathbf{1}[o_S(d)=b_g(d)]\right).$$

The census sums each current cardinality once and includes it in $C$ exactly when the emitted witness is uncovered. Strict cursor advancement rejects repeated documents, missing current origins fail, and a reused origin identity with a different tensor shape fails. Therefore a successful complete census yields the populations in the definitions above and a matching witness for every current origin. The caller must stage all witnesses and the resulting header in one atomic mutation; an error, including a rejected witness callback or either source/caller cancellation, invalidates that batch.

This comparison does not assume an ordering between the selected canonical view and the build capture. The existing publication API allows a generation captured from a newer committed source to be published on an older retained canonical view with the same expected head. An older current origin can differ from the build's newer origin even if its allocation or publication clock precedes capture. Such an origin is uncovered. A field clock, mutation watermark or journal position cannot replace exact membership.

Ordinary replacement requires the actual previous canonical origin together with its matching witness. The common owner checks the full generation, document, origin and tensor shape before applying the replacement equations. The mutation owner supplies a globally fresh replacement origin, which is uncovered by the already selected generation. A witness from another document, another generation, or a superseded tensor is rejected before arithmetic. Immutable value records allow retained readers and undo roots to keep the preceding header and witnesses together.

The provider-independent header envelope occupies 72 bytes and the witness envelope occupies 120 bytes. Both have explicit versioned magic, deterministic byte order and reserved-byte validation. Decoding requires independently selected generation/field context; witness decoding additionally requires the actual current document and complete origin. The header verifies $C\le N$, and replacement uses checked arithmetic. Common MVCC and the Key/Value record layout define the atomic transaction path below. A provider must opt in with its writer format, canonical mutation and generation lifecycle owners before exposing exact counts.

Raw-field adoption must establish a complete census before exposing totals; partially stamped fields cannot advertise exact populations. Provider acceptance must cover disjoint writers in both commit orders, publication with late writers, savepoint/statement rollback, retained generations, reopen and restore. The common transaction fixture does not establish persistent-provider format or recovery acceptance.

## Evaluated population effects and concurrency

The common MVCC owner retains canonical origin replacements and generation publication/retirement effects. A publication retains its complete verified build-origin reader; its header template supplies physical identity and dimensions, never trusted counts. Providers supply only record addressing, codecs and an adapter over the existing fixed-view canonical validator. An unsupported layout rejects these typed operations. No fallback installs unmaintained raw counts.

For ordinary writes, original canonical record preconditions remain mandatory. Once those preconditions hold against the latest committed view $S$, reconciliation forms $S'$ by applying the transaction's evaluated canonical writes. It validates the complete resulting tensor shape and each replacement origin, then removes the actual old document summand using its required witness and inserts the fresh summand. Disjoint documents remove and insert different summands, so either commit order yields the same sum for the resulting state. Writes to the same canonical record retain their ordinary conflict. Derived headers and witnesses do not add a false conflict between disjoint writers, and reconciliation never reevaluates expressions or application callbacks.

A transaction publishing a generation $g$ instead performs the complete census on $S'$ against its retained $b_g$. This applies whether the private publication preceded or followed a concurrent canonical commit. A late writer committed after publication updates the newly selected header using that generation's actual witness. A writer evaluated before the first generation existed still carries its typed origin change, so the new generation also sees its contribution at commit. Retirement selects the latest witness prefix during resolution, removing witnesses inserted after its private preview as well as those already visible. The original catalog, field-lifetime and generation-head preconditions remain the publication owner's responsibility.

A raw exact/IVF/HNSW writer cannot supply the typed origin and witness required by the invariant. It therefore retains an explicit origin invalidation, including for a previously absent document. Its physical origin key identifies the field without reading a removed origin value. At private application, command refresh and final publication, the common owner rejects that invalidation if an existing population for the field survives the final structural and generation-lifecycle effects without a fresh complete census. A first publication in the same transaction recomputes its entire census on the final canonical view: an earlier raw deletion is valid, while surviving unstamped raw values fail. Explicit structural header copies do not replace this census and cannot suppress the invalidation check. If publication commits first, the late raw writer is rejected; if raw deletion commits first, a subsequent census includes only the remaining valid origins, while surviving unstamped raw values make publication fail. Thus no accepted order exposes a live population with invalidated provenance. Retirement or whole-field removal may eliminate the association before ordinary raw writes proceed. With no population association, ordinary raw writes retain their existing unstamped semantics and disjoint-document concurrency. Undo removes their invalidation effects together with the raw records. A later complete typed replacement supersedes an earlier invalidation; an earlier untyped structural origin write cannot erase a later invalidation's final-publication check.

Private batch application, command refresh and final publication use this same reconciliation. Private application stages the complete candidate under the transaction's existing atomic undo boundary. Savepoints retain the header/witness roots and the lifecycle-effect position; undo restores both. Published and retained snapshots own immutable records. Therefore error or rollback cannot leave a new tensor paired with its preceding counts, and old retained snapshots do not acquire the new counts. The prepared fingerprint includes the lifecycle order, physical identities, complete build-origin digest and generation; a pending receipt resolves the same evaluated attempt. Final admission validates the resolved committed sequence before atomically installing the records, so a concurrent commit between reconciliation and admission requires a new reconciliation.

Fenced structural copies retain ordinary canonical preconditions for their population records. Later private previews preserve that explicit ownership rather than weakening it into a derived merge. Retirement still removes the complete latest witness prefix when the final explicit header is deleted. A charged ordered index of the original canonical writes supplies these ownership lookups; resolution does not rescan the entire write batch separately for every witness.

Generation census uses bounded read pages, but its complete staged witness set is not constant memory. Every retained record, effect and lookup buffer must be admitted under the existing transaction allowance; failure discards the candidate rather than raising the limit or installing partial metadata. The build-origin reader retains its original cancellation and resource controls. Planning does not invoke this census: it may only read the completed fixed-size header for the exact selected association.

## SQLite Key/Value and redb ownership

SQLite main record format 54 and redb main record format 53 enable the common Key/Value population layout and exclude predecessor writers that omit its effects. The native SQLite adapter uses the distinct native layout described below. Header and witness addresses include the canonical table/field encoding and complete generation identity. They share the same versioned record store, transaction, receipt and retained history as their canonical origins; no auxiliary database or independently committed counter is introduced.

The canonical replacement owner stages coordinate changes without first deleting the origin as an untyped record. It then stages exactly one typed origin replacement alongside its immutable change entry. This preserves both the origin's strict precondition and its derived population effect until final reconciliation. Raw-vector replacement retains its original unstamped semantics only while the field has no active population; all three raw vector owners forward the common commit-time invalidation check. Actual generation publication retains the sealed source's complete validated origins on the same physical lease, retires the previous population and publishes the new census in the existing caller mutation. Retirement removes the latest witnesses even when a concurrent writer created them after its private preview.

Column/table rename copies both population namespaces with canonical data under the existing structural guards. Movement involving a DiskANN field rejects a destination containing any canonical vector, origin, journal, population header or witness before staging writes; ownership is established by actual origin/journal/population records or the stored DiskANN index reference, including empty predecessor fields. Ordinary raw-vector backfill retains its existing destination-preservation contract, and identical source and destination names leave storage unchanged. Exact-key collision checks are insufficient because independently selected generations have distinct header keys even when their canonical fields would be mixed. With an empty destination, movement is a bijection on record addresses that preserves document, origin, generation and cardinality, so it preserves both sums. Subsequent private replacements update those copied counts before final publication while retaining the copied records' strict preconditions. Field clear, column deletion and table purge delete the matching populations with the canonical namespace. Quiescent tombstone reclamation includes the population namespace under the same absence-epoch protocol; retained readers exclude physical removal.

An older selected generation without a population header is initialized by writable binding, before exposing the live handle. The initializer retains the actual complete build-origin reader, requires the captured catalog and selected head, and stages the common census in the caller's transaction. Commit reconciles against the latest canonical state, including writers that evaluated before initialization. Undo removes the entire derived installation. The graph, row expressions, canonical origins and selected generation are unchanged. Fixed metadata reads never trigger initialization and old retained views can still report unavailable counts. A malformed present header or a missing witness beneath a present header is an error, not an estimate.

After initialization, the census establishes the defining invariant. Every typed mutation preserves it by the replacement argument, publication reestablishes it for the new generation, and structural movement preserves the associated summands. Atomic common MVCC publication and history retention then preserve that invariant on every exposed Key/Value view. This induction establishes the existing count observation without changing the document, payload, score or composition carrier. Census witnesses remain charged to the caller's existing transaction budget; fixed planning reads decode only their selected 72-byte header.

## Native SQLite population ownership

Native mapping 13 stores the same shared 72-byte header and 120-byte witness inside field-owned native families 60 and 61. Let $O_t$ be the native table's complete object/storage-generation identity and let $G(g)$ encode every component of the selected DiskANN generation. The native addresses are

$$\phi_{\mathrm{head}}(t,f,g)=(60,O_t,f,G(g)),\qquad \phi_{\mathrm{witness}}(t,f,g,d)=(61,O_t,f,G(g),d).$$

Native tuple encoding is injective in these components, and the families are distinct from canonical vectors, origins and changes. Decoding validates the native key against the row, the complete generation against its payload and the witness against its actual document/origin. Canonical field descriptors retain the table name, field and complete native owner; their reconciliation adapter reuses the retained canonical validator rather than reconstructing origins from coordinates. Thus the record mapping preserves the domain, identity and cardinality of every summand defined above.

Actual canonical replacement stages one typed origin with its coordinates and immutable change row. Native raw exact/IVF/HNSW mutation maps its origin invalidation to the same common lifetime check, including absent origin keys and later first publication. Actual generation publication retains the sealed complete-origin reader, retires the preceding generation's population and publishes the new census in the same native mutation. The provider maps these evaluated effects to common MVCC; it supplies no separate arithmetic or publication algorithm. Common reconciliation therefore establishes the same invariant by census and preserves it for each fresh replacement, disjoint commit order, command refresh and retained/private view. Header reads admit only the known table/field/generation envelope plus the fixed payload; they do not read witnesses, graph pages, build origins or the corpus.

Native column movement rejects a populated destination when either field has canonical DiskANN provenance/populations or a stored DiskANN index reference, including predecessor fields without provenance records. This preserves the existing raw destination backfill contract for ordinary IVF/HNSW rewrites. Identical-name movement is inert. Under the existing structural guards, permitted column/table/owner movement is a bijection on the canonical records and both population families: the names or owner addresses change while document, complete origin, generation and cardinality are preserved. Applying this bijection preserves both sums; subsequent replacements use the moved witnesses. Field clear, column/table removal and scoped tombstone reclamation include both families. Retained history prevents reclaiming records still visible to an old reader.

An atomic format upgrade installs empty families and excludes earlier native writers while preserving canonical data, stable data namespace, transaction history, receipt outcomes and identifier watermarks. It does not invent counts for existing generations. Writable binding performs their first complete census under the original catalog/head guards and caller allowance, with ordinary private undo. Old retained metadata can remain unavailable; malformed present metadata fails. The main SQLite format remains 54, redb remains 53 and catalog format remains 49.

Backup restoration distinguishes the stable native data namespace from the transaction-history identity. Population addresses follow the former; the common retained record view follows the latter. A pending predecessor restore upgrades through its explicitly authorized restoration owner inside the original physical transaction, preserving the durable source/target intent; it never clears that marker to admit ordinary access. Failure rolls back an incomplete format change, and retry still requires the original restoration request. Changing history therefore leaves the address mapping and canonical sums unchanged, while subsequent fresh origins belong to the new history.

These facts give an induction on the native operation history: initialization supplies the defining census, common replacement/publication preserves or reestablishes it, structural bijections preserve its summands, and atomic publication/retention expose only complete corresponding views. Errors leave the preceding view intact. No document support, payload merge, raw vector value, score, ranking or composition operator changes; the extension supplies the existing exact count observation through a second physical representation. Admission of all effects, origins, witnesses and retained views remains subject to the caller's existing resource and cancellation controls.

## Verification obligations

Owner regressions use literal cardinalities for full tensors, identical-coordinate replacements, zero-norm and empty tensors, deletion, repeated writes, failed validation, independent forks, old readers, rebuild and clear. Checked-arithmetic cases reject invalid subsets and overflow. A metadata-only source rejects all document/origin/coordinate enumeration and graph/PQ/origin artifact reads while projecting independently supplied totals. Actual Engine planning and JSON EXPLAIN verify current roots, private writes and savepoint/transaction rollback. Source-scoped executed results are recorded in the implementation plan.

Persistent-record regressions independently spell out both byte layouts and reject truncated, oversized, reserved-byte, identity and subset violations. Repeated replacements compare maintained counts with a separate full-origin sum. Census regressions use actual sealed build-origin artifacts and a current source that rejects coordinate and journal reads; literal expectations cover an older current origin, identical identities in different documents, covered/uncovered empty tensors, changed tensor cardinalities and an empty corpus. These owner checks do not substitute for provider transaction or recovery acceptance.
