# Resolved builtin scalar cast execution

[#1108](https://github.com/cognica-io/uqa-engine/issues/1108) identifies repeated textual type resolution in row evaluation. SQL owns `NumericCast`, selected only from resolved builtin integer, floating-point and numeric identities. It invokes the existing conversion and numeric modifier kernels directly. Execution owns one optional descriptor per immutable prepared cast expression and retains its already-admitted source name; Engine supplies the invoking catalog callbacks.

SQL's `ResolvedCast` extends that selection to builtin scalar inputs converted to numeric, text, varchar, bpchar, character, boolean, UUID, JSON and JSONB. Its fixed-size metadata retains the source distinctions used by the kernel and the destination modifiers; the admitted source name remains available to current callbacks. It calls the existing value constructors. Real output retains its single-precision spelling; internal `"char"` retains its signed-byte integer conversion. The older `NumericCast` interface remains restricted to numeric source and destination identities.

The first evaluated row follows the original source inference, operand evaluation, catalog resolution and conversion order. Only a successful conversion to an explicitly qualified builtin target is retained. Subsequent ordinary scalar rows of the same type schema evaluate the operand once and use that descriptor without name construction, parsing or catalog name lookup. A changed schema follows the original path; cloned prepared expressions start with independent empty state. Unqualified source or target names, domains, OID aliases and containers still resolve and convert through the invoking catalog on every row; their catalog-free source inference may reuse the metadata described below. Parameter-dependent operands retain the complete original inference and resolution path. A catalog-bearing runtime carrier still follows its live physical-output or label path, even when an API caller supplies a builtin source schema.

The retained object contains conversion metadata, never the previous row's result. Every invocation keeps its current domain adapter, cancellation tokens and output allowance. Retained source-name capacity stays charged to the original production owner and is released when the prepared expression dies. This does not cache a domain check or remove an operand evaluation.

## Preservation argument

The selected builtin source and destination identities determine the numeric kernel and destination modifier; neither reads search_path, role, timezone, DateStyle or a mutable catalog descriptor. Reusing that selection for the same immutable expression and schema is equivalent to selecting it again. The value conversion itself remains per row, so rounding, overflow, NULLs, output allocation failure and the invoking callback's value or error remain observable at their original evaluation point. Expressions that cannot establish this invariant use the existing generic conversion.

This optimization introduces no new algebraic operator and does not reorder, eliminate or duplicate SQL operand evaluation. It preserves numeric results and SQL error order; it changes only repeated metadata work and the bounded lifetime of an admitted type name.

For the additional scalar selections, the source and target identities likewise determine the conversion and modifier. Text conversion uses the same value-to-text, real-formatting and internal-character kernels; length application uses the original Unicode character traversal and padding constructor. Boolean, UUID and JSON conversion use their existing constructors. Replacing repeated type-name selection with these fixed identities therefore preserves each row's value and the order of its callbacks and errors. Catalog-sensitive types are excluded from selection; temporal conversions retain only their fixed type selection and read current settings as described below, and runtime catalog-bearing carriers return to the generic path. No prior row's result, callback result or authorization decision is reused.

## Temporal descriptors and live settings

Temporal builtin source/destination identities and modifiers are now reusable through the same prepared-expression owner. The descriptor stores only the target kind, optional fractional precision and optional interval field mask. Source distinctions remain fixed-size metadata. Date/time input, infinity handling, interval field truncation and rounding reuse the existing SQL kernels; typed modifiers no longer require constructing and reparsing names. The descriptor remains below the existing 64-byte ceiling. Catalog-defined types and catalog-bearing runtime carriers keep their original resolution/decoding path.

Only type selection is retained. For every input value, the selected path enters the current DateStyle and IntervalStyle scopes before the current domain callback, then reads the current output style or timestamp zone at the original conversion boundary. Each setting scope restores its caller on success and failure. Date-to-character output shares the existing date formatter and applies the already selected character modifier without another type-name parse. A transaction clock remains live for special textual inputs. No setting value, callback result, converted value or failed conversion is retained.

Let the fixed builtin identities and modifiers be T and let the current value, settings, callback and production control be v, S, H and C. The ordinary path computes K(T, v, S, H, C) after resolving T. The retained descriptor encodes exactly T and invokes the same ordered setting scopes, callback and conversion kernels for each new v, S, H and C. Replacing repeated selection of that identical T therefore leaves the observable value, precision, earliest conversion error, callback count and cancellation unchanged. A changed input schema, parameter-dependent expression or unqualified identity cannot establish fixed T and keeps the generic path. This preserves the SQL row carrier and multiplicity, and introduces no new algebraic operation or evaluation reordering.

The failing-before Execution fixture performs 1,000 type resolutions for 1,000 alternating MDY/DMY rows. The correction requires one source selection and two catalog name lookups while retaining all 1,000 setting reads and callbacks. ## Catalog-sensitive source metadata

Execution can retain the source name even when the cast cannot retain a conversion descriptor. SQL's existing `scalar_cast_source_type_name_with_control` reads only the immutable expression, the supplied `RowSchema` and parameters; this call has no catalog resolver. Function bindings supply their original return-type spelling, and domain inference preserves the domain identity. The prepared-state registration excludes every parameter-dependent expression root. For the remaining roots, source inference is therefore a pure function of the unchanged expression and shared schema identity. Reusing its admitted name, including the absence of a name, is equivalent to repeating that inference.

The first successful evaluation retains only that inferred name and the existing shared schema. The subsequent evaluation still reads the current operand, resolves both source and target names against the current catalog, invokes current domain adapters and executes the ordinary SQL conversion. An unqualified name may resolve differently after `search_path` or catalog changes. A routine still executes once for every row, and its returned value is never retained. Existing builtin descriptor selection remains restricted to explicitly qualified builtin identities; this change does not make catalog-sensitive descriptors reusable.

A different schema follows the original inference path without replacing the first schema's entry. A failed first conversion stores no entry. Cloned prepared expressions begin with independent empty entries. The retained `Produced<String>` keeps its original memory reservation until the prepared expression is dropped; it does not bypass admission by retaining an unaccounted clone. Current cancellation and output controls remain active. This preserves row multiplicity, evaluation order, domain identity, live callbacks and conversion errors without adding an algebraic operation.

The regression fixtures fail before the correction with 1,003 instead of one source inference across changing unqualified targets, 1,000 instead of one across bound routine calls, and three instead of two across two schema identities. Fixed-work checks retain all 2,000 catalog resolutions and 1,000 routine invocations where required. Separate cases cover unknown source metadata with changing runtime carriers, later overflow and constraint failures, the unchanged 4KiB owner budget, failed-publication cleanup and cancellation. These counters establish reduced repeated work, not latency acceptance; controlled historical comparison and automatic delivery remain separate obligations.


## Scoped catalog descriptors

SQL can retain successfully resolved source and target descriptions for a single Execution-owned cast expression when the invoking hook explicitly certifies an immutable catalog identity. The SQL type-name parser admits schema-qualified names and bound user-type identities; ordinary unqualified names retain live namespace lookup. Each native scoped hook supplies its own identity for the immutable CTE catalog used by its cast resolver. Custom hooks decline by default and may opt in only while their qualified/bound resolutions remain unchanged. A retained identity owns its token, so a later catalog cannot become equal merely by reusing an address.

The first evaluation preserves source inference, operand evaluation, target/source lookup, current setting scopes and conversion order. Only success may retain descriptions, and a callback that changes the scope prevents publication. Later rows require the same complete shared type-schema identity, evaluate their operand once, and then check the current catalog identity. A changed identity invokes ordinary name resolution using that already evaluated operand. Parameter-dependent roots, unqualified spellings and custom mutable hooks keep their existing path. Conversions still invoke live domain/input routines, physical composite/enum observation, DateStyle, IntervalStyle and timezone handling through the original SQL kernels.

Let $D(C,s,t)$ denote the successful source/target descriptions obtained from catalog scope $C$ for fixed names $s,t$, and let $K(D,v,H,S,P)$ be the existing ordered conversion with current value $v$, callbacks $H$, session settings $S$ and production control $P$. The capability guarantees that $D(C,s,t)$ is invariant for the same scope and admitted names. Replacing a repeated $D$ by its retained identical descriptions therefore leaves $K$ unchanged. Checking the scope after operand evaluation preserves the case where that operand changes the catalog. Failed lookup/conversion never publishes metadata, and a changed scope takes the original lookup path before conversion. No operand, callback result or value is cached; SQL multiplicity, value/type/null observations and callback/error order remain unchanged. This is an ownership/work correction within the existing row carrier and UnifiedPlan, not a new algebraic operation.

Type payloads retain their original production leases. The optional boxed descriptor additionally reserves its fixed allocation before publication; insufficient allowance declines retention while preserving the already successful conversion. Entries are bounded by expression count and disappear with that expression owner. No row value, global descriptor cache or cross-statement name result is retained.
