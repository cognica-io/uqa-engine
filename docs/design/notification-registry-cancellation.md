# Notification registry cancellation preservation

This provider change adds cancellation to the existing SQLite notification registry while preserving the committed-history contract in [SQL notifications and SSE](sql-notifications-and-sse.md). SQLite owns native connection callbacks and physical transactions; Common Storage supplies the retained read control. It adds no Engine behavior, transport, query operator or dependency on a runtime.

The SQLite provider exposes `NotificationRegistry::begin_with_control` and `NotificationRegistryTransaction::commit_with_control`. Admission retains the existing registry connection pool and the original cancellation signal. Each operation installs native busy and progress callbacks only while its connection is borrowed on the executing thread. Moving the retained transaction to another thread therefore does not detach cancellation or leave callbacks bound to its construction thread. Nested operations retain every enclosing signal for that connection; an unrelated connection does not inherit another registry's cancellation. Operation guards restore the preceding native policy, and outermost completion releases the temporary callback-context stack. This stack and SQLite's native statement/cache allocations belong to provider workspace, separate from a receiver's queue-byte allowance.

The safe rusqlite busy API takes a function pointer, so its cancellation context is scoped per executing thread. The callback only inspects retained flags and yields between native lock attempts; it never executes SQL or changes the invoking connection. SQLite may return `BUSY` without invoking the callback to avoid a deadlock, so only an actually observed cancellation converts `BUSY` or `INTERRUPT` into the typed cancellation error. Other native errors retain their original cause. The original thirty-second native wait ceiling remains; two-millisecond callback waits are polling granularity, not an end-to-end latency guarantee. These rules follow SQLite's [busy-handler contract](https://www.sqlite.org/c3ref/busy_handler.html) and [progress-handler contract](https://www.sqlite.org/c3ref/progress_handler.html).

Let $S$ be the last committed registry state and $P$ one privately evaluated registration, cursor update or recovered publication. Native lock retry continues the same SQLite operation; it does not evaluate $P$ again. Before a successful registry commit, cancellation either leaves the explicit transaction for ordinary rollback or interrupts a write and lets SQLite roll back the entire transaction. Both cases restore $S$ and expose no prepared delivery. The latter case poisons the retained transaction and preserves its typed cancellation instead of replacing it with a missing-savepoint cleanup error. A non-cancellation rollback failure retains its existing diagnostic. SQLite's [interruption contract](https://www.sqlite.org/c3ref/interrupt.html) permits a nearly completed operation to finish, so successful commit remains successful even if the signal races with completion; no post-commit flag check invents an aborted outcome.

Ordinary `commit` and suspension of an unresolved publication retain completion authority independently of the original query cancellation. A committed main-store publication remains recoverable when a cancellable registry recovery attempt stops before acknowledgement; later recovery uses its original immutable intent and existing fingerprint checks. Thus cancellation changes whether an uncommitted attempt finishes, without changing committed notification values, duplicate suppression, subscription boundaries or metadata-erasure laws. Rollback and pool return run after cancellation callbacks are removed; an unusable lease follows the existing pool discard policy.

This provider boundary does not yet wire a caller's registration deadline through Engine gates, limit admission waiters, or interrupt an operating-system file open or encryption-key initialization already in progress. It supplies native lock/VM cancellation and preserves transactional outcomes, rather than establishing a total registration/close deadline or a complete deployment memory profile. Those remain direct-listener acceptance obligations.
