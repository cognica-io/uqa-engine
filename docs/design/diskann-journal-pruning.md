# DiskANN journal pruning

Storage owns bounded reclamation of immutable change records after [atomic generation publication](diskann-generation-publication.md). Key/Value and native SQLite adapters supply the current canonical/journal view, actual catalog binding and the evaluated mutation batch. Execution schedules finite journal passes through the database's existing background maintenance host; Engine retains provider, catalog, cancellation and status adapters. The same host also schedules [automatic graph reconstruction](diskann-maintenance-capture.md#automatic-reconstruction); final physical metadata reclamation remains unfinished.

The same provider capture also supports [exact outstanding-change accounting and consuming reconstruction](diskann-maintenance-capture.md). Census pages use the fixed canonical/journal view throughout; pruning continues to decide deletion from its current publishing transaction. Shared origin classification does not make these two evidence views interchangeable.

## Authority and deletion

`KeyValueDiskANNPruner` opens complete origins from an actual retained `KeyValueDiskANNSource`. It verifies the immutable origin artifact once and reuses bounded point lookup for subsequent pages; it does not accept a caller-created membership map or reconstruct coverage from a digest. Each command checks the source's actual history and full catalog-to-physical mapping, validates the current dimensions, complete index parameters and committed selected head, and requires that head to remain unchanged at commit. The canonical source supplies captured catalog guards, while obsolescence is checked against the command's current view rather than the older build snapshot. Native SQLite maps the head through family 57 and deletes journal rows in family 59 in the same underlying transaction.

For an immutable journal identity $(d,v)$ with origin envelope $J(d,v)$, selected generation $G$ and command snapshot $S$, deletion requires either $O_G(d)=J(d,v)$ or $\operatorname{version}(O_S(d))\ne v$, with absence distinct from an explicit empty replacement. Equal versions with different origin envelopes are corruption and fail the entire command. The current canonical source validates complete ordinal coverage before supplying its origin. No ordering relation on writer allocations, revision numbers or fingerprints establishes coverage.

The obsolete-version rule relies on the existing mutation contract: a committed canonical mutation and its journal entry publish atomically, mutation identities are never reused after undo, and receipt recovery resolves the original evaluated transaction without invoking its callback again. A visible committed journal identity cannot become current again after a later committed canonical origin supersedes it. A writer that has not committed contributes no visible journal key to this command; when it commits, its distinct key remains. Private canonical input and a private selected head are rejected as cleanup authority, so rollback cannot turn an apparently obsolete private version into the restored committed version. Each deleted key additionally carries its exact committed record requirement.

The deletion transaction preserves older readers through ordinary MVCC history retention. A reader that selected an older canonical origin or head continues seeing the corresponding historical journal entry; the physical current-row deletion does not remove that history. If the selected head or captured catalog definition changes before cleanup commits, all evaluated deletions fail atomically. Automatic maintenance uses an independent inactive provider session and captures committed catalog/head authority; it cannot adopt or complete an application's private DDL or transaction.

## Bounded progress and failure

`DiskANNPruneRequest` examines at most `min(max_records, 64)` journal entries; zero is invalid. Provider cursors seek exact mutation keys, including obsolete versions, and materialize only one bounded origin envelope at a time. Complete canonical ordinal validation and origin-artifact point lookup retain their original controls and bounded workspace. The cursor binds the physical generation and the last examined immutable key; switching generations requires a fresh pass. This interface does not claim a constant amount of work for an arbitrarily large canonical tensor.

`DiskANNPruneResult` reports evaluated entries and deletions, not durable completion. A page with deletions advances only after its original transaction commits. A page with zero deletions may advance after confirmed rollback of its read/guard-only transaction: no deletion needs publication, and its captured discovery keys were still examined. Reaching the end completes that pass; a later pass restarts from the beginning because a later commit can insert a key before the old cursor. Restart after process loss is safe without a persisted cursor: already committed exact deletions are absent, and surviving records are rechecked against current authority. The original retained build snapshot is unnecessary for coverage lookup, although the internal adapter still uses a captured catalog binding. Callers release the pruning handle and captured binding after the pass; their retained provider views otherwise continue pinning ordinary MVCC history.

Cancellation, quota failure, invalid provider completions, corrupt records or a failed precondition invalidate the enclosing batch. Savepoint rollback restores the deletions with the other evaluated writes. Commit acknowledgement recovery must preserve the original deletion bytes, head/catalog requirements and receipt fingerprint; it must not rerun the pruning callback. Bounded abandoned/retired physical generation cleanup runs through provider VACUUM; obsolete mapping and MVCC head-tombstone reclamation remain separate lifecycle work.

## Automatic finite passes

`PersistentStorageBackend::diskann_journal_pruner` captures one committed journal-discovery view, the actual selected physical source and its verified origins. It does not prepare resident PQ codes or hydrate graph pages. Each page selects keys from that fixed discovery view but reads origin envelopes and canonical obsolescence from its current publishing transaction. A key already removed by another maintainer consumes a discovery slot and requires no deletion. Keys committed after capture, including keys ordered before the cursor, wait for the next pass.

Let $K_0$ be the finite ordered journal keys visible at capture. Each successful page advances over at most 64 distinct keys of $K_0$, including absent current keys, and no later write can enlarge $K_0$. Subject to successful transaction completion, at most $\lceil |K_0|/64\rceil+1$ pages finish the pass. Deletion authority is unchanged: surviving records must satisfy the current catalog/head guards and the origin predicate above. Thus the finite discovery restriction changes scheduling only, preserving current exact-change results and all older MVCC views. Restarting after interruption is safe because missing keys do not reappear and every surviving key is revalidated.

Execution's `DiskANNJournalMaintenance` shares an existing immutable catalog snapshot and admits one index at a time. It visits at most one catalog entry or evaluates one 64-entry page per host step. New catalog entries wait for the next catalog pass, so neither continued writes nor index creation can extend an admitted pass indefinitely. The original allowance covers scheduler metadata, its retained name, decoded definition workspace, provider source and origin reads. The existing database worker coalesces wakes, continues successful pending steps without a per-page delay and polls idle or failed work approximately once per second; opening the dedicated pruning session does not restore a second Engine or its PQ caches. Origin verification occurs once per admitted index pass and is not a constant-time opening operation.

The host supplies the storage commit generation already incorporated into its catalog snapshot. A completed catalog pass suppresses another pass at that same generation; a newer independent version must not be substituted for the catalog's known version. The scheduler records this version at admission, not completion, so commits during a pass trigger another pass. Missing version support disables this optimization, and a failure clears the suppression. Pages with no deletions confirm rollback instead of publishing empty guarded transactions, preventing maintenance from repeatedly waking itself on an unchanged database.

Maintenance opens its independent writer through `open_controlled_session`, which shares the invoking allowance with private MVCC batches and retained reads as well as the pruning buffers. Execution verifies the returned database, distinct session affinity, shared allowance and original write cancellation before admitting a job. Read/rollback cancellation stays independent so cancellation cannot prevent cleanup. Default capability implementations reject unsupported providers; they do not grant a fresh memory limit or fall back to an ordinary independent session.

The execution transaction owner stores the evaluated result before completion. An indeterminate or committed-but-unacknowledged outcome retains that same session and result; later steps call completion only, even after cancellation. A failed page preserves its original error even if rollback also fails. Rollback failure retains the same job while its provider transaction remains active; an already closed transaction releases the failed job without advancing progress. Neither progress counters nor the continuation advance before confirmed completion; a page with deletions requires committed evidence, while a zero-deletion page permits confirmed rollback. Catalog/head replacement rejects the old pass atomically, releases it after completion and allows a fresh catalog pass to select the replacement. Final worker shutdown cancels and joins the existing host and releases its retained resources through provider cleanup.

`Engine::automatic_diskann_maintenance_status()` retains its completed pruning-pass and confirmed examined/removed counters. Separate fields report complete captured censuses, confirmed rebuilds, the current operation, pending completion and the latest failure. These counters do not report reclaimed historical bytes or performance acceptance.
