## Reproduction and owner

Execution's actual `Distinct` operator retained a typed row schema but passed only the scalar values to its exact-key encoder. SQL's admitted native ranges use text carriers, so numeric bounds with equal values and different decimal scales acquired different keys. The independent PostgreSQL range matrix reproduces twelve output rows where eleven, including one NULL, are expected for `numrange` under forced spill. Typed ranges nested in arrays and records already retain an OID during key traversal; scalar columns did not carry their corresponding type.

SQL continues to own range observation and comparison semantics. Its selected-type reader now accepts an already resolved borrowed `ColumnType` without resolving its identity again. Execution passes each scalar's selected type to the same admitted range-key writer that already serves nested fields. Native text uses the existing selected reader; declared physical values retain input-free observation. Core, persistent encodings, provider versions and dependency directions are unchanged.

Full-row DISTINCT borrows each type from its existing row schema. DISTINCT ON resolves its key expression types through the same evaluator context once at open, then retains them beside the prepared expressions. Neither path constructs a temporary typed row or copies every input merely to preserve its type. Unknown or ordinary TEXT inputs keep their existing string interpretation.

The public Engine corpus independently reproduced the same loss in GROUP BY, aggregate DISTINCT, joins, UNION and INTERSECT. General and projected grouping now retain the selected key types through hashing, collision comparison, partial-state schemas and both ordered and exact-key spill merging. Join keys retain types once per open for direct and computed paths; the direct index compares collisions under the same selected SQL type. External sorting and set merging retain types beside prepared keys, while aggregate sort/merge buffers share their comparison types through accumulator templates. These are statement metadata retained beside keys and in temporary schemas, not per-row copies of type definitions or changes to persistent key bytes.

MODE's frequency comparison also uses the selected type retained for its first ordering key. The final consumer audit reproduced two additional public SQL failures: numeric range spellings with a combined frequency of four lost to a different range occurring three times. The former value-only comparison split the first group even though its sort already used selected range ordering. Reusing that ordering type corrects the frequency boundary in memory and spilled runs.

The final aggregate review reproduces four more failures in JSON/JSONB object aggregates with DISTINCT range arguments. Their internal argument list lacked field types even when the surrounding sort retained scalar types. The template now captures every argument type once; the DISTINCT tie-breaker stores individual argument keys after explicit ordering keys. Adjacent equality uses those same types, while transition callbacks receive the unchanged original tuple. The template also restores the tuple arity alongside its shared types. This covers registered aggregate tuples and the existing multi-argument built-ins without changing their public carriers.

## Preservation argument

For a resolved native range type $T$, let $R_T(v)$ be SQL's existing admitted range reader, and let $K_T(v)$ be the already implemented nested-range exact encoding of $R_T(v)$. For every pair of admitted values of $T$, the existing range comparison/key contract gives $K_T(a)=K_T(b)$ exactly when the PostgreSQL range comparator returns equality. The scalar correction supplies the previously discarded $T$ and calls that same writer. Therefore it restores the same equivalence relation at the scalar boundary without defining another normalization or comparison algorithm.

For positional keys, the existing row count, component type tags and length framing are preserved. Equal complete keys therefore require equal selected components, including existing NULL framing. The in-memory set and spill set both compare these complete byte keys, so replacing one representation by the other cannot change the selected equivalence classes. DISTINCT emits the first input row for each class; it does not rewrite that row's numeric scale, range spelling or bound values. Applying the same reasoning to evaluated DISTINCT ON keys preserves first-row selection under their existing input order. The ordered implementation now retains the same selected types in both its sort and adjacent-equality consumers. Lexicographic ordering consequently makes each selected equality class contiguous, adjacent comparison keeps its first member, and the unchanged ordinal sort restores first-input order. Key values and the ordinal representation are unchanged; a single row still does not invoke comparison or read a malformed physical key. The existing lazy-read test and independent range matrices verify that boundary.

When a selected type is absent or is unrelated to ranges, the new adapter calls the unchanged value encoder. A TEXT value that looks like a range consequently remains TEXT. A domain over a range uses its already admitted base representation; observation performs no new domain constraint check. The controlled entry point forwards the same allowance and cancellation owners to the selected reader and output. On failure all temporary owners unwind; only completed key output escapes. These changes add no algebraic operator and leave document support, row payloads, scores and persistent index bytes unchanged. Group hash hits use the same selected comparator to resolve collisions. Partial-group metadata preserves physical/internal columns independently of SQL-visible columns. Ordered merges and exact-key merges therefore combine exactly the same equivalence classes; aggregate counts sum their existing multiplicities, joins retain their Cartesian multiplicities, and set operations retain their existing set/bag multiplicity rules. Streaming hashes keep their existing writer call boundaries; congruence is checked between SQL-equal values, without assuming that an arbitrary Hasher treats one concatenated write identically to several writes.

MODE counts the contiguous equality classes established by the same selected sort. Its unchanged maximum-frequency and first-on-tie rules therefore select the PostgreSQL class regardless of input spelling, sort direction or spill. It retains an existing input representation and preserves NULL exclusion; the correction adds no key allocation or additional pass.

For an argument tuple with types $T_1,\ldots,T_n$, equality is the product $\bigwedge_i E_{T_i}(a_i,b_i)$, including the existing NULL equivalence. Lexicographic ordering of the individually selected argument keys makes these classes contiguous after the explicit aggregate ordering prefix. The same component equalities remove adjacent duplicates, so memory and spill retain one unchanged argument tuple per class. Types and arity remain template metadata; every retained sort value still enters the existing byte-accounted buffer and merge path.
