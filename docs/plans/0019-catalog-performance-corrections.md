## Ownership and verification

Execution owns catalog identities, virtual-row production, derived metadata and DDL algorithms. SQL owns type identity and semantic rules; Planner owns constant simplification of analyzed RULE conditions. Engine supplies catalog/session/transaction adapters and retains the requested immutable generation. The Execution, SQL, Planner and Engine manifests, enabled features, dependency policy and manual ownership boundaries have been inspected; these corrections require no new dependency or feature edge.

Use deterministic work counters and synthetic fixtures in the existing owning-crate test targets to prove the eliminated work, with semantic assertions and existing concurrency/restoration regressions. Run focused local checks once the affected unit is ready, then normal pushes drive automatic CI. Timing acceptance uses only the controlled runner and its independent noise bound; generated reports and diagnostic traces remain ignored artifacts. The source-identified catalog defects do not depend on waiting for the timing investigation.

## Type occupancy preservation

For a retained catalog generation $C$, let $B$ be its database-independent builtin type identities, $U(C)$ its domain, enum and standalone-composite identities and arrays, and $R(C)$ its relation and graph-label row/array identities. Type occupancy is membership in $B\cup U(C)\cup R(C)$. Reading these identities directly must return the same membership as the complete type projection and explicit relation/graph claims, without allocating or formatting unrelated result rows. The builtin set is immutable; user identities are read from the caller-selected generation rather than a global mutable cache. Allocation still checks occupancy before acquiring its object lock and after refreshing shared state following the wait. Thus an unchanged catalog yields the same selected address, while a newly occupied address is rejected before retention. Transaction/savepoint lock ownership, cancellation and rollback remain with the existing reservation owner; no query, payload or scoring operation changes.

### Scoped catalog callbacks

A callback created after its original scope became stale selects current inputs instead of labeling the old scope with a new revision. Domain signature matching borrows the selected domain allocation directly. Read-only view analysis receives the catalog already selected by its caller; DML and restoration keep their existing fresh-definition interfaces. SQL view contexts distinguish routine resolution from the catalog metadata reader. Execution caches selected relation descriptors in their immutable catalog generation, with only one missing OID retained so arbitrary absent probes cannot grow the cache. Bound type names continue to use the original query scope. Runtime inquiries retain current role/search-path behavior and refresh after private DDL and rollback; portal workers continue to supply their original catalog.

For a runtime read at revision $r$, the adapter supplies the retained catalog $C_r$ until a catalog change invalidates $r$. The next inquiry selects $C_{r+1}$ from the same Engine source as before, while a portal's source remains its pinned generation. Repeated inquiries therefore observe the same definitions without rebuilding the table map. Permission decisions still run through Execution's existing ACL owner with the invoking role, and every descriptor is derived solely from its owning immutable view. No relational, graph, payload or scoring operation changes. ### DDL and restoration snapshots

The #663 correction separates catalog synchronization from query-view capture; deletion and domain validation still select the current definition view after synchronization and retain the original post-lock convergence loop. Key-name projection validates every persistent key owner using borrowed metadata, retains the original view when names are unchanged and copies only changed key or inherited-key collections otherwise. Partition naming borrows the existing private candidate instead of cloning its complete table map for each child; the original catalog still supplies the same graph definitions without adding query read attribution, and the earlier children's names remain visible. Deliberate private candidate isolation is retained.

For a selected generation $C$ and the name registry $N$, projection validates the same relation, table-incarnation and constraint identities before returning the same named declarations. If no name differs, its result is $C$ itself; otherwise its new table map shares every unchanged collection with $C$. Changing a candidate never changes $C$. Refresh-only calls preserve synchronization order and errors, while the caller still chooses between the retained query view and current DDL definitions. No SQL, storage format or algebraic operation changes. The final focused run passes 26 Execution tests and 203 Engine tests, covering unchanged and changed allocations, malformed owners, temporary tables, partition identity, lock waits, private DDL, savepoints, rollback and native SQLite/SQLite Key/Value/redb restoration. PostgreSQL 18.4 in Docker independently confirms colliding long partition names, constraint rename rollback and both outcomes of domain validation after a relation-lock wait: committed violating data fails with SQLSTATE `23514`, while rolled-back data permits validation. Strict Execution/Engine library and test Clippy, rustfmt, dependency/ownership, harness, header, file-size and deterministic-inventory checks pass. Four work-count regressions are included in the automatic Linux/macOS inventory. These checks establish eliminated copies and behavioral preservation, not elapsed-time acceptance; #659, #662 and #653 retain their separate completion requirements.

### Validated index inquiries

The next #662 unit retains the validated index relation collection in its immutable catalog view. `pg_get_indexdef`, named index resolution and relation-OID fallback use OID/name maps; complete catalog, constraint, dependency and restoration consumers borrow the same collection. Initial derivation still decodes and validates every index in the original order, including table incarnations, owning constraints and parent identities. It remains linear in the number of indexes. Subsequent inquiries use logarithmic map lookup without decoding or cloning the collection; this is a retained-generation improvement, not a claim that a new cold catalog requires no work. Legacy initial restoration retains its separate conversion path.

Let $I(C)$ be the ordered validated index collection of immutable catalog $C$. The retained value is exactly $I(C)$, and the OID/name maps select the first matching position as the original search did. They are built only after complete validation succeeds, so errors retain their original order and failed attempts publish no partial result. A new catalog view owns another derivation, while older views continue borrowing their unchanged $I(C)$. Formatting and schema visibility still use the caller's current resolution. Consequently every inquiry and full projection returns the same metadata, with no change to relational, graph, payload or scoring operations.
