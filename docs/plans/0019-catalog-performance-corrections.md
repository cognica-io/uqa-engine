## Ownership and verification

Execution owns catalog identities, virtual-row production, derived metadata and DDL algorithms. SQL owns type identity and semantic rules. Engine supplies catalog/session/transaction adapters and retains the requested immutable generation. The Execution, SQL and Engine manifests, enabled features, dependency policy and manual ownership boundaries have been inspected; these corrections require no new dependency or feature edge.

Use deterministic work counters and synthetic fixtures in the existing owning-crate test targets to prove the eliminated work, with semantic assertions and existing concurrency/restoration regressions. Run focused local checks once the affected unit is ready, then normal pushes drive automatic CI. Timing acceptance uses only the controlled runner and its independent noise bound; generated reports and diagnostic traces remain ignored artifacts. The source-identified catalog defects do not depend on waiting for the timing investigation.

## Type occupancy preservation

For a retained catalog generation $C$, let $B$ be its database-independent builtin type identities, $U(C)$ its domain, enum and standalone-composite identities and arrays, and $R(C)$ its relation and graph-label row/array identities. Type occupancy is membership in $B\cup U(C)\cup R(C)$. Reading these identities directly must return the same membership as the complete type projection and explicit relation/graph claims, without allocating or formatting unrelated result rows. The builtin set is immutable; user identities are read from the caller-selected generation rather than a global mutable cache. Allocation still checks occupancy before acquiring its object lock and after refreshing shared state following the wait. Thus an unchanged catalog yields the same selected address, while a newly occupied address is rejected before retention. Transaction/savepoint lock ownership, cancellation and rollback remain with the existing reservation owner; no query, payload or scoring operation changes.

### Scoped catalog callbacks

The #660 correction records source identity and invalidation revision when a query captures its catalog, and retains runtime callback inputs until that revision changes. A callback created after its original scope became stale selects current inputs instead of labeling the old scope with a new revision. Domain signature matching borrows the selected domain allocation directly. Read-only view analysis receives the catalog already selected by its caller; DML and restoration keep their existing fresh-definition interfaces. SQL view contexts distinguish routine resolution from the catalog metadata reader. Execution caches selected relation descriptors in their immutable catalog generation, with only one missing OID retained so arbitrary absent probes cannot grow the cache. Bound type names continue to use the original query scope. Runtime inquiries retain current role/search-path behavior and refresh after private DDL and rollback; portal workers continue to supply their original catalog.

For a runtime read at revision $r$, the adapter supplies the retained catalog $C_r$ until a catalog change invalidates $r$. The next inquiry selects $C_{r+1}$ from the same Engine source as before, while a portal's source remains its pinned generation. Repeated inquiries therefore observe the same definitions without rebuilding the table map. Permission decisions still run through Execution's existing ACL owner with the invoking role, and every descriptor is derived solely from its owning immutable view. No relational, graph, payload or scoring operation changes. PostgreSQL 18.4 in Docker independently confirms table-column updatability, EXECUTE privilege revoke/rollback, and a volatile function's newly created schema being visible to the following `current_schema()` expression in both returned rows. The final focused run passes 250 Execution catalog tests and 25 Engine catalog/state tests, including the late-created callback regression. Strict Engine/Execution/SQL library and test Clippy, rustfmt and ownership/dependency checks pass. Fresh PostgreSQL 18.4 sessions also confirm next-command visibility of peer schema creation in READ COMMITTED, REPEATABLE READ and SERIALIZABLE; the matching Engine test covers all three persistent providers.

The broader integration run passes 64 of 65 tests.
