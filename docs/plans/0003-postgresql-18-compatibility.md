# PostgreSQL 18 compatibility plan

Status: Active living plan

Update rule: Update this plan, its synchronized status ledger, the manual, and `tests/parity/pg18/manifest.json` in the same compatibility PR whenever supported behavior or a remaining gate changes.

## Goal

The long-term goal is complete PostgreSQL 18 compatibility at every externally observable boundary: SQL parsing and execution, data types and casts, catalogs, errors, transactions and concurrency, frontend/backend protocol 3.0 and 3.2, and behavior seen by standard PostgreSQL clients. UQA Engine may retain its own internal storage and execution architecture, but an implementation difference is not a reason to expose different PostgreSQL behavior.

This plan distinguishes a PostgreSQL 18 baseline from complete compatibility. The baseline is reached when PostgreSQL 18 grammar, metadata, fixtures, and protocol primitives are authoritative and every unimplemented PostgreSQL 18 shape fails explicitly. Complete compatibility is reached only when the PostgreSQL 18 regression, isolation, protocol, catalog, and client matrices pass without semantic exemptions.

## Non-negotiable rules

- Parser acceptance is not execution support. Every newly accepted AST field must be implemented or rejected before any state change.
- Workarounds are prohibited. A compatibility defect must be fixed at the owning parser, type, catalog, planner, executor, storage, or protocol boundary; source rewriting, silent normalization, test-only behavior, and local dependency overrides are not shippable implementations.
- Silent approximation is a compatibility bug. This includes dropping `RETURNING` aliases, enforcing a `NOT ENFORCED` constraint, selecting a text overload for `bytea`, or omitting catalog state.
- PostgreSQL 18 is the differential oracle. Checked-in fixtures record the exact PostgreSQL server version, architecture, query text, columns, ordered rows, NULLs, value types, errors, and SQLSTATE where applicable.
- Historical PostgreSQL 17 measurements remain historical evidence. Active fixture names, paths, defaults, tests, and compatibility prose move to `pg18`; old benchmark and changelog facts are not relabeled.
- Protocol 3.0 remains supported while protocol 3.2 is added. Version negotiation and unsupported `_pq_.` options must follow PostgreSQL rather than relying on the current libpq default.
- A compatibility claim is no broader than its passing evidence. The manual must identify the current milestone until the complete-compatibility gates pass.
- Add every newly confirmed compatibility gap to the manifest and this plan immediately with an incomplete status; promote it to `verified` only after focused tests and the PostgreSQL 18 differential oracle pass.

## Current implementation status and open PostgreSQL 18 bugs

The historical starting point used `pg_query` 6.1.1 with PostgreSQL 17 grammar, reported `server_version` as `17.0-uqa`, stored the active TPC-H-derived oracle in `expected/pg17.json`, and accepted only frontend/backend protocol 3.0 primitives. Active assets now use `pg18`, session metadata reports `18.0-uqa`, and the checked-in 22-query oracle records PostgreSQL 18.4 server and platform provenance.

The PostgreSQL 18 parser migration replaces the four DML `returning_list` fields with complete `returning_clause` handling. PostgreSQL 18's PL/pgSQL JSON producer also needs to serialize `retvarno` for datum-backed `RETURN` and `RETURN NEXT`; UQA Engine consumes those slots directly and does not rewrite routine source. The reproducible parser chain is imported as the `uqa-pg-query` workspace crate from `jaepil/pg_query.rs@50329932e504c8ad96208a3bbafdec7d9fdaf81d` and `jaepil/libpg_query@a5356d05a1269f2982b906611d7e545c550bb369`; the latter contains the PostgreSQL 18 parser, corrected PL/pgSQL datum serialization, structured `%TYPE` and `%ROWTYPE` identifier metadata, trigger-promise and type-cache fixes, and a process-wide pthread exit key with a `PTHREAD_KEYS_MAX + 1` regression test so one integration-test executable can safely create parser threads throughout its lifetime.

## Domain constraint lifecycle preservation

The ALTER DOMAIN lifecycle retains the domain's OID, its base conversion, existing constraint identities and every stored value. Let $V$ be the existing value carrier and $C=[c_1,\ldots,c_n]$ its ordered domain checks. After base conversion, a domain conversion returns its input $v\in V$ exactly when each CHECK evaluates to TRUE or NULL and the NOT NULL condition holds; otherwise it raises the first violation. Adding a CHECK inserts it into the same name order, dropping one removes only that check, and validation changes only its catalog validation flag. Thus the value carrier and its existing equality, comparison, hashing and relational operations are unchanged; only the explicitly requested domain-conversion acceptance predicate changes. For checks with stateful functions, the statement evaluates each selected check in the same order and with the same borrowed value, preserving the existing function and transaction effects rather than treating those checks as pure predicates.

Existing-value validation applies the newly selected check to each directly typed value, including derived domains, and never converts or rewrites the value. It neither repeats older checks nor changes their effects. NOT VALID deliberately leaves old values unvalidated while imposing the same check on subsequent conversions; marking a check validated requires a successful scan. A failed statement restores the catalog through the existing transaction boundary, whose established treatment of nontransactional sequence effects is unchanged. A successful statement preserves all preexisting values except for effects explicitly performed by the selected CHECK itself; such functions keep the normal statement and transaction semantics. Relation locks retain each inspected identity through publication, and validation's latest-row selection is separate from ordinary query snapshot selection. Each relation retains its latest immutable storage snapshot before evaluating rows, so a CHECK callback cannot insert new rows into its own validation scan. This follows PostgreSQL 18's [per-relation validation snapshot](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/commands/typecmds.c). These observations establish preservation of UQA's existing value and relation operations without introducing an algebraic operator or an optimizer rewrite.

### Prepared input preservation argument

Let $S$ be the retained source tree, $C$ its analysis catalog and $t$ its analysis clock. For each unknown string leaf $x$ whose context selects an implemented input type $T$, SQL analysis computes $I_T(C,t,x)$ in expression-analysis order and retains that typed value in $A_{C,t}(S)$. A later execution with parameters $p$, execution catalog $C'$ and clock $t'$ evaluates this analyzed tree; parameter conversion, ordinary function calls and domain constraints remain at their existing execution boundaries. In particular, a domain input retains its base-type value while the enclosing domain coercion still consults the execution catalog. This separates PostgreSQL's analysis-time observation from its execution-time observation without introducing a new UQA operator.

For fixed analyzed inputs, replacing an input leaf by the value its input function already returned preserves its value and type. Induction over the scalar and relational trees then preserves each existing operator's complete operands and results, including decorated payloads and scores, because no operator implementation or evaluation order changes. Runtime parameters and functions are not substituted by this rule. Invalid input fails at the same ordered analysis point; query optimization remains after preparation. Thus every existing composition observes the same typed operands that PostgreSQL's retained analysis exposes, and all algebraic laws that the existing operators satisfy remain unchanged. This argument does not claim new laws for payload merging or ranked results.

A selected relation or routine replacement makes the analyzed tree stale; namespace catalog invalidation and a different effective search path also require analysis. Exact record identities distinguish equal-content replacements, while unrelated records and data changes leave them equal. Local publication events remain pending across transaction and savepoint completion, so rollback cannot erase a required invalidation and a statement prepared after a private DDL change still sees its completion. Reanalysis starts from $S$, recomputes its inputs under the new analysis context, checks the original fixed result descriptor and publishes only against the same retained definition identity. Domain-check execution invalidation alone rebuilds the executable plan from $A_{C,t}(S)$, preserving its input observations. ### Original-row rewrite preservation argument

For each affected relation $R$, let $S_R$ be the ordered rows visible when that relation's physical rewrite starts, and let $D_R$ be its original column descriptor. Analysis fixes the source slots of every transform before any declaration changes. For original row $r\in S_R$, effectful evaluation is $\operatorname{eval}(e_i,D_R,r,\sigma_{i-1})=(v_i,\sigma_i)$, where $\sigma_i$ carries transaction and routine side effects. Actions run in their written order, never using $v_j$ as the source row of a later action; this does not assert that volatile expressions commute. The replacement row retains surviving original slots, applies those assignments in order, then fills added defaults and computes stored generation expressions. Induction over the action queue therefore preserves the same original input for each expression, including repeated targets, while the last assignment to a destination determines that destination's value. Dropping a name does not remove its retained old slot; a newly added column with the same name has a different immutable column identity and cannot provide that slot.

All affected relation identities are locked before declaration publication. Traversal records each identity once, so a diamond reaches its shared child exactly once. Child analysis uses that child's descriptor, making field-name binding independent of its physical column order. The outside-parent check rejects a type change that would leave an unaffected supplying parent inconsistent. Before rewriting a later relation, only surviving transaction changes after the retained log marker are reconciled into its original slots; rolled-back frames contribute no changes. Within a relation, evaluation reads its captured input and publication replaces the current physical rows with precisely the validated replacement rows, so self-inserts and self-updates cannot alter that input. Completed writes to other relations retain their ordinary transaction effects.

Typed spill encoding is an exact representation of row values and full-width document identities, not a new relational or scoring operator. Replay preserves each row and its order; sorted callback identities preserve the final insert/update/delete presence for each identity. All resident input, output and callback-index reservations charge the same statement allowance, and encrypted spill retains excess records. Key relocation changes only the physical address of a row; external uniqueness validation checks the complete replacement relation before publication. Row-local checks precede global key checks, and affected foreign keys are validated after the relations are replaced. Existing statement/savepoint rollback restores catalog, rows and indexes when any step fails. Consequently relational observations and existing retrieval compositions over unchanged fields retain their meanings; this correction changes only the PostgreSQL-incompatible sequential rewrite behavior.

Row storage grows on disk with the retained data while resident buffers remain bounded by the original allowance; replay additionally holds the current decoded row and existing provider workspace. Each original row evaluates its scheduled transforms once. Reconciliation visits the surviving transaction log separately for each affected relation and merges its changed identities in order; this can cost the number of affected relations times the log length. The reference and resource tests establish correctness and retained-memory behavior, not a timing or throughput improvement.
