# Bit-string input and consumer acceptance

This prerequisite fixes [#914](https://github.com/cognica-io/uqa-engine/issues/914) inside original record 64 and [PR #911](https://github.com/cognica-io/uqa-engine/pull/911). The original composite-consumer reference retains all thirteen previously failing bit/varbit observations; the integrated implementation now passes the full 172-observation reference on all four providers, including persistent reopening. A carrier or parser-only change is not completion.

## Ownership and representation

Core owns a packed finite bit sequence, its canonical representation, equality/order/hash and controlled copies. SQL owns BIT/VARBIT identity, declared modifiers, binary/hexadecimal text input, assignment versus explicit casts, operators, physical Datum interpretation and diagnostics. Execution consumes selected SQL equality, hash and retained result metadata; Engine supplies session, provider and reopen adapters. Inspected manifests and the dependency policy allow SQL to use Core; no reverse dependency or new Cargo feature is required.

`BitStringValue` stores most-significant-bit-first bytes and the exact logical bit length. The final byte's unused low bits are zero and no excess bytes are accepted. This retains one byte per eight input bits without conflating a bit string with ordinary text or BYTEA. The dynamic `Value::BitString` variant now retains that owner across controlled copies, tagged JSON, native SQLite document/index values and Execution binary spills. SQL keeps fixed/varying identity and length constraints in `ColumnType`, array element OIDs and record field descriptors, independently of this shared physical carrier. Public-provider and binding execution remain separate acceptance requirements.

## Preservation argument

Let $B=\{0,1\}$ and let $B^*$ be the finite bit sequences representable by the length field. For $s\in B^*$ of length $n$, define $P(s)$ as $n$ together with $\lceil n/8\rceil$ bytes, filling each byte from its most significant bit and setting every unused low bit to zero. The inverse reads exactly the first $n$ bits. Therefore $P$ is injective and surjective onto the admitted packed representations: unpacking $P(s)$ yields $s$, and packing an admitted representation's logical bits yields its original bytes and length. Constructors and deserialization reject values outside this image instead of silently normalizing them.

Equality of admitted packed values is equality in $B^*$. Lexicographic byte comparison followed by logical length comparison is the same lexicographic bit order with $0<1$: the first differing logical bit has the greatest positional weight among the remaining bits of its byte; if one sequence is a prefix, zero padding cannot reverse that order, and either the first nonzero suffix bit or the length tie-breaker places the extension after its prefix. Thus the comparison is total, antisymmetric and transitive, and equality agrees with both comparison and hashing. Bounded-chunk comparison uses the same ordered byte partitions and performs no value transformation, so cancellation checks do not change completed observations.

The controlled constructor transfers the already-owned packed allocation and its reservation. Copying admits the destination before allocation and retains that reservation until the copied value is released; failed validation, quota failure and either caller's cancellation release partial owned state. These operations do not mutate their inputs. The standalone carrier adds no operation on document support, payload merging, scoring or ranked results, so those existing UQA carriers and laws remain unchanged. The dynamic integration appends a distinct Core tag and preserves every existing variant tag and comparison rule.

SQL length semantics are a separate boundary: a fixed-length assignment requires exact length, a varying-length assignment permits at most the declared bound, and explicit casts can truncate or right-pad according to the target family. These are not equality normalizations and must not change the logical value retained by an ordinary read. The independent PostgreSQL probe also distinguishes the BIT keyword's default length of one from unmodified quoted/catalog `bit`, which has no length constraint. See PostgreSQL's [bit-string contract](https://www.postgresql.org/docs/18/datatype-bit.html) and [type implementation](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/utils/adt/varbit.c).

For a positive modifier $n$, define the fixed assignment domain $F_n=\{s\in B^*:|s|=n\}$ and the varying assignment domain $V_n=\{s\in B^*:|s|\le n\}$. Assignment is the identity on its domain and reports the selected family’s length error outside it. Fixed explicit coercion $P_n(s)$ takes the first $n$ bits and appends zeroes if $|s|<n$; varying explicit coercion $T_n(s)$ takes the first $\min(n,|s|)$ bits. Consequently $P_n$ maps into $F_n$, $T_n$ maps into $V_n$, and both are idempotent. Also $T_m(T_n(s))=T_{\min(m,n)}(s)$, by taking the same prefix. Fixed coercions of different lengths do not generally commute, so no such rewrite is permitted. These are explicit value transformations, not changes to equality or hashing of an existing value.

SQL input expands every hexadecimal digit into its four most-significant-first bits, or consumes binary digits directly, then applies the packed bijection above. Each destination byte combines disjoint digit positions with bitwise OR; no positions overlap, and the final unused positions remain zero. Length-constrained input validates its byte-derived logical length before checking digit validity; explicit text casts instead validate the entire unconstrained input before coercion, including digits outside the eventual retained prefix. This distinction preserves both successful values and the observed error ordering. Output reads the same logical positions and is therefore the inverse binary spelling, including leading zeroes and empty input.

For an integer $a$ and result width $n$, integer-to-bit conversion emits $a\bmod 2^n$ as exactly $n$ bits; arithmetic sign extension supplies positions beyond the original signed width. Widening an int4 to int8 preserves this residue, so both callers share one conversion kernel after their own integer-range checks. A bit string of at most $w$ bits converts to its unsigned positional sum, interpreted as a signed two’s-complement integer only when its width is exactly $w$; longer inputs report the corresponding integer-range error. The implementation admits packed destination bytes before production and never expands an intermediate bit-per-byte buffer. Retained source and destination leases remain independent, and all failing paths release their partial destination.

## Dynamic values, physical retention and consumer preservation

Let $D$ be the previous dynamic-value domain and form the disjoint union $D\sqcup B^*$. The new variant has its own tag, so its inclusion is injective and no bit value equals a previous string, byte sequence or number. On $D$, all previous discriminants and operation branches remain unchanged. Structural values apply the existing ordered traversal to their children; by induction on finite container depth, replacing a child by its bit inclusion preserves every unrelated child, container position, field identity and NULL observation. Fixed and varying SQL declarations share the bit sequence but retain distinct type OIDs in their descriptors; reached record fields therefore still perform the original type-identity check before value comparison.

The tagged codec writes a distinct type name, exact logical length and hexadecimal spelling of the canonical bytes. The spill codec writes a previously unused binary tag, length and a framed byte sequence. Each decoder validates the packed representation before admitting a value. Their decoding and encoding compositions are identities on admitted bit values by the packed bijection; the existing container codecs preserve this identity by structural induction. The physical SQL payload adds a four-byte logical length inside the existing owned varlena boundary. Reads admit only the packed destination and reject length/data outside that boundary; lazy unobserved fields retain their original bytes. Native SQLite's separate stored-value enum carries the same validated owner, while serialized providers use the Core tagged codec. SQLite record format 63 and redb record format 59 exclude owners that do not recognize this new value or descriptor; initial format conversion leaves existing user values unchanged.

An Execution exact key is a distinct bit tag followed by its logical length and framed canonical bytes. Equality of such keys is therefore equivalent to equality of bit sequences, including sequences with identical packed bytes and different lengths. Hashing streams this same key, so equal SQL bit values have equal hashes; collisions still require the existing exact comparison. Physical Datum consumers decode to the same admitted sequence before hashing. DISTINCT, grouping, joins, sets and reservations keep their existing state operations and only gain this injective key component. Spilling and restoring an admitted component commutes with comparison and exact-key construction because its round trip is the identity. Packed allocation capacity is charged by Core and by both existing aggregation retention estimators; output remains charged separately when expanded into text.

Local language adapters render the complete binary spelling as a string; that spelling is injective on $B^*$ and preserves leading zeroes and logical length. SQL result metadata continues to distinguish fixed and varying declarations. The existing HTTP parameter protocol has no bit variant: the Rust client rejects a direct or nested bit carrier before sending a request, rather than silently transmitting a differently typed parameter. Text parameters with an explicit SQL cast remain the existing wire contract. Runtime binding validation is still required before claiming parity.

Optional foreign transports retain their own capability boundary. The pinned DuckDB Rust parameter enum has no bit-string variant, and the dialect-independent Flight literal encoder has no negotiated bit type. Both reject direct or nested packed bit parameters through their existing typed unsupported-value errors; they do not replace a bit string with text or bytea, which would erase its type or logical length. Every previous variant follows its existing branch, and recursive arrays/lists propagate the same error before producing a transport value. The independently enabled Arrow and DuckDB configurations exposed missing exhaustive matches in automatic CI; all forty FDW owner tests pass with both handlers enabled after correcting those matches, including empty bits and equal padded bytes with different logical lengths.
