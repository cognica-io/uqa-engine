# Retained relation columns in scalar-subquery correlation

Issue [#1175](https://github.com/cognica-io/uqa-engine/issues/1175) was reproduced while verifying #714 on memory, native SQLite, SQLite Key/Value and redb. A trigger's `INSERT ... VALUES` expression reads `SUM(a)` from an OLD or NEW transition relation. The runtime correlation adapter supplies the persistent catalog but omits the retained relation descriptor, so SQL classifies the local `a` as an outer reference and Execution rejects the absent positional outer row. The existing missing-outer-row error is correct for genuinely correlated plans and remains in place.

SQL now accepts a borrowed `CorrelationRelations` view in its existing correlation context. Execution lends descriptors already owned by the invoking CTE scope to both ordinary correlation classification and EXISTS decorrelation. Engine and Planner retain their existing catalog-only contexts; they do not implement correlation analysis. Relation rows are not read or copied to supply this metadata. No Cargo dependency, feature, authorization decision or catalog lifetime changes.

For each source name, local WITH declarations take precedence, then an exact retained relation name, then the original persistent/virtual catalog lookup. Source aliases and positional column aliases apply at their existing boundary. Explicitly qualified physical names do not match an unrelated unqualified retained name. Within a query scope, a column present in this source metadata is local; a column not resolved in any enclosing analyzed scope remains an external reference. Supplying the descriptor therefore corrects the false outer dependency without suppressing an actual outer dependency or changing row lookup, SQL value computation, cardinality checks, NULL semantics or error evaluation order. Source descriptors and scalar-subquery cache entries retain the same invoking execution scope.

The SQL-owner regression covers unqualified and qualified local fields, positional aliases, genuinely outer fields, explicitly qualified physical names and local CTE shadowing. The public Engine case uses two cascading foreign keys and 32KiB child rows under 64KiB query memory; six original row events and one coalesced statement event must match independently captured Docker PostgreSQL 18.4 output, with rollback and persistent reopen on all four providers. Reference SQL SHA-256 is `051c155269b5a15e3b133daed516238e8a0fd1873cca1f863cc017be61b91af9`; output SHA-256 is `134b198548195dc13bbd7eec3e76abc2600c9f679c79317cbc10cc1720459407`. The reference transaction creates and rolls back its own schema. All 267 integrated local cases pass, including SQL correlation owners, Execution cache/cancellation consumers, rewrite rules, triggers, foreign keys and the four-provider PostgreSQL reference case.
