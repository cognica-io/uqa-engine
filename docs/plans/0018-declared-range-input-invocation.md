## Ownership and selection

SQL owns the cast boundary and reuses its existing range grammar, typed input, comparison, multirange normalization and physical producers. Unknown/string inputs call the declaration's input; same-type physical values remain binary identities, including a domain-to-base relabel, without reading a lazy payload. Distinct range identities cannot become aliases solely because their endpoint types match. Arrays use the existing catalog-aware element cast and preserve their dimensions and NULL members. Catalog constants retain the input result instead of repeating effects when the stored expression executes.

Execution borrows the range definition and value descriptor from the pinned catalog generation. Endpoint type names use immutable type identities rather than mutable spelling. Its `RangeConstruction` implementation delegates each finite endpoint to the established SQL cast owner, uses the selected comparison and range support state, and encodes a nonempty argument only when the definition names a canonical routine. The routine owner borrows the selected function through the generation's existing OID index and invokes the existing interpreter as a catalog callback. It passes an already admitted argument without repeating input or domain checks. Engine supplies catalog/session/transaction and interpreter adapters; no parsing, ordering, normalization or codec algorithm is implemented there. Cargo features and dependency direction are unchanged.

PostgreSQL's [range input and make_range implementation](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/utils/adt/rangetypes.c) parses syntax before endpoint input, reads the lower endpoint before the upper endpoint, serializes before canonicalization, and skips canonical functions for empty ranges. Its catalog callback does not recheck the routine's EXECUTE privilege; ordinary explicit calls still do. The optional callback's result is observed and serialized without calling canonicalization a second time. SQL NULL from the callback reports XX000 with the selected function OID. A subtype-difference routine is not an input operation and is not invoked by this boundary.

## Preservation argument

Fix an immutable definition $r=(T,C,L,F)$ and a valid input text $s$. SQL's existing grammar yields an empty value or ordered endpoint strings $(l,u)$ and flags $b$. The adapter evaluates each present endpoint through the previously selected input $I_T$, giving $a=I_T(l)$ and $z=I_T(u)$ in that order; missing endpoints cause no type input. It then delegates to the existing constructor $R_r(a,z,b)$, whose proof covers ordering, emptiness, optional canonicalization and multirange normalization. Thus the adapter introduces no alternative ordering or set algebra: it composes the original constructor with the definition's selected operations.

Let $E_r$ be the already verified declared physical encoder and $D_r$ the admitted observer. The final result is $E_r(R_r(a,z,b))$. For successful in-bounds values, the existing codec argument establishes $D_r(E_r(x))=x$ with the same range identity and typed endpoints. Encoding and identity casts do not call $I_T$ or $F$. Consequently input/canonical effects occur exactly at the constructor's established boundaries, even when they are not pure or idempotent; no algebraic rewrite assumes otherwise. Range and multirange equality consumers continue using the same selected comparison and exact keys.

Every grammar buffer, endpoint, normalized member, callback argument and physical output is admitted under the supplied production control. The argument owner remains live during callback execution; callback output passes the existing external-value retention boundary before controlled observation. Catalog definitions and routine metadata retain their established generation owners rather than masquerading as per-value scratch. Both cancellation owners are checked by the shared production operations. Failures release in-flight values before their leases; successful return retains only the produced output's ownership.
