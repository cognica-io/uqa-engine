# Declared range catalog generations

This is the durable catalog boundary of original record 65, following [physical production](0018-declared-range-encoding.md). It connects stored range definitions to retained Engine generations and SQL value observation. SQL `CREATE TYPE AS RANGE`, generated constructor routines, selected comparison/canonical invocation and complete lifecycle DDL remain required work; this internal catalog interface does not complete record 65 or advertise those SQL statements.

## Ownership and representation

SQL owns `StoredRange` and its independently named `StoredMultirange`, structural identity validation and type metadata. A definition retains four distinct type OIDs, two object incarnations, two array names, the range owner and ACL, its bound endpoint type, selected operator-class/collation OIDs and optional canonical/difference routine OIDs. No support object is inferred again from an endpoint's spelling. In particular, an integer endpoint does not imply the native integer range's canonical function.

Execution owns versioned records, exact OID claims, publication, private-record reconciliation, descriptor derivation, type lookup and catalog projections. A complete catalog validation rejects range OID/name collisions with other type families and missing or self-referencing endpoint types. The catalog emits the four PostgreSQL type rows and the definition-derived `pg_range` row. Arrays depend internally on their elements and the multirange depends internally on its range; the range owns shared role and ACL dependencies. Multirange usage inquiries follow the primary range's ACL, while its own `pg_type.typacl` stays NULL. Constructor routine records are independent objects and are not synthesized from a renamed type.

Engine adds only the durable registry cell, snapshot/restore and private-refresh adapters, publication adapter and value-layout lookup. Algorithms and their tests remain in SQL and Execution. No dependency edge or Cargo feature changes. Existing databases without declared ranges allocate no range descriptor cache and skip complete range-claim validation.

## Preservation proof

Let a valid registry $C$ be a finite map from qualified primary names to definitions. For each definition $r$, let $O(r)$ be its four distinct type OIDs and $N(r)$ its four qualified names. Validation requires disjoint $O(r)$ and $N(r)$ across definitions and other catalog types. Define $L_C(o)$ as the descriptor selected by either the range or multirange OID of $r$, and undefined otherwise. Because the OIDs are disjoint, $L_C$ is a function. Both primary OIDs select the same immutable descriptor; generated array OIDs are resolved by the array owner and never masquerade as range layouts.

A catalog generation is immutable. Renaming a primary or multirange name changes $N(r)$ but preserves $O(r)$, endpoint layout and selected support identities. Thus lookup through a retained OID, physical decoding and every previously admitted value observation are unchanged: $D_{L_C(o)}(v)=D_{L_{C'}(o)}(v)$ whenever only names or authority change. A retained generation keeps its original map even after a newer generation drops or replaces an object. A replacement with a separately allocated OID cannot satisfy lookup of the original OID merely by acquiring the old name. This preserves the typed values consumed by comparison, exact keys and output without rerunning input, domain constraints or canonical functions.

Serialization stores every definition and exactly its four OID claims under one version marker. Deserialization checks the marker, claim bijection and structural authority before publication. Consequently, for every admitted registry, restoration after successful publication yields the same identities and selected metadata. Unknown formats, absent claims, surplus claims and conflicting names have no published interpretation. Shared provider transactions make failed writes and enclosing rollback atomic; the storage format fence prevents older owners from ignoring the new records.

Publication assumes that the declaring owner holds the required definition/identity locks and has refreshed its inputs after any wait. Each changed map entry is replaced only if its current value equals the statement's original value. A stale replacement fails, while changes to disjoint names commute: applying either order produces the union of both independent changes. During refresh, provider-reported private keys select this transaction's replacement or deletion; all other keys come from the latest committed generation. This is ordinary finite-map override, so unrelated committed definitions survive and savepoint/transaction restoration recovers the saved registry. No document support, row multiplicity, payload collision operation, score or ranking operation changes.

A descriptor index is built once per retained read view, with one descriptor shared by both OIDs. Its initial work and memory are linear in the number of range definitions; repeated lookup performs a tree lookup and shared-owner clone with no allocation. Catalog publication and restoration validate complete type claims only when ranges exist. They reuse borrowed type/name lookups without materializing `pg_type` rows: for $R$ ranges and $T$ other definitions the lookup work is $O(RT)$, with temporary space bounded by an individual name lookup. These are in-memory metadata visits, not stored-row or document reads. The 0/512 unrelated-table regression checks the absence of full catalog projection and a 16KB peak scratch ceiling. There is no wall-clock speedup claim.

## Verification and remaining acceptance

The compact PostgreSQL 18.4 Docker fixture checks the actual `pg_type`, `pg_range` and `pg_depend` rows of `CREATE TYPE r AS RANGE(subtype=integer)`, with routine aliases explicitly cast to OIDs for a physical-row comparison. Independent lifecycle probes establish separately movable multirange names, inherited owner/usage authority and independently retained constructor names. A rolled-back PostgreSQL owner probe confirms that only the primary range records the shared owner dependency. The input statements, version and image digest accompany the consumed fixture; raw traces remain outside the repository.

Owning tests cover all four exact claims, malformed/unknown records, cross-family name/OID collisions, stale publication, independent changes, metadata lookup, pinned generations and allocation-free repeated descriptor lookup. Engine adapter tests cover native SQLite, SQLite K/V and redb refresh, savepoints, rollback, durable reopening and physical value observation. These use the internal catalog publication interface; they are not evidence for unimplemented SQL range declarations.

The range registry requires development SQLite record format 65 and redb record format 61. Actual predecessor/current binaries verified SQLite 64→65 and redb 60→61 in all nine native/Key-Value file configurations and redb. Original data, history, receipts and watermarks survive, and older reopened writers and retained SQLite handles reject the upgraded format. The predecessor is `b2e7032c3e08325bef6924944e05ca2c3e76cf16`. Automatic Linux/macOS regression acceptance remains required before merge. Issue [#943](https://github.com/cognica-io/uqa-engine/issues/943) tracks the reproduced metadata panic corrected here: declared range names were sent to a built-in-only type-name branch.

Local source verification passes 87 SQL range tests, 36 Execution range tests and two Engine tests, including the three-provider retained-state scenario and all ten new automatic checks. Strict library/test Clippy passes for SQL, Execution, Engine and both providers; the final Execution metadata-lookup change also passes its focused Clippy check. Formatting, 109 runtime dependency edges, Engine ownership, 223 integration sources in 22 test targets, Rust headers and file ceilings pass. The automatic inventory is 808 checks / 1,202 cases plus eight independent-process histories per operating system; actual reports at the delivered source remain pending.
