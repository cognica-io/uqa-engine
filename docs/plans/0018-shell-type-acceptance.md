# Shell type catalog and type descriptions

This is the shared shell-publication prerequisite of original record 65, following the [typed endpoint boundary](0018-user-defined-ranges.md). It does not complete custom range/multirange publication or any other original extension record. Type-description bug [#933](https://github.com/cognica-io/uqa-engine/issues/933) is corrected at the same object-lifecycle boundary; the original wider COMMENT task remains open for other object classes.

## Ownership and implementation

SQL owns undefined-type metadata, syntax, ordered declaration validation, diagnostics and AST/plan effects. Execution owns independent type records, OID claims, object locks, completion, catalog rows, privilege checks, descriptions and the dependency deletion boundary. Engine only retains the shared registry cells, statement snapshots, session refresh and persistence adapters. Existing enum/composite private-overlay merging is shared through `TypeRecordFormat`; no reverse dependency, new Cargo feature or value carrier is introduced. Shell declarations create no callable value layout or generated array.

Comments use catalog object addresses independently of type names. Their object-first ordered map supports point lookup for `obj_description(oid, class)` and a bounded prefix lookup for `obj_description(oid)`; neither scans unrelated descriptions. The dependency deletion target set includes implicit array and relation row types, so those descriptions are removed even when the physical definition is removed by its owner. Publication clones the registry once per change; bulk removal does not clone it per deleted object.

## Preservation argument

Let a shell be $S=(o,i,n,r,a)$: type OID, immutable object identity, qualified name, owning role incarnation and optional ACL. Creation reserves a fresh name and a single OID under the existing catalog lock/allocator. It publishes no value layout. The independent shell record and OID claim describe exactly $o$; restoration checks the format marker, matching claims, unique nonzero identities, consistent names and live owner incarnation before exposing the registry. Thus a shell cannot acquire an array or a different public identity merely by restoring it.

Completion retains the shell's type-object lock and refreshes the catalog before checking $i$ and the completing role. For a completed enum, domain or composite $T$, publication preserves $o$ and $i$, installs the definition and newly allocated associated identities, resets the ACL as PostgreSQL does, and removes $S$ within the existing statement transaction. Success exposes one completed definition, while a statement failure or savepoint rollback restores the original shell and claims. A competing identity at the same name is not treated as the captured shell.

Descriptions form a partial map $C:(\mathrm{class},o,\mathrm{subobject})\rightharpoonup\mathrm{text}$. Renaming, schema movement, owner changes and shell completion preserve $o$, so they preserve $C$ without text rewriting or name lookup. NULL and empty comments remove the entry. Deletion removes exactly the descriptions of the dependency target identities, including implicit row and array types. Other entries remain unchanged. Provider metadata and the retained map share the same transaction/rollback boundary; a peer refresh overlays only transaction-private keys over its newly committed registry.

The construction extends catalog authority without adding SQL values, equality classes or operators. Existing value operations therefore use the same carriers, type identities and algebra. Comment reads are stable observations of a statement catalog; comment writes and type publication retain their existing transactional effects rather than participating in scalar equality or indexing.
