# Fixed unbound SQLite inverted-index snapshots

Issue #124 affects the direct, unbound `SQLiteInvertedIndex` API. The original physical snapshot retained analyzer bindings and a clone of the live managed connection, so later replacement or deletion changed an earlier reader. Native MVCC snapshots already retain their selected committed/private record owner. The correction replaces that physical capture while preserving the native path; no additional PR is opened while #149 is pending.

## Ownership and implementation

`uqa-storage-sqlite` owns the physical SQLite read boundary and occurrence-row projection. Capture current rows, legacy format presence and field-specific skip/block-max tables inside one existing `read_snapshot` boundary, including writes private to the capturing connection. Reuse the native occurrence row codec for common key/value projections. `uqa-storage::KeyValueRead::retain` already copies selected bytes under a `StorageReadControl`; `KeyValueInvertedIndex::snapshot_from_read` already retains analyzer revisions and supplies immutable posting/statistics readers. Reuse these interfaces instead of reanalyzing unavailable source text, copying unrelated database tables or adding snapshot algorithms to Engine.

The existing SQLite crate dependency direction permits this adapter. Native SQLCipher and Emscripten SQLite use the current `blob`, `cache` and `functions` features; no backup/serialization feature or additional crate is needed. Copied key/value buffers, descriptors, analyzer metadata and retained readers keep the invoking allowance until the final nested reader drops. SQLite page/cache allocations retain their existing provider ownership.
