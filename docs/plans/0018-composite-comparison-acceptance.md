## Character output preservation

The declaration compiler also assigned an implicit length of one to the catalog name `bpchar`, losing spaces before output. PostgreSQL's parser supplies the default length for the `CHAR` and `CHARACTER` keywords; an unmodified `bpchar` catalog name has no length constraint. SQL now preserves that distinction for table columns and composite attributes, including quoted and qualified names. The independent catalog observation checks OID 1042 with `atttypmod = -1` for `bpchar`, versus 5 for `CHARACTER` and 8 for `CHAR(4)`. Explicit length validation and padding still use their existing paths.

Scalar bpchar-to-text coercion removes trailing ASCII spaces; a bpchar field's type output retains them. Previously, context-free array and record output incorrectly selected the scalar coercion. SQL's container-field conversion now selects type output for the existing bpchar and Boolean carriers and recursively decodes physical fields through the existing controlled codec. The existing quoting rules then escape that output. Named records, anonymous rows and arrays all use the same field conversion; nested containers follow it recursively.

For a container with fields $v_1,\ldots,v_n$, its text is the existing delimiters and escaping applied in order to each field's type output. The corrected bpchar branch returns exactly its owned string, which is the PostgreSQL type output, while the scalar branch remains unchanged. Structural induction over arrays and records therefore preserves padding at every container depth without changing scalar coercion. The correction does not mutate fields or change comparison, equality-key or index code, so the existing padding-insensitive equality classes and relational multiplicities remain unchanged. Each copy, physical decode and append uses the caller's production control; existing admission failures and cancellation release the same owned temporary reservations. Owner tests cover ordinary and retained physical carriers, nested output, memory failure and cancellation; the public bpchar reference covers all four providers and persistent reopening.

The #913 correction passes five focused SQL owner tests and the eighteen-observation bpchar reference on each of memory, native SQLite, SQLite Key/Value and redb. The reference includes two observations after actual reopening of each persistent provider. ## Range bound ordering foundation

The SQL range owner now compares admitted ranges by emptiness, lower bound and upper bound, and compares normalized multiranges lexicographically by their members. An unbounded lower endpoint is negative infinity and an unbounded upper endpoint is positive infinity; equal finite lower endpoints place an inclusive bound first, while equal finite upper endpoints place an exclusive bound first. This follows PostgreSQL 18's [range comparison](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/utils/adt/rangetypes.c) and [multirange comparison](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/utils/adt/multirangetypes.c). Existing subtype parsing, numeric comparison and discrete canonicalization remain the owners of bound values.

For a fixed subtype, each nonempty canonical range has the comparison key $(L,U)$, where $L$ and $U$ are endpoints ordered as above; the empty range precedes every such key. Each endpoint order extends the subtype order with one infinity and an inclusivity tie-breaker, so reflexivity, antisymmetry and transitivity are preserved. Lexicographic extension preserves these properties first for the pair of bounds and then for the finite sequence of normalized multirange members. Numeric scale changes cannot alter this order because the existing numeric comparator supplies the endpoint equivalence classes. The new methods borrow admitted bounds and never change their text representation, membership, overlap or union behavior. They retain the caller's production control for numeric scratch and cancellation; this does not claim that parsing a range is allocation-free.

The compact SQL-owner fixture `crates/uqa-sql/src/expr/range/comparison/postgresql.json` records 1,264 pair comparisons independently captured from Docker PostgreSQL 18.4 across all twelve built-in range/multirange families. It includes empty and unbounded ranges, equal numeric values with different scales, NaN, finite and infinite temporal bounds, inclusivity and multirange prefixes. The two foundation tests pass locally, including unchanged retained memory after comparison, zero-allocation admitted integer comparisons and cancellation cleanup. Commit `88358f561` adds this foundation; the consumer correction described below connects it to record/array comparisons and SQL equality keys.

## Range reservations and remaining SQL consumers

The two-session PostgreSQL 18.4 transcript `composite_range_reservations_oracle.json` independently captures fourteen ordered commands. An uncommitted composite `numrange` key conflicts with an equal key of a different decimal scale (`55P03` at `lock_timeout`); a different range remains writable; rollback admits the retry; a committed equivalent key reports `23505`. Before the correction SQLite, SQLite Key/Value and redb all admitted the conflicting insert. The corrected three-provider probe passes locally. It measures no elapsed-time threshold.

Execution now adds the SQL-normalized range reservation to the existing predecessor addresses. If $x \sim y$ under the selected field operator, their normalized address is the same, so successful writers cannot concurrently hold conflicting reservations. Keeping every predecessor address preserves the old locking relation for unchanged physical inputs; it does not make an older writer understand new equality classes, so every concurrent owner must use the correction. Nonrange keys retain exactly their existing three addresses. Reservation traversal retains declared field metadata without selecting the SQL hash operator or eagerly reading opaque physical fields; malformed deferred fields keep their original validation boundary. Range and multirange key tags are distinct from the existing enum tag.

The SQL exact-set interface now lends the statement catalog to recursive UNION and cached IN membership; correlated membership and recursive CYCLE use the same SQL equality operators. The opaque Core set interface remains available for document identities. Referential scans and post-lock child rechecks compare their already-coerced columns through SQL, retaining the existing indexed candidate selection, row visibility and lock protocol. For a fixed valid key domain, replacing raw text identity with the same SQL equivalence relation makes duplicate elimination, membership and cycle termination agree with the operator; no row payload is rewritten. A foreign-key action selects exactly those visible child keys equal to its parent key, preserving cascade multiplicities and NO ACTION rejection instead of silently leaving a reference behind.

Focused Execution checks pass for actual DISTINCT spill, both direct and encoded join keys with either smaller build side, forced-spill inner/full joins with duplicates and unmatched NULL rows, exact-set spill and cached/streamed membership. The checks retain original values, assert the selected strategy and cleanup, and preserve raw-key behavior. Existing subquery-cache tests (thirteen) and DISTINCT/key tests (thirty-six) also pass. The expanded public reference contains 190 independent observations (177 initial, thirteen reopen), adding recursive UNION/CYCLE, cached and correlated IN, indexed and unindexed FK cascade, NO ACTION, upsert and rollback. All four providers pass the 190 observations, including actual reopening of each persistent provider; the three persistent providers also pass every command and diagnostic in the two-session transcript.
