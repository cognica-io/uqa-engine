# Extension packages, data models, and SQL types implementation plan

Status: Active. Implementation starts from main `8a99d4fd` (0.4.7), inspected on 2026-09-29. The [extension design](../design/data-model-and-type-extensions.md) defines the target contracts, proofs and acceptance criteria; this plan fixes the implementation order, owners, representation decisions and completion ledger. The [manual](../manual/README.md) remains authoritative for public behavior; a unit extends it only when its exit evidence passes.

## Outcome and fixed boundaries

Deliver the required outcomes of the design: user-defined enum, composite, range and base types with their generated arrays and domain composition; host-registered extension packages installed by PostgreSQL 18 `CREATE EXTENSION`, `ALTER EXTENSION` and `DROP EXTENSION`; functions, casts, operators, operator classes and families contributed by those packages; owned data models with generic source and command nodes; optimizer contributions consumed by normal planning; and direct authoring in Rust, Python, Node.js and browser WASM. Ordinary SQL and extension work must compose in the same query and logical transaction, and a second independently authored model or type must not require a new core enum branch or an Engine algorithm.

PostgreSQL 18.4 is the oracle wherever PostgreSQL defines the construct, including values, catalog rows, diagnostics, validation order, transaction effects and persistence. A difference is a bug fixed in its owning crate. Each unit captures its PostgreSQL evidence from a pinned `postgres:18.4` image before implementing the behavior, and never derives expected results from UQA output.

The unit order below follows ownership dependencies. PostgreSQL-native type forms come first because they exercise durable type identity, catalog projection, binding, value consumers and persistence without host code. Package registration, the extension-value envelope and host implementations then reuse those owners. Unsupported shapes keep failing explicitly with PostgreSQL diagnostics until their unit is complete; a parser-accepted but ignored declaration is forbidden.

## Representation decisions

Enum values use a dedicated Core carrier `EnumValue { type_oid, key }`. The key is an immutable byte string allocated when a label is created and compared lexicographically; it is never the PostgreSQL float4 `enumsortorder`, because PostgreSQL renumbers that column when midpoints collapse while the relative order of existing labels never changes. A new label receives a key strictly between the keys of its neighbors, so for labels $a$ and $b$ of one type, $a < b$ in declaration order if and only if $k(a) <_{\mathrm{lex}} k(b)$, and $k(a) = k(b)$ if and only if $a = b$. Every existing context-free consumer of `Value` order, equality and hashing therefore implements the SQL enum order without a catalog callback. Different enum types are never compared by SQL binding; the carrier orders them by type OID only for internal bookkeeping.

The catalog maps `(type_oid, key)` to the label OID, current label text and the PostgreSQL float4 sort position. Text output resolves labels through the statement's catalog context, so `ALTER TYPE ... RENAME VALUE` changes no stored row. A context-free text conversion of an enum carrier is a typed error rather than an invented rendering. `pg_enum.enumsortorder` follows PostgreSQL's float4 midpoint and renumbering algorithm exactly and is independent of the stored key.

Composite, range and host base types add their own bound `ColumnType` variants. Composite values reuse the named `Record` carrier with a bound type identity; user ranges generalize the closed built-in range subtype set; host base types use the separate `ExtensionValue` envelope whose SQL order, equality and hashing come only from bound operator-family operations.

### Preservation obligations

Let $C_n$ be the existing composite carrier with ordered live attributes, including nullable outer values. Appending a new attribute defines $E(x_1,\ldots,x_n)=(x_1,\ldots,x_n,\mathrm{NULL})$ and $E(\mathrm{NULL})=\mathrm{NULL}$ on existing values. Projection $P$ onto the old attributes satisfies $P\circ E=\mathrm{id}_{C_n}$. Extend $E$ structurally through domains, array elements and enclosing composite fields while preserving array bounds, dimensions, outer NULLs and every unrelated field. Induction on that finite acyclic type tree proves the corresponding projection law at each nesting level. Attribute validation must reject cycles before publication, preserving that precondition.

A stored typed ROW constructor retains the type OID, its original ordered attribute numbers $I$, and the selected input expressions $e_i$ with their creation-time coercions. For a current descriptor with ordered live numbers $J$, evaluation places $e_i$ at its original number when $i\in I\cap J$ and places NULL at numbers in $J\setminus I$. Under addition, $I\subseteq J$, so every original input runs exactly once in the same order and $P(C_J(e))=C_I(e)$, including the original evaluation effects and errors. Fresh ROW casts still validate their written width against the current descriptor; the extension rule applies only to retained constructors. Identity assignment of an already typed composite preserves this result without rerunning field-domain constraints. Catalog-free constant folding must leave these constructors intact because their observable width depends on the current descriptor.

Before an earlier catalog can change a descriptor, initial restoration must bind its predecessor ROW casts with the original descriptor through each owning object binder. This transformation preserves the type identity, selected child expressions, field order and ordinary coercions, and occurs in the initial catalog transaction. A failed conversion rolls back every metadata change; snapshot and secondary-session restoration must refuse a required migration. These migration and persistence obligations remain under verification.

An input constant is the result $v=I_D(t)$ of the original descriptor's input function, including its field-domain checks. Persisting that typed value separates input conversion from later observation. A descriptor addition transforms each stored occurrence to $E(v)$; it must not compute $I_{D'}(t)$ or re-run a field constraint. The same structural induction applies to typed constants in defaults, checks, generated expressions, views, index expressions, routine bodies, event definitions and partition boundary datums. Existing owners publish their changed definitions in the same statement transaction, and index keys are rebuilt after the new descriptor is visible. Rollback must restore both definitions and physical keys. These additional obligations are under active regression verification.

Consequently, expressions observing only the old attributes have the same values under the corresponding projection; complete composite output and introspection intentionally observe the new trailing NULL. For the PostgreSQL record equality and lexicographic order, appending the same NULL to two existing non-NULL records preserves their result: an earlier unequal field still decides, and previously equal records gain equal final fields. This does not substitute for the separately tracked missing record comparison behavior. Existing document support, payloads, ranking scores and row identities do not change. No new algebraic operator or approximation is introduced.

Execution must establish these laws for durable table and materialized-view values, catalog snapshots, field-number dependencies and cached/prepared plans. All additions run in the existing statement transaction: a later failure restores both the registry and every rewritten value, while committed restoration retains the same identities and new descriptors. The independent references and owning-crate tests below establish these obligations for attribute addition.

Retained prepared constants keep their original datum $v$. Reading it under the current descriptor applies $E(v)$ into a separately admitted result; it never mutates $v$ or runs the input function again. Returning to the old descriptor after rollback consequently reads $v$, so the extension/projection identity also holds across transaction undo. ### Removal preservation argument

Let a named composite descriptor have immutable type identity $T$ and live attribute-number set $I$. Removing attributes $D \subseteq I$ produces $J=I\setminus D$ and projection $P_J:(\prod_{i\in I}V_i)\cup\{\mathrm{NULL}\}\to(\prod_{j\in J}V_j)\cup\{\mathrm{NULL}\}$, with $P_J(\mathrm{NULL})=\mathrm{NULL}$ and $P_J(v)_j=v_j$. For every surviving field observation $\pi_j$, $\pi_j\circ P_J=\pi_j$; removing disjoint sets composes as $P_K\circ P_J=P_K$ for $K\subseteq J$, and $P_I$ is the identity. These equalities follow componentwise from selection of the same original attribute number. Type identity and surviving attribute numbers do not change; re-adding a name allocates a fresh number and introduces NULL, never the removed component.

Extend the projection recursively over the finite acyclic composite/domain type graph and elementwise over arrays. Structural induction preserves every unaffected scalar, outer NULL, array dimension, lower bound and surviving nested field. A stored constructor retains original argument-to-attribute numbers: evaluation visits only current live numbers, so its result is the projection of retained components without evaluating removed arguments. The latter is a state-effect requirement, not a claim that projection commutes with eager evaluation of volatile arguments.

Projection is not injective: records differing only in removed attributes become equal. Therefore this change does not preserve old whole-record equality, ordering or unique-key distinctness. PostgreSQL permits previously distinct stored unique keys to collapse on removal; subsequent writes must enforce uniqueness using the new descriptor. Rebuilt physical keys must represent that current comparison while preserving all existing rows. No optimizer may infer injectivity or transport an old record order through this change.

Prepared logical inputs retain their original descriptors and values. For each current descriptor $J$, SQL projects a private copy by attribute number before planning; it never destroys the original components, so rollback to $I$ yields $P_I(v)=v$. A bound field selector retains its original result type and number. If that number is absent, its result is NULL after evaluating its base; a new attribute with the same spelling has a different number and cannot become its target. Result types, array bounds and nested descriptors follow the same structural induction as stored values.

A generic plan retains its own input descriptors independently of the logical source. Projecting a copy of that cached plan preserves scalar constants already folded when it was built: if a field selection was reduced to scalar $k$ under descriptor $J_0$, later descriptor changes do not retroactively reevaluate it. A still-executable field selection applies the current projection and retains base-expression effects. Attribute numbers are never reused; a previously removed original number becoming live again identifies catalog undo and requires rebuilding constants folded under the undone descriptor. The immutable logical datum supplies the restored components. Constant field folding is permitted only for an already-read composite constant with the bound type identity; runtime ROW constructors and volatile bases remain executable. Separately, ordinary relation/routine dependency invalidation reanalyzes the source against the current catalog, preserving PostgreSQL's errors and field-name rebinding at that boundary. The independent reference distinguishes execution before versus after removal, mixed scalar/whole-record cached output, volatile inputs, table-driven reanalysis and rollback.

Dependency checks reject surviving catalog definitions that observe a removed field, or CASCADE removes their owning objects before projecting values. A successful publication exposes the new descriptor and all corresponding stored values together; failure restores their former state. Unrelated document support, payloads, graph carriers, scores and ranked operations are unchanged. ### Renaming preservation argument

Let a composite descriptor assign distinct live attribute numbers $I$ to names and types, and let a successful rename replace one name while preserving every number and type.
