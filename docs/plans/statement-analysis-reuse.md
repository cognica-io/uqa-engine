## Derived-source execution handoff

The root execution binder already visits nested derived-query sources to obtain the parent source's descriptor. Previously, each streamed derived builder recursively bound those same descendants again. SQL now captures successful source descriptions during that original traversal and extracts a structurally aligned tree borrowing the original execution syntax. Only original query-block identities admitted before traversal receive entries; temporary view/CTE/function-member syntax is excluded. Temporary address keys are discarded before returning the borrowed tree. This metadata is created after optimization and never reads QueryPlan's pre-optimization analyzed_source annotation.

Execution forwards each join child's metadata to that child's physical builder and checks the actual source identity. A derived block additionally requires the same complete outer RowSchema, parameter slice, routine resolver, native immutable catalog snapshot, search path/current user/temporary namespace, CTE row descriptors, deferred-definition identities, non-returning names and recursive visibility widths. A changed or specialized source, different scope, local CTE declaration, direct table-function binding or deferred DISTINCT slice takes the ordinary binding path. Each query still selects its own dynamic/bound lookup mode. Runtime-defined/open source descriptions are not transferred. The tree is released when physical assembly returns; physical operators do not retain it.

For a fixed query node $q$, immutable binding inputs $C$ and complete enclosing description $S$, let $D(q,C,S)$ be the raw source description obtained by the ordered binder. The first root traversal still performs $D$ at the original position and fails immediately on an error. A later physical assembly of that same borrowed $q$ may substitute its previously successful $D$ only after the stated identity and scope checks. The substitute shares the same immutable descriptor; a failed guard instead repeats the original binder. No SQL expression is evaluated by this transfer, and subsequent reference, type, set-context, routine-privilege and relation-privilege checks remain in their original order. Therefore values, positional labels/types, SQL bag multiplicities, side effects, first diagnostics and UnifiedPlan structure are preserved. This argument applies to eligible streamed derived sources; it does not establish reuse across independent CTE/routine scopes or authorize omission of privilege checks.

## Complete SELECT coverage within an immutable scope

[PR #1276](https://github.com/cognica-io/uqa-engine/pull/1276), composed above merged #1275 and #1274, addresses repeated authorization lineage in original direct derived sources. SQL owns a borrowed coverage value that can only be constructed after the existing complete ordered table/column check succeeds. Its structural projections visit the original join children and direct derived QueryBlock nodes without allocating an index of descendants or traversing them a second time. Execution retains it alongside the existing source binding, guarded by the same immutable catalog, namespace, CTE definitions, complete outer RowSchema, parameters and routine resolver. It additionally compares the complete RoleReference, including role incarnation, and relation lookup mode. Equal role names or successful type binding alone never establish authorization.

Let $C(Q,E,r)$ be the ordered complete SELECT check for query $Q$ in immutable environment $E$ under subject $r$, and let $D$ be an original direct derived block visited by its lineage traversal. Successful $C(Q,E,r)$ has checked every table and column required by $D$, including unused inner projections, predicates, reachable CTEs and authorization-only columns. When the original $D$ and its full environment/subject remain identical, repeating its successful check cannot introduce a new denial. The source certificate records only this coverage; it does not certify a copied or rewritten query, a view expansion, another routine subject, a different lookup mode or a new catalog. Those cases use the original complete check. The first enclosing check stays at its original scheduling boundary, after the same reference/planning/lock metadata work. Failure emits no certificate. Therefore the correction preserves first errors and successful SQL bags, values, side effects, privileges and UnifiedPlan while removing repeated analysis of already covered descendants. Foreign ACL metadata errors remain inside the initial complete check even when a table grant exists. Native CatalogReadView uses ordinary table/column SELECT grant implication: a successful union of required columns also covers each descendant subset, while a descendant requiring no columns is authorized by the same table or any successful column grant. Foreign table and column checks resolve the same immutable security metadata before testing their grant; a successful root check cannot hide a different descendant-only metadata lookup. The SQL value records structural coverage only, and does not promise reusable outcomes for arbitrary mutable or inconsistent PrivilegeCatalog implementations. No routine EXECUTE check, value callback or scalar-subquery execution check is suppressed.
