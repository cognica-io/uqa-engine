# Concurrent storage transaction implementation plan

Status: Implementation in progress. Common storage owns versioned records, private command views/savepoints and logical Key/Value sessions with retained commit outcomes. SQLite Key/Value and redb route their existing catalog/backend sessions through these records and migrate legacy files with old-writer guards. Independent direct Key/Value writers now overlap, including SQLite connections in separate native processes; Engine SQL still retains its writer gate. The explicit native SQLite record adapter now converts its baseline and atomically maintains current rows and history, and native document/B-tree and exact/IVF/HNSW vector stores and metadata/schema/model/analyzer/view/foreign/table/index/column/statistics/sequence operations can bind to common logical sessions. Common Key/Value and native SQLite occurrence, IVF and HNSW merging is implemented; complete native catalog/backend routing, SQL isolation/publication and provider reclamation remain pending. Baseline: UQA 0.3.6, commit `24e464f7709cd5d942df8d0aeef5d522716b1bfb`, inspected on 2026-09-16. The [design](../design/concurrent-storage-transactions.md) defines the intended architecture; this plan distinguishes implemented storage behavior from the complete public capability.

Native SQLite, SQLite Key/Value and redb occurrence merging is implemented in [`occurrence resolver`](../../crates/uqa-storage/src/mvcc/occurrence/resolve.rs), with owner tests for shared clusters/totals, document and structural conflicts, late caches, savepoints, retained snapshots, admission retries and receipt recovery. The [storage contract](../manual/internals/03-storage.md) describes the behavior and [upgrade notes](../manual/reference/10-upgrading.md#unreleased-rust-keyvalue-compound-operations) describe the record-format and wrapper requirements. Native SQLite and common Key/Value IVF/HNSW merging now retains ordered evaluated document inputs, prepares matching generations against a fresh snapshot, and fences document/structural conflicts. Both native SQLite and Key/Value HNSW now use the same vector journal and conflict resolver.

The common Key/Value sequence consumer audit now routes definition/name changes and reservation/set-value operations through one evaluated mutation, with fixed-view reads and original write/schema preconditions. A deterministic schedule reproduced duplicate `1..3` reservations in the previous split read/write path. The implementation removes the catalog-local sequence mutex and uses the common provider boundary. Verification covers interleaved value/definition/name changes, selected independent sessions, rollback/savepoints and reopen; autonomous SQL values, definition locking and conflict handling in the new Engine transaction model remain required.

Sequence review also distinguishes ownership metadata from allocation-generation replacement. `OWNED BY` and implicit owner attachment preserve the allocation generation; the issuing session abandons its unused cache while peer caches and later nontransactional reservations survive ownership rollback. SQL owns the explicit value-option classification, execution owns generation selection and publication, and Engine retains the existing state adapter. The reference schedule ran on PostgreSQL 18.4 Docker image `sha256:a02db8cac496f15b094798a38254f14d6e00741f709360e5e00bb6668ea31636`: with `CACHE 3`, A receives 1, B receives 4, A executes `BEGIN; ALTER SEQUENCE ... OWNED BY NONE` and receives 7, then rolls back; A next receives 8 and B next receives 5. A subsequent `INCREMENT BY 10` replaces the generation and B next receives 19. UQA verification passes 95 Engine SQL sequence cases, including the previously failing memory and three-provider ownership schedules, plus 15 Engine sequence-state adapter cases, 507 SQL and 360 execution unit cases, the manual SQL check and strict six-owner all-target Clippy. Raw reference output remains outside the repository.

## Objective and completion boundary

Implement overlapping logical write transactions for default relational SQLite, SQLite Key/Value and redb using shared storage MVCC and brief serialized physical commits. Transaction B must write and commit independent rows while transaction A retains uncommitted changes; A's later commit or rollback must preserve B. Include shared indexes, catalog/graph state, PostgreSQL 18 transaction semantics, existing persistent open modes, migration, bounded resources and recovery. Engine retains transaction/session adapters; storage and execution algorithms remain with their owning crates.

Design-document completion and runtime completion are separate. This documentation task is complete when both documents agree with the inspected source, define decisions and acceptance gates, pass document/repository checks and are committed and submitted for review. Runtime completion requires every implementation unit and acceptance row below, with evidence attached to the implementation revision. A passing two-row test, one provider, a subset of isolation levels or a green reference-only PostgreSQL run cannot substitute for that full boundary.

## Confirmed starting points

- [`PersistentStorageSession`](../../crates/uqa-storage/src/backend.rs) already pairs catalog/backend handles, and provider factories create independent sessions. Extend this boundary instead of introducing a parallel Engine persistence API.
- In the baseline, SQLite `BEGIN IMMEDIATE`, redb's retained `WriteState`, Engine deferred promotion and Engine eager transaction entry all participate in serialization. The redb and SQLite Key/Value physical lifetime writers have since been replaced; native relational SQLite and Engine's writer gate remain. The reader/writer capability does not imply multiple writers.
- [`uqa-execution::row_locks`](../../crates/uqa-execution/src/row_locks/mod.rs) owns row/relation waits, deadlocks, cross-process coordination and row-change rechecks. Engine's `row_locks.rs` is only a reexport.
- Common storage already owns K/V catalogs, rows, occurrences, B-tree, IVF and HNSW behavior. Physical clusters/counters are shared by different rows, so opaque buffered K/V replacement is insufficient.
- Existing ownership/dependency policy forbids common storage and its tests from depending on providers, and forbids execution from depending on either concrete provider. No policy weakening or new Engine runtime dependency on redb is planned.
- The manifest audit resolved rusqlite 0.39.0 and redb 4.1.0; native SQLCipher, compressed rollback-journal and Emscripten plain SQLite must retain their separate physical contracts. No new Cargo feature currently supplies this behavior.

## Access-path audit deliverable

The [initial runtime access inventory](../design/concurrent-storage-transactions.md#runtime-access-paths) identifies native and K/V provider bypasses, initial restore, transaction control, execution locks, shared indexes, graph handles, registries, allocation, notifications, maintenance and retained resources. [`capture_concurrent_writes.py`](../../tests/parity/pg18/capture_concurrent_writes.py) captured three PostgreSQL 18.4 schedules with B's completed commit preceding A's commit/rollback/savepoint ending. Their [compact fixture](../../tests/parity/pg18/concurrent_writes.expected.json) includes SQL steps and observations. A bounded public-0.3.6 SQLite reproduction left B unfinished while A held a write; B committed after A rolled back, preserving rows `(1,0)` and `(2,20)`. This is a correctness baseline, not timing evidence. That release also rejects SQL `lock_timeout`; the PG18 manifest now records these unresolved locking bugs.

The implemented [`mvcc`](../../crates/uqa-storage/src/mvcc/mod.rs) module owns record histories and private changes. `PreparedRecordCommit` owns evaluated bytes before commit admission and validates every original revision, including tombstones. `MemoryVersionStore` publishes complete prepared histories atomically and registers snapshots under the same gate as publication and reclamation. Foreign-budget prepared values are copied into the store allowance before acquiring publication admission; values already owned by that allowance remain shared. `PrivateRecordChanges` stages atomic batches, retains fixed private command views across undo and later writes, restores nested/repeated savepoints without allocating, and prepares final replacements without copying payloads. Intermediate private history stays in its charged journal until the owner and retained views are dropped; spill and intermediate reclamation remain open. The `CommittedRecordSnapshot` interface and `MergedRecordSnapshot` reader combine committed versions and fixed private changes in bounded ordered pages without duplicate identities or implicit snapshot advancement. Record reclamation returns unused header capacity through the core budgeted vector owner; shrinking failure preserves retained revisions and reports a typed resource error. The record and private-view tests include generated savepoint histories and merged pages compared against independent copied-map models; the session and complete owner-suite evidence is recorded below. This remains a storage building block: Engine SQL command/savepoint integration and serializable isolation are not established.

The common [`VersionedPersistence`](../../crates/uqa-storage/src/mvcc/persistence.rs) contract and [`redb record adapter`](../../crates/uqa-storage-redb/src/mvcc/mod.rs) persist non-reused transaction allocations, ordered record versions and commit receipts atomically. Prepared batches carry SHA-256 fingerprints computed before the physical writer; retry returns the existing matching receipt and rejects a different batch under the same allocation. Native commit errors are indeterminate, while failures before native commit are rejected attempts. A redb storage-backend synchronization failure test closes and reopens the actual database format, verifies an atomic old-or-new outcome with a matching receipt and resolves the same prepared commit. This is I/O failure/recovery evidence, not process-kill or power-loss evidence. The adapter retains all record versions and receipts pending reclamation.

[`VersionedKeyValueStore`](../../crates/uqa-storage/src/mvcc/session/mod.rs) now owns logical sessions, borrowed reads, ordered batches, prefix deletion and named savepoints. It seals evaluated changes before persistence and retains a failed attempt, including autocommit, until its outcome is resolved. A known committed receipt cannot be reported as rollback. Session retention is explicitly bounded (64 MiB by default); private history and batch buffers share that allowance, while borrowed encoded values do not consume the caller's query decode budget. Owner tests cover independent writer schedules, atomic conflicts, lost replies, mismatched receipts, cached terminal outcomes, duplicate savepoints/prefix deletion, cancellation and batch-allocation failure. Generated merged-read cases also check borrowed visitors against the independent ordered-map model. Current affected-owner verification is recorded below.

redb's existing `store` and catalog/backend session factory now use the common session. File-backed tests prove B's commit precedes A's commit, rollback or savepoint ending, and verify reopen state. The provider passes eight unit and 21 integration cases, including atomic legacy migration, collision rollback and I/O failure/reopen. [`verify-redb-legacy-writer.py`](../../scripts/verify-redb-legacy-writer.py) uses the actual crates.io 0.3.6 provider (archive SHA-256 `b20b61d2f69be5f39186f220599576ad28afe82d12740592c316c018ee721fc4`) to create a file, migrate/mutate it, reject the released writer and verify a second reopen, with redb pinned to workspace version 4.1.0. The new [`SQLiteRecordStore`](../../crates/uqa-storage-sqlite/src/mvcc/mod.rs) implements the same persistence contract using managed connections. ## Acceptance matrix

Use named synchronization events and channels/barriers. Start A, receive proof that A staged a change, start B, receive B's successful commit before allowing A to finish, and verify both session views and reopened state. Timeouts only detect a hung schedule. Where PostgreSQL permits multiple victims, fixtures specify allowed outcomes and serial histories instead of requiring one scheduler-dependent winner.

redb tests use one supported open database owner and independent logical sessions; concurrent redb file opens by separate processes are not a capability of the current library. SQLite native multiprocess tests are required. Browser tests cover the supported runtime/file ownership model and must not silently skip core session semantics under the label of platform limitations. No entire-provider or isolation-mode exemption is allowed for the requested behavior.

## Review risks that must be closed

- Native SQLite bypasses: a correct K/V adapter cannot compensate for direct native catalog/document/index reads that ignore snapshot visibility.
- Shared physical values: same-term clusters, counters, vector roots and graph adjacency must merge typed logical changes without losing updates or creating unrelated SQL conflicts.
- Publication races: a process can die after physical commit and before publishing its in-memory epoch; surviving processes must recover from durable evidence.
- Read/GC admission: pinning after horizon selection can lose required history; compressed native read transactions can accidentally retain the old writer bottleneck.
- Isolation versus retries: RC target rechecks must preserve command sources and effect counts; RR/serializable errors cannot be replaced by transparent transaction replay.
- Format safety: an unrecognized metadata key does not keep a 0.3.6 redb or SQLite K/V writer out of a new database.
- Security and resources: history, spill and cross-process observations can disclose data or grow without bounds unless their owning budgets and encryption are explicit.

Each risk needs owning tests and review evidence in the implementation PR. An unresolved risk keeps the corresponding unit pending; it is not a reason to waive that portion of the requested feature.

### Key/Value document ownership and table lifecycle

Common Key/Value document writes now use one evaluated view for owner selection, tuple metadata and row mutation. The exact-name owner registry keeps catalog adoption, definition-only drop, full removal, purge, rename and generation replacement consistent with durable reservations; raw standalone names remain distinct from canonical catalog names. Reverse claims reject duplicate identities and inconsistent bindings. Data writers retain definition requirements and merge immutable marker touches, while structural operations fence the corresponding data revision. Rename rejects destination collisions atomically. Common document snapshots and compound reads retain one view, and key-only seeding avoids reading unrelated document payloads.

Queued identifier inheritance preserves deleted or privately rolled-back reservations during Key/Value and native SQLite owner transfers. Changing the storage generation of the same object seeds only visible IDs. Engine retires rows under the old generation before selecting the new namespace, preserving both continued and explicitly restarted TRUNCATE identity semantics. The shared nonzero identity generator now belongs to storage, with the existing execution import retained as a re-export. Record format 6 upgrades formats 1–5 while preserving existing histories and reservations and rejecting older writers. Tests cover real SQLite file modes and redb reopen, exact-name rename combinations, corrupt bindings, metadata races, retained snapshots, legacy seeding and evaluated-batch failures.
