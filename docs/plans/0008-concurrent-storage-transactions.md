# Concurrent storage transaction implementation plan

Status: Implementation in progress. Common storage owns versioned records, private command views/savepoints and logical Key/Value sessions with retained commit outcomes. SQLite Key/Value and redb route their existing catalog/backend sessions through these records and migrate legacy files with old-writer guards. Independent direct Key/Value writers now overlap, including SQLite connections in separate native processes; Engine SQL still retains its writer gate. Native relational SQLite mapping, shared index merging, SQL isolation/publication and provider reclamation remain pending. Baseline: UQA 0.3.6, commit `24e464f7709cd5d942df8d0aeef5d522716b1bfb`, inspected on 2026-09-16. The [design](../design/concurrent-storage-transactions.md) defines the intended architecture; this plan distinguishes implemented storage behavior from the complete public capability.

## Objective and completion boundary

Implement overlapping logical write transactions for default relational SQLite, SQLite Key/Value and redb using shared storage MVCC and brief serialized physical commits. Transaction B must write and commit independent rows while transaction A retains uncommitted changes; A's later commit or rollback must preserve B. Include shared indexes, catalog/graph state, PostgreSQL 18 transaction semantics, existing persistent open modes, migration, bounded resources and recovery. Engine retains transaction/session adapters; storage and execution algorithms remain with their owning crates.

Design-document completion and runtime completion are separate. This documentation task is complete when both documents agree with the inspected source, define decisions and acceptance gates, pass document/repository checks and are committed and submitted for review. Runtime completion requires every implementation unit and acceptance row below, with evidence attached to the implementation revision. A passing two-row test, one provider, a subset of isolation levels or a green reference-only PostgreSQL run cannot substitute for that full boundary.

## Confirmed starting points

- [`PersistentStorageSession`](../../crates/uqa-storage/src/backend.rs) already pairs catalog/backend handles, and provider factories create independent sessions. Extend this boundary instead of introducing a parallel Engine persistence API.
- In the baseline, SQLite `BEGIN IMMEDIATE`, redb's retained `WriteState`, Engine deferred promotion and Engine eager transaction entry all participate in serialization. The redb and SQLite Key/Value physical lifetime writers have since been replaced; native relational SQLite and Engine's writer gate remain. The reader/writer capability does not imply multiple writers.
- [`uqa-execution::row_locks`](../../crates/uqa-execution/src/row_locks/mod.rs) owns row/relation waits, deadlocks, cross-process coordination and row-change rechecks. Engine's `row_locks.rs` is only a reexport.
- Common storage already owns K/V catalogs, rows, occurrences, B-tree, IVF and HNSW behavior. Physical clusters/counters are shared by different rows, so opaque buffered K/V replacement is insufficient.
- Existing ownership/dependency policy forbids common storage and its tests from depending on providers, and forbids execution from depending on either concrete provider. No policy weakening or new Engine runtime dependency on redb is planned.
- The manifest audit resolved rusqlite 0.39.0 and redb 4.1.0; native SQLCipher, compressed rollback-journal and Emscripten plain SQLite must retain their separate physical contracts. No new Cargo feature currently supplies this behavior.

## Access-path audit deliverable

The [initial runtime access inventory](../design/concurrent-storage-transactions.md#runtime-access-paths) identifies native and K/V provider bypasses, initial restore, transaction control, execution locks, shared indexes, graph handles, registries, allocation, notifications, maintenance and retained resources. [`capture_concurrent_writes.py`](../../tests/parity/pg18/capture_concurrent_writes.py) captured three PostgreSQL 18.4 schedules with B's completed commit preceding A's commit/rollback/savepoint ending. Their [compact fixture](../../tests/parity/pg18/concurrent_writes.expected.json) includes SQL steps and observations. A bounded public-0.3.6 SQLite reproduction left B unfinished while A held a write; B committed after A rolled back, preserving rows `(1,0)` and `(2,20)`. This is a correctness baseline, not timing evidence. That release also rejects SQL `lock_timeout`; the PG18 manifest now records these unresolved locking bugs.

The implemented [`mvcc`](../../crates/uqa-storage/src/mvcc/mod.rs) module owns record histories and private changes. `PreparedRecordCommit` owns evaluated bytes before commit admission and validates every original revision, including tombstones. `MemoryVersionStore` publishes complete prepared histories atomically and registers snapshots under the same gate as publication and reclamation. Foreign-budget prepared values are copied into the store allowance before acquiring publication admission; values already owned by that allowance remain shared. `PrivateRecordChanges` stages atomic batches, retains fixed private command views across undo and later writes, restores nested/repeated savepoints without allocating, and prepares final replacements without copying payloads. Intermediate private history stays in its charged journal until the owner and retained views are dropped; spill and intermediate reclamation remain open. The `CommittedRecordSnapshot` interface and `MergedRecordSnapshot` reader combine committed versions and fixed private changes in bounded ordered pages without duplicate identities or implicit snapshot advancement. Record reclamation returns unused header capacity through the core budgeted vector owner; shrinking failure preserves retained revisions and reports a typed resource error. The record and private-view tests include generated savepoint histories and merged pages compared against independent copied-map models; the session and complete owner-suite evidence is recorded below. This remains a storage building block: Engine SQL command/savepoint integration and serializable isolation are not established.

The common [`VersionedPersistence`](../../crates/uqa-storage/src/mvcc/persistence.rs) contract and [`redb record adapter`](../../crates/uqa-storage-redb/src/mvcc/mod.rs) persist non-reused transaction allocations, ordered record versions and commit receipts atomically. Prepared batches carry SHA-256 fingerprints computed before the physical writer; retry returns the existing matching receipt and rejects a different batch under the same allocation. Native commit errors are indeterminate, while failures before native commit are rejected attempts. A redb storage-backend synchronization failure test closes and reopens the actual database format, verifies an atomic old-or-new outcome with a matching receipt and resolves the same prepared commit. This is I/O failure/recovery evidence, not process-kill or power-loss evidence. The adapter retains all record versions and receipts pending reclamation.

[`VersionedKeyValueStore`](../../crates/uqa-storage/src/mvcc/session/mod.rs) now owns logical sessions, borrowed reads, ordered batches, prefix deletion and named savepoints. It seals evaluated changes before persistence and retains a failed attempt, including autocommit, until its outcome is resolved. A known committed receipt cannot be reported as rollback. Session retention is explicitly bounded (64 MiB by default); private history and batch buffers share that allowance, while borrowed encoded values do not consume the caller's query decode budget. Six owner tests cover independent writer schedules, atomic conflicts, lost replies, duplicate savepoints/prefix deletion, cancellation and batch-allocation failure. Generated merged-read cases now also check borrowed visitors against the independent ordered-map model. Common storage passes 191 unit, 79 integration and one documentation test.

redb's existing `store` and catalog/backend session factory now use the common session. File-backed tests prove B's commit precedes A's commit, rollback or savepoint ending, and verify reopen state. The provider passes eight unit and 21 integration cases, including atomic legacy migration, collision rollback and I/O failure/reopen. [`verify-redb-legacy-writer.py`](../../scripts/verify-redb-legacy-writer.py) uses the actual crates.io 0.3.6 provider (archive SHA-256 `b20b61d2f69be5f39186f220599576ad28afe82d12740592c316c018ee721fc4`) to create a file, migrate/mutate it, reject the released writer and verify a second reopen, with redb pinned to workspace version 4.1.0. The existing 15 Engine redb regression scenarios pass, including catalog/document rollback, savepoints, sibling cache refresh, text/vector queries, index lifecycle and legacy content migration. Engine SQL still retains its writer gate; these tests do not establish concurrent SQL, shared-index merging or complete PostgreSQL isolation.

The new [`SQLiteRecordStore`](../../crates/uqa-storage-sqlite/src/mvcc/mod.rs) implements the same persistence contract using managed connections. It stores unsigned allocations/sequences as ordered eight-byte BLOBs, validates all original heads before mutation, and publishes histories, heads, the sequence and receipt in one short native transaction. Length probes and payload reservations share one physical read snapshot; logical snapshots retain no physical reader between calls. Connection-local write permission guards all record tables and closes on error or unwind. Key/Value conversion replaces the legacy writable table with a guard view, adds a native-catalog guard and records the mapping in durable metadata. Existing native relational materializations still need their own guarded mapping. Physical writes explicitly select `synchronous=FULL`; legacy connection defaults are unchanged. The `functions` feature is now declared at runtime for both native SQLCipher and Emscripten SQLite.

SQLite evidence now includes the complete provider suite (242 unit and 177 integration tests); its ignored child-process entry point is invoked by two parent tests across all four file modes. The public Key/Value store and raw record adapter allow a second process to commit before A finishes. Tests also cover connection-clone affinity, one-connection in-memory pools, rollback/savepoints, oversized values with key-only reads, migration collisions and resource failure, active-native-transaction rejection, and missing or altered guards. Native `SQLITE_FULL` preserves pending receipts with no partial records; a busy physical COMMIT is indeterminate and resolves using the identical batch. These checks are not process-kill or power-loss evidence. The common suite passes 191 unit, 80 integration and one documentation test, and redb passes eight unit and 21 integration tests. Engine's 173 storage integration cases pass, including ten SQLite Key/Value and 15 redb cases. Failed Engine commits now abort retained provider changes before cache restoration; if abort also fails, frames and locks remain until explicit cleanup succeeds. Native relational routing, complete indeterminate-outcome publication and concurrent SQL enablement remain unfinished.

[`verify-sqlite-legacy-writer.py`](../../scripts/verify-sqlite-legacy-writer.py) uses the actual crates.io 0.3.6 provider (archive SHA-256 `3db0f72ba7aaf9b64b00ae2b02c8e36a7273d0c969f0b3da47f95d18beb29f6b`) to create binary fixtures, migrate/mutate them, reject old Key/Value writes and native catalog initialization, and reopen the result in plain, SQLCipher, compressed and encrypted compressed modes. The conversion preserves original bytes and publishes its mapping and guards atomically. It rejects native relational files rather than changing their format.

Both released-provider verifiers also pass under Python 3.10.8. Their shared provenance helper uses locked Cargo metadata to identify the registry package and obtains its archive SHA-256 from Cargo's directory-source checksum or the downloaded archive itself; no Python 3.11-only TOML parser or additional Python package is required. Both checksums match the compact references above.

The common `StorageSessionAffinity` contract identifies one native or logical transaction context without treating a file identity as a session identity. Catalog/backend facades forward their store's identity; connection/store clones share it and independent sessions do not. Engine invokes common validation before restore or sibling attachment. Tests cover valid and mismatched pairs in native SQLite, SQLite Key/Value and redb, malformed provider pairs on initial/sibling opens, omitted identity on one side, and legacy custom pairs that omit both. The 29 Engine open/restore unit cases and the actual Rust storage/transactions example also pass, including reopen, rollback, savepoints and sibling reads. Strict affected-owner Clippy and Emscripten SQLite/Engine library compilation pass; the latter is compile evidence, not browser execution. This establishes handle affinity; durable format/model validation and removal of the Engine writer gate remain separate requirements.

The core buffer owners now reconcile allocator-reported capacity before moving existing elements, including vector growth/shrink, deque growth and string growth. A forced oversized replacement test checks both successful accounting and limit rejection that preserves the original values, capacity and reservation; zero-sized vectors and deques retain a zero-byte allowance. The updated owners pass 104 core unit and 68 core integration tests, the complete common-storage suite (191 unit, 79 integration and one documentation test), and strict core/storage Clippy.

Before changing transaction entry, record concrete source owners and migration/routing decisions for catalog initialization, ordinary SQL DML/DDL, direct document/index APIs, graph/Cypher, B-tree/expression/unique indexes, posting clusters and statistics, IVF/HNSW, models/analyzers/routines, sequences and ID allocation, LISTEN/NOTIFY, prepared statements and cursors, temporary and unlogged relations, background ANALYZE, VACUUM/rebuild, backup/restore, callbacks, FDWs and each Engine/provider open constructor. Include error/unwind and savepoint paths. Update the inventory when a bypass is discovered; do not paper over it with a global transaction lock.

Native SQLite and SQLite K/V require distinct physical adapters to the same common record/visibility contract. Route both completely before claiming default SQLite support. Keep current SQLite tables as atomic current-state materializations with history; do not silently convert `Engine::open` into an unrelated K/V format. Retain the verified redb old-writer guard and exercise corresponding SQLite guards with actual old libraries. These are implementation deliverables, not optional follow-up optimizations.

Audit lower-level native SQLite writers as well as Engine/catalog opens. rusqlite `functions` is now a runtime feature in both SQLite-provider target declarations. Keep checking packaged consumers without development-feature unification while extending record-table guards to native materializations and legacy K/V writes. Reported transaction affinity is now checked for manually paired handles and provider-created Engine sessions. Complete format/model validation before enabling the concurrent capability. These changes belong to the provider/common interface units, with corresponding Rust upgrade notes.

## Acceptance matrix

Use named synchronization events and channels/barriers. Start A, receive proof that A staged a change, start B, receive B's successful commit before allowing A to finish, and verify both session views and reopened state. Timeouts only detect a hung schedule. Where PostgreSQL permits multiple victims, fixtures specify allowed outcomes and serial histories instead of requiring one scheduler-dependent winner.

| Required behavior | Deterministic evidence | Required coverage |
| --- | --- | --- |
| Independent writer progress | A writes row 1 and waits; B writes row 2 and commits; A then commits, rolls back or rolls back a savepoint. Check intermediate visibility and final reopen state. | Default SQLite, SQLite K/V, redb; same table and different tables; separately constructed SQLite providers and native processes |
| Shared physical data | Force two independent documents into one term cluster, common counters, index nodes and catalog containers; both commits survive and query results agree with visible rows. | Full-text scores/occurrences, B-tree/expression keys, IVF/HNSW, graph membership/path data, statistics |
| Snapshot isolation | Interleave reads and commits, including a writer retaining its private changes while a later command sees B; missing keys, empty ranges, paging, reverse scans, cursors, drop/recreate and PostgreSQL TRUNCATE/table-rewrite exceptions. | RC, RU-as-RC, RR; all providers; command, transaction and retained-resource boundaries |
| Conflicting writes and constraints | Same-row update/delete, key collisions, parent removal, deferred checks, cascades, exclusions, partition moves and `MERGE` actions; compare row counts, returned values and SQLSTATE. | Owning execution tests plus real multi-session Engine/Docker PostgreSQL schedules |

redb tests use one supported open database owner and independent logical sessions; concurrent redb file opens by separate processes are not a capability of the current library. SQLite native multiprocess tests are required. Browser tests cover the supported runtime/file ownership model and must not silently skip core session semantics under the label of platform limitations. No entire-provider or isolation-mode exemption is allowed for the requested behavior.

## Review risks that must be closed

- Native SQLite bypasses: a correct K/V adapter cannot compensate for direct native catalog/document/index reads that ignore snapshot visibility.
- Shared physical values: same-term clusters, counters, vector roots and graph adjacency must merge typed logical changes without losing updates or creating unrelated SQL conflicts.
- Publication races: a process can die after physical commit and before publishing its in-memory epoch; surviving processes must recover from durable evidence.
- Read/GC admission: pinning after horizon selection can lose required history; compressed native read transactions can accidentally retain the old writer bottleneck.
- Isolation versus retries: RC target rechecks must preserve command sources and effect counts; RR/serializable errors cannot be replaced by transparent transaction replay.
- Format safety: an unrecognized metadata key does not keep a 0.3.6 redb or SQLite K/V writer out of a new database.
- Security and resources: history, spill and cross-process observations can disclose data or grow without bounds unless their owning budgets and encryption are explicit.

Each risk needs owning tests and review evidence in the implementation PR. An unresolved risk keeps the corresponding unit pending; it is not a reason to waive that portion of the requested feature.

## Commits, evidence and document maintenance

Commit and push completed logical units with their tests and necessary contract changes. Separate mechanical ownership extraction from behavior changes when extraction is needed. Do not create a long chain of experiment, timing-output or corrective bookkeeping commits. Keep one reviewable implementation PR current with the final behavior, validation and remaining work; this design proposal can be reviewed separately before runtime changes begin.

Track status and compact evidence in the table above rather than appending repeated chronological reports. Each accepted unit records the tested commit, commands or CI links, test counts/schedule identifiers and unresolved gates. An implementation change that alters a decision updates the design and plan together; only verified public behavior enters the manual. Review the final diff for dependency direction and ownership before committing, and run `python3 scripts/check-workspace-dependencies.py --staged` on the exact index.

No performance measurements are scheduled by this plan. Deterministic concurrency progress, bounded work/memory and correctness are acceptance gates. Any later throughput study requires a controlled host, independently established noise bound, fixed workload and run limit before measurement. Keep generated reports and diagnostic traces in ignored output directories or CI artifacts; commit only compact fixtures, expected outcomes and provenance.
