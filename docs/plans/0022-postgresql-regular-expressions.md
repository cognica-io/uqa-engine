## Substring pattern forms (#981)

### Ownership and correction

SQL owns overload resolution, the regular-expression kernels and scalar execution; Planner owns constant simplification; Execution owns the routine catalog projection. Overload binding already resolved `substring(text, text)` and `substring(text, text, text)`, but evaluation dispatched by name and read the second and third arguments as integer positions. Execution binding now derives `FunctionDispatch::RegexSubstring` or `FunctionDispatch::SimilarSubstring` from the resolved argument types, as it derives the selected `to_bin` and `random` overloads, and the dispatched PostgreSQL scalar kernels pass those calls to the regular-expression owner's `eval_dispatched_substring`. Prepared and stored bindings keep their existing representation without a dispatch, so definitions created before this change select the pattern forms after reopening and no persisted format changes.

The POSIX form compiles the pattern through the existing regular-expression owner and returns the first parenthesized subexpression or the whole match. The SQL form is PostgreSQL's SQL-language function `substring($1, similar_to_escape($2, $3))`, which PostgreSQL inlines while planning. Its kernel therefore returns NULL for a NULL pattern or escape, then applies the existing `similar_to_escape` kernel, and only then returns NULL for a NULL string before the same extraction. The planner keeps the call but follows `simplify_function`: a strict NULL constant or an all-constant call is folded as before, and otherwise a constant pattern and escape are translated by `check_constant_similar_translation`, as the inlined body's constant `similar_to_escape` would be folded, unless the caller lacks EXECUTE on the routine, in which case PostgreSQL does not inline it either.

The routine catalog gains PostgreSQL's identities for the implemented `substring` and `substr` overloads (OIDs 877, 883, 936, 937, 2012, 2013, 2073, 2074, 2085 and 2086), including OID 2074 as a SQL-language routine with PostgreSQL's stored body. Stored expressions, CHECK constraints, defaults, `regprocedure` input and routine privileges previously failed for every `substring` and `substr` form because no catalog signature existed. The bit-string overloads 1680 and 1699 are not implemented (#989).

### Preservation argument

Dispatch is a function of the resolved signature only. The positional signatures `(text, integer)`, `(text, integer, integer)` and their bytea counterparts map to no dispatch, so their calls reach the unchanged positional kernel exactly as before. Only `(text, text)` and `(text, text, text)` map to the new variants; before this change those calls failed with `42804` for every non-numeric pattern and returned a positional slice when the pattern text parsed as an integer. Every previously successful result of a positional signature is therefore preserved, and the only changed observations are those of the two pattern signatures, which now follow PostgreSQL's definitions.

For the POSIX form, PostgreSQL's strict `textregexsubstr(s, p)` returns the span of the first parenthesized subexpression `m1` when `p` has one and the whole match `m0` otherwise, and NULL when the selected span is absent. The implementation computes the same function of `(m0, m1)` from the owner's spans, so its result is PostgreSQL's whenever the engine chooses PostgreSQL's `m0` and `m1`, which PostgreSQL's own engine in the SQL owner (#980) does.

For the SQL form, let `t(p, e)` be `similar_to_escape(p, e)`, which is strict and whose translation text equals PostgreSQL's for every independently observed pattern. PostgreSQL evaluates `substring(s, p, e)` as `NULL` when a constant argument is NULL, as the folded value when all arguments are constant, and otherwise as `textregexsubstr(s, t(p, e))` with `t` folded when `p` and `e` are constant. The planner preserves the first two cases through the existing folds and reproduces the third case's planning-time evaluation of `t` without changing the expression. At execution, the kernel evaluates `NULL` when `p` or `e` is NULL, otherwise `t(p, e)`, then `NULL` when `s` is NULL, otherwise the POSIX extraction: this is exactly the strict evaluation of the inlined body, including its error precedence. The selection of matches, including PostgreSQL's non-greedy prefix produced by `t`, is again the engine's, and PostgreSQL's engine (#980) makes it PostgreSQL's.

The new catalog rows add identities for routines that already resolved and executed; they do not change overload resolution, results or the routine catalogs of other functions. Evaluation reads only its arguments and the per-call compiled pattern. It does not touch storage, catalog state, row support, multiplicity or ordering. The input's code points, the translated pattern, the engine's working memory and the result are admitted under the caller's allowance; only the result survives a successful call, and a rejected output releases its reservation. Both cancellation scopes are checked before and after matching.

## Set-returning `regexp_matches` (#982)

### Ownership and correction

SQL owns the regular-expression kernels, flag validation, named-argument positions, set-returning classification and table-function signatures; Planner owns constant simplification; Execution owns table-function row streams and the routine catalog projection. Evaluation previously routed `regexp_matches` with the scalar `regexp_match` to one capture array or NULL and accepted `g` without iterating, so the function returned at most one row, returned a NULL row when nothing matched, and was undefined in `FROM`. The SQL owner now provides a `RegexMatches` cursor. Creating it parses the flags and finds every match through the owner's `MatchSet`, as `regexp_matches` calls `setup_regexp_matches` on its first call, and reports `54000` `too many regular expression matches` where PostgreSQL's match locations would exceed `MaxAllocSize`; the cursor then owns the input's code points and the recorded match spans, and each request builds the capture array of the next match, as each later call runs `build_regexp_match_result`, and admits it under the requesting control. Execution adapts the cursor to a one-column table-function stream, which `FROM`, `LATERAL`, `ROWS FROM`, `WITH ORDINALITY` and the select-list set projection all consume. Semantics classify `regexp_matches` as a set-returning built-in with PostgreSQL's named `(text, text)` and `(text, text, text)` signatures and `text[]` column, named arguments of a built-in table function take their declared positions as in a scalar call, and the planner no longer folds a strict set-returning call with a NULL input to one NULL value.

Flag parsing now validates the whole flag string before a caller inspects `g`, as `parse_re_flags` does. `regexp_matches` and `regexp_replace` accept `g`; `regexp_match`, `regexp_like`, `regexp_count`, `regexp_instr` and `regexp_substr` reject it with `22023`, `<function>() does not support the "global" option`, before the pattern is compiled, and `regexp_match` adds PostgreSQL's hint. These functions previously reported `g` as an invalid option when the loop reached it. `regexp_match` also gains its PostgreSQL argument names. The routine catalog gains OIDs 2763 and 2764 with their argument names, set-returning flag and row estimates of 1 and 10.

### Preservation argument

Let `m0, m1, ...` be the matches PostgreSQL's `setup_regexp_matches` records for `regexp_matches`, which does not ignore degenerate matches: the first search starts at offset 0, each later search starts at the end of the previous match, or one character later after an empty match, and the iteration stops once that start passes the end of the input; without `g` only `m0` is taken. `MatchSet::find` runs the same loop over the same operands: the input as code points, which `pg_mb2wchar_with_len` produces in a UTF-8 database, the pattern compiled by PostgreSQL's own `pg_regcomp` with the options of `parse_re_flags` under the strategy `pg_set_regex_collation` selects for the call's input collation, and each search run by `pg_regexec` from the recorded start. Every search therefore returns PostgreSQL's spans, the loop records PostgreSQL's match locations in PostgreSQL's order, and `regexp_matches('aab', 'a*', 'g')` returns `{aa}`, `{""}` and `{""}`, including the empty match right after `{aa}` that an iterator skipping adjacent empty matches would drop. `MatchSet::row` builds each row as `build_regexp_match_result` does, one element per parenthesized subexpression, or the whole match when the pattern has none, and NULL for a span the engine left unset, so the rows agree with PostgreSQL in number, order and value.

PostgreSQL grows its location array through sizes of the form `2^n - 1` and reports `54000` once it would need more than `MaxAllocSize / sizeof(int)`, 268,435,455 entries: two per recorded span and one for the input length it stores after the last match. `MatchSet` tests the same count before it records a match, so the error arises at the same match. The strict function returns no rows for a NULL argument: the cursor reports that before any work, and the planner no longer replaces the call by a NULL constant, while the all-constant fold already excluded set-returning calls. Flag parsing is the previous loop with `g` recorded instead of conditionally rejected, so every flag string keeps its options, and a string with a letter outside PostgreSQL's set reports `invalid regular expression option` for its first such letter, which previously was `g` itself when `g` preceded it in a single-result function. The changed observations of this unit are therefore the `regexp_matches` rows, `g` in the single-result functions, and the `regexp_match` named arguments. Positional calls of the other set-returning functions keep their argument evaluation, and named calls of set-returning functions without declared argument names still report an undefined function.

Matching happens once, when the cursor is created, as in PostgreSQL's first call. The compiled expression and the engine's working memory are charged to the creating control's allowance and released when the search ends, and the cursor keeps only the input's code points and the match spans, which PostgreSQL likewise keeps in the function's multi-call memory context. Rows are produced on demand: each request builds one capture array under the requesting control and transfers it to its consumer, so one row is resident in the stream at a time, and a rejected row is released while the cursor stays at that match, so a later request produces it again. Production follows ordinary scalar evaluation, which, like PostgreSQL, does not bound function results by `work_mem`. Execution checks query cancellation before each row, the owner checks both cancellation scopes before each row and after each search, and the engine's own interrupt checks observe them during compilation and matching. Evaluation reads only its arguments and does not touch storage or catalog state, and the new catalog rows add identities without changing overload resolution.

## Split functions (#983)

### Ownership and correction

SQL owns the split kernels, flag validation, named-argument positions and table-function signatures; Execution owns the table-function row stream and the routine catalog projection. `regexp_split_to_table` previously compiled its pattern in Execution with the Rust `regex` crate, accepted exactly two arguments, reported compile errors as `42804`, and split at the empty matches at the start and end of the input that PostgreSQL ignores; `regexp_split_to_array` did not exist (`42883`). The SQL owner now provides a `RegexSplit` cursor. Creating it parses the flags, rejects `g` with `22023`, `regexp_split_to_table() does not support the "global" option` or its `regexp_split_to_array` counterpart, and finds every match through `MatchSet` with degenerate matches ignored, as both functions call `setup_regexp_matches`; each request returns the next piece, the text between consecutive matches, as `build_regexp_split_result` does. Execution streams `regexp_split_to_table` through the same one-column adapter as `regexp_matches` and no longer depends on the `regex` crate, and `regexp_split_to_array` is a strict scalar kernel of the owner that collects the same pieces into one `text[]` value. Both functions gain PostgreSQL's argument names `string`, `pattern` and `flags`, and the routine catalog gains OIDs 2765 to 2768 with their argument names, the set-returning flag of `regexp_split_to_table` and its row estimate of 1000.

### Preservation argument

Let `m1, ..., mk` be the matches `setup_regexp_matches` records for a split: every match of the pattern, searched as `regexp_matches` searches with `g`, except the degenerate ones, which are empty matches at the start or end of the input or directly after the previous match. PostgreSQL returns the `k + 1` pieces between consecutive matches, from the start of the input or the end of the previous match to the start of the next match or the end of the input. `MatchSet` applies PostgreSQL's degenerate test to each search result, keeping a match that starts before the end of the input and ends after the previous match's end, and `RegexSplit` returns the same `k + 1` slices in order, so `regexp_split_to_table` returns PostgreSQL's rows and `regexp_split_to_array` PostgreSQL's array, with the matches `regexp_matches` would find, because both run the same engine and loop. A two-argument split without empty matches returned the same pieces before whenever the previous engine selected the same matches, so the changed observations are the ignored degenerate matches, the flags argument and its `g` diagnostic, the engine's syntax and diagnostics, and the new array function and identities.

As for `regexp_matches`, matching happens when the cursor is created, the cursor keeps the input's code points and the match spans, and each piece is admitted under the requesting control; a rejected piece is released and the cursor stays before it. `regexp_split_to_array` releases the cursor's code points and spans before it returns the array. The owner checks both cancellation scopes before each piece and after each search, Execution checks query cancellation before each row, and evaluation reads only its arguments.

## Search loop of the counting, position and replacement functions (#999)

### Ownership and correction

SQL owns the four kernels. `regexp_count`, `regexp_instr` and `regexp_substr` previously iterated the Rust crate's matches over the slice of the input after `start`, and `regexp_replace` its captures, so they skipped an empty match that begins where the previous match ended, and `^`, `\A` and word boundaries treated `start` as the beginning of the string. They now use PostgreSQL's search loop. `regexp_count`, `regexp_instr` and `regexp_substr` validate their parameters and then their flags, reject `g`, and record every match from character `start` through `MatchSet`, as each calls `setup_regexp_matches` with `start - 1` and with subexpressions only for a positive `subexpr`; a pattern without subexpressions records its whole match as its only pattern, so `subexpr` 1 selects it, as in PostgreSQL. `regexp_replace` follows `replace_text_regexp`: it compiles the pattern before it searches, so an invalid pattern is reported even when `start` lies beyond the input, and its four-argument form with text flags reports flags that begin with a digit with PostgreSQL's hint `If you meant to use regexp_replace() with a start parameter, cast the fourth argument to integer explicitly.`, as `textregexreplace` does before `parse_re_flags`. An invalid occurrence is reported as `invalid value for parameter "n"`, PostgreSQL's spelling.

### Preservation argument

PostgreSQL computes `regexp_count`, `regexp_instr` and `regexp_substr` from `setup_regexp_matches(input, pattern, flags with g, start - 1, collation, subexpr > 0, false, false)`: the number of matches, or the start or end (`endoption`) and the text of subexpression `subexpr` of match `n`, with 0 or NULL when match `n` or that subexpression does not exist or did not take part in the match. `MatchSet::find` with the same start and subexpression choice records the same matches, as argued for `regexp_matches`, and the kernels apply the same selection, so positions are PostgreSQL's one-based character positions. `regexp_replace` runs the loop of `replace_text_regexp`: it compiles with `REG_NOSUB` unless the replacement contains `\1` to `\9`, as `check_replace_text_has_escape` decides, searches the whole input from `start - 1`, replaces match `n`, or every match when `n` is 0, advancing as `setup_regexp_matches` does, copies the rest unchanged, and expands `\&`, `\1` to `\9` and `\\` as `appendStringInfoRegexpSubstr` does; without an explicit `n`, `g` selects every match and its absence the first. Each function therefore returns PostgreSQL's result whenever the searches return PostgreSQL's spans, which PostgreSQL's engine (#980) guarantees.

The parameter checks, NULL handling and flag order are unchanged apart from the occurrence parameter's name. The changed observations are the matches the loop now finds, anchors and word boundaries at `start`, subexpression 1 of a pattern without subexpressions, the replacement's compile-before-search order and the digit-flag hint. Each kernel retains only its admitted result: the input's code points, the match spans and the engine's working memory are charged to the call's allowance and released before the result is returned. The replacement loop checks both cancellation scopes before each search, as `replace_text_regexp` calls `CHECK_FOR_INTERRUPTS()`, and the other kernels check them after each search.

## Routine result types in `information_schema.routines` (#992)

### Ownership and correction

Execution owns the `information_schema` projection and the `reg*` output catalog. `information_schema.routines` previously reported `USER-DEFINED` and NULL type columns for array results, such as the `text[]` of `regexp_match`, and listed every built-in routine whatever the current user's privileges. It now derives `data_type`, `type_udt_catalog`, `type_udt_schema`, `type_udt_name` and `dtd_identifier` from each routine's `prorettype` through `pg_type` and `pg_namespace`, as PostgreSQL 18's view definition does: `ARRAY` for a varlena type with an element type, `format_type` for another `pg_catalog` type and `USER-DEFINED` otherwise, so `text[]` results report `ARRAY` and `_text`. Procedures have no result type; `udt_catalog`, `udt_schema` and `udt_name` stay NULL; `parameter_style`, `security_type` and `as_locator` follow the definition; user routine rows report `MODIFIES` and the empty source of a SQL-standard body; and a routine is listed only through usage of its owner role or its `EXECUTE` privilege, and its definition only through usage of its owner role, as the view's `pg_has_role` and `has_function_privilege` conditions select them. The `reg*` output catalog records `pg_type.typlen` for the `ARRAY` rule, and its alias-constant output moves to its own module.

### Preservation argument

The view is a projection of catalog state: it reads routine identities, result types, owners and `EXECUTE` privileges and writes nothing. Each derived type column is a function of `prorettype`, `typelem`, `typlen` and the type's namespace, computed with the view's own `CASE` order, and the row filter is the view's disjunction of owner usage and `EXECUTE`. For a current user with either right, a routine's row therefore equals PostgreSQL's row in these columns and keeps its other columns, and for any other user the row is absent, as in PostgreSQL. The `reg*` output catalog only gains the `typlen` attribute the rule reads.

## Catalog signatures of the regular-expression functions (#992)

### Ownership and correction

SQL owns the fixed built-in registry, overload selection and the set-returning declarations; Execution owns the routine catalog projection, `regprocedure` input and routine privileges; evaluation remains in the SQL regular-expression owner. The routine catalog had no PostgreSQL identities for the scalar regular-expression functions, so persistent databases rejected a stored expression such as `CHECK (regexp_like(x, 'a'))` with `42883`, and `'regexp_like(text,text)'::regprocedure` failed the same way. The SQL fixed built-in registry now declares every `pg_proc` overload of `regexp_count`, `regexp_instr`, `regexp_like`, `regexp_match`, `regexp_matches`, `regexp_replace`, `regexp_split_to_array`, `regexp_split_to_table` and `regexp_substr` with its argument names and no defaults, and the FROM-clause set functions select from the same declarations. Select lists, FROM, LATERAL, ROWS FROM, WHERE, views, prepared statements and routine bodies therefore select PostgreSQL's overload as `func_get_detail` does: incompatible or missing arguments report `42883` with PostgreSQL's signature text, such as `function regexp_like(unknown, unknown, integer) does not exist`, an unknown fourth `regexp_replace` argument selects flags, untyped parameters take the declared types, named arguments follow the declared names and their case, including `"N"`, and EXECUTE authorization reaches the selected overload, including select-list set-returning calls.

Execution adds the PostgreSQL 18.4 identities of the 23 scalar overloads, OIDs 2284, 2285, 3396, 3397 and 6251 to 6269, with their argument names, strictness, immutability, parallel safety and source names; with OIDs 2763 to 2768 from #982 and #983, all 29 regular-expression overloads carry PostgreSQL's identities. CHECK constraints, defaults, generated columns, expression and partial indexes and domain constraints store and print the calls on every provider, `regprocedure` accepts them, and `GRANT` and `REVOKE EXECUTE` persist across reopening. A set-returning call stored without a binding by an earlier version selects its declaration when its projection is planned, so such definitions keep executing under the same authorization.

### Preservation argument

Declarations change which calls resolve and which identity a call binds, not how a resolved call evaluates: evaluation still dispatches the bound call by name to the SQL owner's kernel with its positional arguments. For every call PostgreSQL resolves, the registry selects the same `pg_proc` overload by the same candidate rules, so the arity, argument order and coercions the kernel receives are PostgreSQL's, and the result is the kernel's result for those values; positional calls with text arguments keep their results. A call PostgreSQL rejects reports PostgreSQL's `42883`. The catalog rows add identities with PostgreSQL's attributes and change no other routine. A definition stored with a binding records the selected identity, and a definition stored before these declarations existed keeps its unbound call, which selects the same declaration when it is planned, so persisted formats are unchanged and older catalogs keep loading and executing.

## PostgreSQL's regular-expression engine (#980)

### Ownership and correction

The new crate `uqa-pg-regex` owns PostgreSQL's engine and the backend services it needs. It has no workspace dependencies, and the dependency policy admits it as a leaf that `uqa-sql` may depend on. `scripts/sync-uqa-pg-regex.py` imports 23 unchanged PostgreSQL 18.4 files from tag `REL_18_4` (`f5cc81719e6da4cbdb1f797c48b693e91018153a`): Henry Spencer's engine from `src/backend/regex`, the regex and `pg_wchar` headers, the builtin provider's Unicode 16 category and case tables and both COPYRIGHT files. The safe API is `Regex::compile`, which runs `pg_regcomp` with PostgreSQL's `REG_*` compile flags under a `RegexCollation`, `Regex::exec`, which runs `pg_regexec` on code points from a search start into `MatchSpan` slots in `regmatch_t` layout, `Regex::subexpression_count`, which is `re_nsub`, and `RegexError`, which carries the engine's `REG_*` code explained with `pg_regerror`'s exact text, a cancellation, or an error PostgreSQL raises with its own SQLSTATE, message and hint. `shim/regex/regc_pg_locale.c` replaces PostgreSQL's file with a port that keeps the selected strategy in the per-thread engine frame instead of process-global variables. It implements four strategies: `C`, PostgreSQL's ASCII table, for `C`, `POSIX` and `ucs_basic`; `BuiltinCUtf8` and `BuiltinUnicodeFast`, the imported Unicode 16 tables with the builtin provider's `casemap_full` setting, for `pg_c_utf8` and for `pg_unicode_fast` and the database default; and `Icu`, ICU4C's `u_is*` and simple case-mapping definitions evaluated over the workspace's ICU4X Unicode 16 data, for `unicode`. The libc strategies are not needed, because UQA defines no libc collation other than `C` and `POSIX`. `RegexCollation::from_oid` applies `pg_set_regex_collation`'s order of checks and its errors in Rust before any C code runs, character-class member lists are built once per process, so a class reference allocates nothing, as a hit in PostgreSQL's ctype cache does, and global C symbols carry a `uqa_pg_regex_` prefix so that they cannot collide with the parser objects of `uqa-pg-query`.

Every engine allocation, chunk header included, is reserved through the caller's `RegexResources` hooks before it happens and released after it is freed. The shim implements `palloc_extended` and its relatives over per-operation memory contexts owned by the Rust wrapper: a refused engine reservation surfaces as `REG_ESPACE`, and a refused reservation for the converted pattern or the expression's memory context reports `out of memory` (`53200`), as `palloc` and context creation do in `RE_compile_and_cache`. The pattern conversion takes one code point slot per pattern byte plus one and is checked against `MaxAllocSize` first, so a pattern of 268,435,455 bytes or more fails with `invalid memory alloc request size` (`XX000`). Dropping a `Regex` deletes its memory context, as `RE_compile_and_cache` deletes the context of an expression it discards, and releases every reserved byte. `CHECK_FOR_INTERRUPTS()` and `stack_is_too_deep()` consult the same hooks. Each operation runs inside a C function that owns a `sigsetjmp` frame without saving the signal mask, selected as PostgreSQL's `c.h` selects it, so cancellation, hook panics, allocation-size errors and stack restarts leave the engine by `longjmp` only to C code that Rust called directly, never across a Rust frame or between stacks; the wrapper then frees the abandoned context and resumes a hook's panic.

The engine recurses on the stack. Every compilation and execution may use `MAX_STACK_DEPTH`, 2 MiB, PostgreSQL's default `max_stack_depth`, with `STACK_DEPTH_SLOP`, PostgreSQL's 512 KiB, to spare, and fails with `REG_ETOOBIG`, `regular expression is too complex`, beyond it; the hooks may only set a lower limit. An operation runs on the thread's own stack when that stack has the headroom. Otherwise it runs there first, capped at the depth that leaves the slop free, and a deeper check abandons it through its error frame and restarts it from the beginning on a separately allocated stack of the same thread through the `stacker` crate, so ordinary operations on threads with a few megabytes of stack allocate nothing and no result depends on the thread's stack. Under `wasm32-unknown-emscripten` the engine's recursion uses the WebAssembly call stack, which C can neither measure nor switch, so the build compiles `regcomp.c` and `regexec.c` with `-finstrument-function-entry-bare` and `-fstack-protector-all`. The shim's `__cyg_profile_func_enter_bare()` then counts the thread's live engine frames exactly, and the wrapper charges each frame 1404 bytes, so that at most 1493 frames stay live: half of Node.js 22's 864 KB default V8 stack at 296 bytes per frame, the largest engine frame measured, which leaves the other half to the embedding. Every compilation and execution there fails with `REG_ETOOBIG` before it can exhaust the call stack, at a compile-and-match overhead of 11 to 14 percent, and native builds stay uninstrumented.

### Preservation argument

The crate changes no SQL behavior by itself; only the SQL owner's evaluation below calls it. Its guarantees are stated against PostgreSQL's own functions: let `regcomp(p, f, s)` and `regexec(r, x, i)` be PostgreSQL 18.4's compilation and search for pattern `p`, flags `f`, locale strategy `s`, compiled expression `r`, code points `x` and search start `i`. The memory services return NULL only for a refused reservation or a failed allocation, where PostgreSQL's `palloc_extended` with `MCXT_ALLOC_NO_OOM` returns NULL for a failed allocation, so the engine takes PostgreSQL's own `REG_ESPACE` path. The interrupt and stack checks only stop an operation. A stopped operation leaves no allocation behind: over the life of an expression the released total equals the reserved total, and an abandoned operation's context is freed before its error or panic continues.

A restart on a separate stack reruns a deterministic operation from its beginning after its memory is released, so it returns what the first attempt would have returned with enough stack. The stack each recursion level uses depends on the compiler and architecture, as it does for PostgreSQL itself: about 240 bytes per nested capturing group with GCC on x86-64, 320 with GCC on AArch64 and 400 with Clang on AArch64, so the deepest pattern accepted under the 2 MiB budget differs between platforms as it does between PostgreSQL builds, and under Emscripten the frame budget sets the bound instead. Per-thread engine state makes operations on different threads independent, and a hook may run another operation with its own locale.

## Statement cancellation scope

### Ownership and correction

SQL owns the running statement's cancellation as scalar evaluation sees it: `uqa_sql::expr::StatementCancellationScope` enters a statement's cancellation token in a thread-local slot and restores the enclosing token on every exit, `check_statement_cancellation()` reports a cancel request or `statement_timeout` with the token's reason and succeeds outside any statement, and `statement_cancellation()` captures the token for a worker thread. Execution's `StatementThreadContext` pairs the token with the statement's temporal input, and `StatementThreadScope` enters and restores both at every compiled, batch, cursor, prepared, routine body and portal entry, for analysis, planning including constant folding, and execution. The parallel executor enters the dispatching thread's context exactly on each rayon worker, so a worker that runs work dispatched outside a statement has neither a token nor a transaction clock, and the scroll-cursor `UNION ALL` branch thread enters the context captured on the thread that starts it. Engine builds the context in one place from the session's transaction clock, date order, interval style and cancellation token, and enters it at its statement boundary and around the direct APIs that evaluate SQL expressions: the reads it admits, such as `get_document`, `find_conflict` and `deep_predict`, which materialize virtual generated columns or evaluate lowered constants, the evaluating row writes `add_document`, `update_document_fields` and `patch_document_fields` with their vector variants, transaction completion with its deferred triggers and holdable cursor materialization, and `deep_learn_table`. Rust code that constructs the compiled statement or prepared registration contexts supplies the session's cancellation token, and hosts that evaluate SQL expressions outside these entry points can enter the scope themselves.

Regular-expression evaluation observed cancellation only through the `ProductionControl` its caller passed, and ordinary evaluation, planning-time folding and table-function construction call it without a cancellation scope of their own, so `statement_timeout` and cancel requests could not stop a long compilation or match there. The engine's interrupt checks and the search and replacement loops between engine operations now observe the running statement's scope as well as the call's own, as `CHECK_FOR_INTERRUPTS` does inside PostgreSQL's engine and in the loop of `replace_text_regexp`, so cancellation interrupts matching wherever it runs. Building the scope also corrected the special date inputs `now`, `today`, `tomorrow` and `yesterday` in scroll-cursor `UNION ALL` branches, which had resolved against the wall clock because the branch thread ran without its statement's temporal input.

### Preservation argument

A statement that is not canceled observes success at every new check, so its results, row order, diagnostics and state effects are unchanged; the checks only add observation points. Outside a statement the slot is empty and every check succeeds, so work dispatched outside a statement, including by a worker that earlier ran a statement's work, never observes a stale cancellation, and each scope restores its caller's token on every exit, including an error or a panic unwinding through it, so nested statements, routine bodies and workers return to their caller's statement. A canceled statement stops at the next check with `57014` and the token's reason, as PostgreSQL reports `canceling statement due to user request` or `canceling statement due to statement timeout` from `CHECK_FOR_INTERRUPTS`; the regular-expression engine then frees the abandoned operation's memory and the call releases its allowance, as for a canceled production control. The temporal input entered with the token is the statement's own, so the special date inputs in a scroll-cursor branch now read the transaction start, as PostgreSQL resolves them. Outside any transaction or statement, as for a direct write to a memory engine, the session has no transaction clock, so the context carries none and evaluation reads the wall clock as `now()` does there, while statement entry points whose inputs supply no clock keep their caller's; a rayon worker no longer keeps the clock of a statement whose work it ran before.

### Verification

Owner tests show that work outside a statement continues and that a statement observes its token with the reason it was canceled for, and a regular-expression owner test shows that a canceled statement scope stops both the engine and the call between engine operations with `57014` under an uncontrolled production control. Execution tests cover the batch, compiled, prepared and portal-worker entry points. Engine tests show that a registered scalar function observes `Engine::cancel` and `statement_timeout` through `check_statement_cancellation` in a plain SELECT, a SQL routine body, EXECUTE, a portal FETCH and a scroll-cursor `UNION ALL` branch, a registered function that a stored generated column reaches through an immutable SQL function observes `Engine::cancel` during `add_document`, `update_document_fields` and `patch_document_fields`, and engine unit tests show that direct reads and evaluating row writes run under the session's clock, styles and cancellation. Dissecting 3000 nested capture groups takes seconds in PostgreSQL 18.4 and in UQA; with `statement_timeout` at 50 ms it now stops with `57014` `canceling statement due to statement timeout`, both in a scalar `regexp_match` and in `regexp_matches` in FROM. An independent PostgreSQL 18.4 transcript of the scroll-cursor branch query under `DateStyle` `ISO, DMY` and `IntervalStyle` `sql_standard` supplies the expected date, interval and clock results of the special inputs.
