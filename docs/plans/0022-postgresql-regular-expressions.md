## Substring pattern forms (#981)

### Ownership and correction

SQL owns overload resolution, the regular-expression kernels and scalar execution; Planner owns constant simplification; Execution owns the routine catalog projection. Overload binding already resolved `substring(text, text)` and `substring(text, text, text)`, but evaluation dispatched by name and read the second and third arguments as integer positions. Execution binding now derives `FunctionDispatch::RegexSubstring` or `FunctionDispatch::SimilarSubstring` from the resolved argument types, as it derives the selected `to_bin` and `random` overloads, and the dispatched PostgreSQL scalar kernels pass those calls to the regular-expression owner's `eval_dispatched_substring`. Prepared and stored bindings keep their existing representation without a dispatch, so definitions created before this change select the pattern forms after reopening and no persisted format changes.

The POSIX form compiles the pattern through the existing regular-expression owner and returns the first parenthesized subexpression or the whole match. The SQL form is PostgreSQL's SQL-language function `substring($1, similar_to_escape($2, $3))`, which PostgreSQL inlines while planning. Its kernel therefore returns NULL for a NULL pattern or escape, then applies the existing `similar_to_escape` kernel, and only then returns NULL for a NULL string before the same extraction. The planner keeps the call but follows `simplify_function`: a strict NULL constant or an all-constant call is folded as before, and otherwise a constant pattern and escape are translated by `check_constant_similar_translation`, as the inlined body's constant `similar_to_escape` would be folded, unless the caller lacks EXECUTE on the routine, in which case PostgreSQL does not inline it either.

The routine catalog gains PostgreSQL's identities for the implemented `substring` and `substr` overloads (OIDs 877, 883, 936, 937, 2012, 2013, 2073, 2074, 2085 and 2086), including OID 2074 as a SQL-language routine with PostgreSQL's stored body. Stored expressions, CHECK constraints, defaults, `regprocedure` input and routine privileges previously failed for every `substring` and `substr` form because no catalog signature existed. The bit-string overloads 1680 and 1699 are not implemented (#989).

### Preservation argument

Dispatch is a function of the resolved signature only. The positional signatures `(text, integer)`, `(text, integer, integer)` and their bytea counterparts map to no dispatch, so their calls reach the unchanged positional kernel exactly as before. Only `(text, text)` and `(text, text, text)` map to the new variants; before this change those calls failed with `42804` for every non-numeric pattern and returned a positional slice when the pattern text parsed as an integer. Every previously successful result of a positional signature is therefore preserved, and the only changed observations are those of the two pattern signatures, which now follow PostgreSQL's definitions.

For the POSIX form, PostgreSQL's strict `textregexsubstr(s, p)` returns the span of the first parenthesized subexpression `m1` when `p` has one and the whole match `m0` otherwise, and NULL when the selected span is absent. The implementation computes the same function of `(m0, m1)` from the owner's captures, so any remaining difference from PostgreSQL is confined to the engine's choice of `m0` and `m1`, which #980 tracks.

For the SQL form, let `t(p, e)` be `similar_to_escape(p, e)`, which is strict and whose translation text equals PostgreSQL's for every independently observed pattern. PostgreSQL evaluates `substring(s, p, e)` as `NULL` when a constant argument is NULL, as the folded value when all arguments are constant, and otherwise as `textregexsubstr(s, t(p, e))` with `t` folded when `p` and `e` are constant. The planner preserves the first two cases through the existing folds and reproduces the third case's planning-time evaluation of `t` without changing the expression. At execution, the kernel evaluates `NULL` when `p` or `e` is NULL, otherwise `t(p, e)`, then `NULL` when `s` is NULL, otherwise the POSIX extraction: this is exactly the strict evaluation of the inlined body, including its error precedence. Any remaining difference is again the engine's selection of matches, including PostgreSQL's non-greedy prefix produced by `t`.

The new catalog rows add identities for routines that already resolved and executed; they do not change overload resolution, results or the routine catalogs of other functions. Evaluation reads only its arguments and the per-call compiled pattern. It does not touch storage, catalog state, row support, multiplicity or ordering. The input copy, translated pattern and result are admitted under the caller's allowance; only the result survives a successful call, and a rejected output releases its reservation. Both cancellation scopes are checked before and after matching.

Nine stored-definition, deferred-error and catalog cases pass again after persistent reopening. Before the correction, 29 of its first 34 single-statement queries differed. Four SQL owner tests replay its constant and row-level cases, planning translation errors, admission and cancellation; the fixed-overload binding test covers all four `substring` signatures; a planner test covers PostgreSQL's planning-time translation; and an execution catalog test compares the ten routine identities and the stored body of OID 2074. Remaining differences inside these forms are match selection and the text of invalid-pattern messages (#980), CONTEXT for errors raised inside the SQL-language form (#306), SQL-syntax printing in stored definitions (#984) and constant folding of unreferenced subquery outputs (#990); the manifest item `functions.substring-pattern-forms` is therefore `partial`. Automatic run 39025611269 accepted the final head with all 1,353 Linux and macOS regression cases, and the unit merged as `1b3557fa8` in #986.

## Set-returning `regexp_matches` (#982)

### Ownership and correction

SQL owns the regular-expression kernels, flag validation, named-argument positions, set-returning classification and table-function signatures; Planner owns constant simplification; Execution owns table-function row streams and the routine catalog projection. Evaluation previously routed `regexp_matches` with the scalar `regexp_match` to one capture array or NULL and accepted `g` without iterating, so the function returned at most one row, returned a NULL row when nothing matched, and was undefined in `FROM`. The SQL owner now provides a `RegexMatches` cursor that owns its input copy and compiled pattern and produces one capture array per request, and Execution adapts it to a lazy one-column table-function stream, which `FROM`, `LATERAL`, `ROWS FROM`, `WITH ORDINALITY` and the select-list set projection all consume. Semantics classify `regexp_matches` as a set-returning built-in with PostgreSQL's named `(text, text)` and `(text, text, text)` signatures and `text[]` column, named arguments of a built-in table function take their declared positions as in a scalar call, and the planner no longer folds a strict set-returning call with a NULL input to one NULL value.

Flag parsing now validates the whole flag string before a caller inspects `g`, as `parse_re_flags` does. `regexp_matches` and `regexp_replace` accept `g`; `regexp_match`, `regexp_like`, `regexp_count`, `regexp_instr` and `regexp_substr` reject it with `22023`, `<function>() does not support the "global" option`, before the pattern is compiled, and `regexp_match` adds PostgreSQL's hint. These functions previously reported `g` as an invalid option when the loop reached it. `regexp_match` also gains its PostgreSQL argument names. The routine catalog gains OIDs 2763 and 2764 with their argument names, set-returning flag and row estimates of 1 and 10.

### Preservation argument

Let `m0, m1, ...` be the matches PostgreSQL's `setup_regexp_matches` records for `regexp_matches`, which does not suppress degenerate matches: the first search starts at offset 0, each later search starts at the end of the previous match, or one character later after an empty match, and the iteration stops once that start passes the end of the input; without `g` only `m0` is taken. The cursor computes the same sequence from the engine's leftmost-first search at each start (`captures_at`), keeping the whole input as search context so anchors and word boundaries see the preceding text, and steps one Unicode scalar after an empty match, which is PostgreSQL's one-character step in a UTF-8 database. It deliberately does not use the native match iterator, which skips an empty match adjacent to the previous match and would drop rows PostgreSQL returns, such as the `{""}` after `{aa}` in `regexp_matches('aab', 'a*', 'g')`. Each row applies the unchanged capture-array construction of `regexp_match` to its match, so whenever the engine selects the same match as PostgreSQL from each start, the rows agree in number, order and value; any remaining difference is confined to match selection, which #980 tracks.

The strict function returns no rows for a NULL argument: the cursor reports that before any work, and the planner no longer replaces the call by a NULL constant, while the all-constant fold already excluded set-returning calls. Flag parsing is the previous loop with `g` recorded instead of conditionally rejected, so every flag string keeps its options, and a string with a letter outside PostgreSQL's set reports `invalid regular expression option` for its first such letter, which previously was `g` itself when `g` preceded it in a single-result function. The only changed observations are therefore the `regexp_matches` rows, `g` in the single-result functions, and the `regexp_match` named arguments. Positional calls of the other set-returning functions keep their argument evaluation, and their named calls still report an undefined function.

Rows are produced on demand. The cursor retains its input copy, compiled pattern and next search offset, and each requested row is one capture array that transfers to its consumer, so one row is resident at a time. Production follows ordinary scalar evaluation, which, like PostgreSQL, does not bound function results by `work_mem`. Under a controlled allowance the owner admits the input copy, the prepared pattern and each row, releases a rejected row and leaves the cursor at that match. Execution checks query cancellation before each row, and the owner checks both cancellation scopes before and after each search. Evaluation reads only its arguments and does not touch storage or catalog state, and the new catalog rows add identities without changing overload resolution.

### Verification

The independent Docker PostgreSQL 18.4 transcript `tests/parity/pg18/regexp_matches_rows_oracle.expected.json` (70 identified statements, captured with `tests/parity/pg18/capture_command_completion_oracle.py` in a disposable database) passes on memory, native SQLite, SQLite Key/Value and redb, and nine stored-view, table, index-rejection and catalog cases pass again after persistent reopening. Before the correction, 46 of its 55 standalone statements differed. Four SQL owner tests replay its constant rows and flag diagnostics, the single-result functions' global-option order, admission and cancellation; the named-argument test covers both functions; a planner test keeps the strict set-returning call; and Execution tests cover the row stream and compare both routine identities and their set metadata. PostgreSQL's hint for set-returning calls in CASE, COALESCE, aggregate and window arguments, and its SQLSTATE for the NOT operand, are missing for every set-returning function (#993), so the transcript keeps only the matching WHERE case. Invalid-pattern messages and match selection remain with #980, and the scalar regular-expression catalog identities with #992. Automatic Linux/macOS acceptance is required before delivery.
