# Native range subtype distance

This bounded unit continues original #638 record 65 with the six native range subtype-distance functions. It also corrects the independently reproduced wide-date input/output defect [#969](https://github.com/cognica-io/uqa-engine/issues/969), which prevented a valid distance input from reaching its kernel. Record 65 remains incomplete: public custom range declarations and generated constructors, native canonical routine aliases, remaining lifecycle/operators and provider/language acceptance still require delivery. The full date/timestamp and calendar-consumer requirements of original record 34 and the wider datetime input work in #289 remain open; only the independently verified finite date input/output boundary and the directly affected range-successor boundary are corrected here.

## Ownership and contract

SQL owns fixed routine signatures, strictness and the numerical distance kernels. Execution projects the six existing PostgreSQL routine OIDs and native source names. Core owns the date carrier and Gregorian input/output conversion. Engine contributes only public-call acceptance; there are no new Cargo dependencies, features, storage formats or execution algorithms in Engine.

The functions are `int4range_subdiff(integer,integer)`, `int8range_subdiff(bigint,bigint)`, `numrange_subdiff(numeric,numeric)`, `daterange_subdiff(date,date)`, `tsrange_subdiff(timestamp,timestamp)` and `tstzrange_subdiff(timestamptz,timestamptz)`. Every result has type `double precision`; a NULL operand yields NULL after ordinary SQL type selection. The routines are immutable, strict and parallel safe, and do not change database state. Native integer and temporal inputs use the existing fixed Datum encoder, including PostgreSQL's epoch and infinity sentinels. Numeric subtraction and conversion reuse the existing controlled Core arithmetic and SQL floating-input owners.

## Carrier and preservation argument

Let $T$ be the selected subtype, $D_T$ its admitted non-NULL values, $F$ IEEE 754 binary64 values including infinities and NaN, and $E$ SQL diagnostics. The new scalar observation is $s_T:D_T\times D_T\to F+E$, extended strictly to NULL. Let $p_T$ encode the existing PostgreSQL fixed-width Datum and let $\operatorname{fl}$ denote binary64 round-to-nearest, ties-to-even. For integer and date inputs, $s_T(a,b)=\operatorname{fl}(\operatorname{fl}(p_T(a))-\operatorname{fl}(p_T(b)))$. Timestamp inputs apply one further rounded division by $10^6$. For numeric inputs, exact decimal subtraction occurs first and SQL's numeric-to-binary64 conversion observes that result, including its established NaN, infinity, overflow and underflow rules. These are the operations in PostgreSQL 18.4 [rangetypes.c](https://github.com/postgres/postgres/blob/f5cc81719e6da4cbdb1f797c48b693e91018153a/src/backend/utils/adt/rangetypes.c); the fixture pins this revision independently of the UQA implementation.

For int4 and date, both signed inputs and their difference fit exactly in binary64, so the kernel equals exact integer subtraction of their physical values. For int8, set $u=2^{-53}$ and $A=|p_T(a)|+|p_T(b)|$. Each conversion has absolute error at most $u$ times its input magnitude and rounded subtraction contributes at most $u(1+u)A$, giving total absolute error at most $(2u+u^2)A$. Timestamp division adds one rounding, yielding at most $(3u+3u^2+u^3)A/10^6$. All fixed-input intermediate magnitudes remain finite and nonzero timestamp differences divided by $10^6$ remain normal. Numeric normal outputs have relative rounding error at most $u$ after exact subtraction; subnormal rounding has absolute error at most $2^{-1075}$, and conversion to zero from a nonzero decimal reports the PostgreSQL range diagnostic. Specials follow the captured native observations rather than laws for finite real numbers.

Distance is not an equality key, a selected comparator or a metric. Distinct adjacent large bigint values can produce zero distance; infinities in date and timestamp use finite native sentinels. Therefore no injectivity, positive-definiteness or substitution into exact/hash/index equality is asserted or implemented. Existing comparison, canonicalization and range construction operations are unchanged. The new function names enter the existing fixed-signature resolver, so schema precedence, coercion, strictness, result typing and stored call identity continue to be selected before evaluation. Pointwise application produces the defined scalar observation on each admitted row without modifying its support, multiplicity, payload or ordering. Any existing optimizer substitution still requires its original type, volatility, error and evaluation-order preconditions; immutability does not authorize treating this rounded observation as exact subtraction or a comparator.

## Gregorian date correction

Core keeps dates as signed Unix day counts. Input already validates the written era, leap year, month and day. A March-based year places leap day at the end of the arithmetic year; a 400-year Gregorian era contains $146097=400\cdot365+97$ days. Write the shifted year as $400e+y$, $0\le y<400$, and the shifted month as $m$, $0\le m<12$. The day index is $146097e+365y+\lfloor y/4\rfloor-\lfloor y/100\rfloor+\lfloor(153m+2)/5\rfloor+d-1-719468$. Euclidean division makes the same identity valid before year zero. Wide intermediate integers avoid overflow before the checked conversion to the existing signed day carrier.

The inverse first obtains the unique era and remainder by Euclidean division by 146097. For $0\le y\le400$, the March-based year-start count is $D(y)=365y+\lfloor y/4\rfloor-\lfloor y/100\rfloor+\lfloor y/400\rfloor$, with $D(400)=146097$. Splitting a year into its century, four-year block and residual year gives the quotient correction used by the inverse: for the era remainder $r$, $y=\lfloor(r-\lfloor r/1460\rfloor+\lfloor r/36524\rfloor-\lfloor r/146096\rfloor)/365\rfloor$. Substitution in each century/four-year residue gives $D(y)\le r<D(y+1)$; the final correction keeps the era's last leap day in year 399. Strictly increasing year starts make this $y$ unique. Subtracting that start yields the day of year; $\lfloor(5d+2)/153\rfloor$ selects its unique month interval, and the residual is its day. Restoring January/February to the following civil year inverts the original shift. These divisions therefore reconstruct the unique original calendar date; conversely, forward conversion reconstructs each integer day. ISO output applies only the existing no-year-zero era spelling, so formatting and parsing preserve each admitted date and its physical Datum. PostgreSQL's additional finite date check is $0\le\text{UnixDays}+2440588<2147483494$; infinities retain their existing separate sentinels. The correction removes Chrono's narrower calendar boundary from date input and output without changing the persisted carrier or timestamp input contract. Range canonicalization applies the same Core date-bound predicate after its finite successor; SQL reports PostgreSQL's `22008`, `date out of range`, before an invalid date can enter the result. Empty-range determination still precedes successor evaluation, and infinity endpoints bypass it. For each admitted finite bound whose successor is admitted, replacing an exclusive lower bound by its successor and an inclusive upper bound by its successor preserves the denoted discrete set; when no admitted successor exists, the operation preserves the native error instead of fabricating a bound.
